# @provino/expect

The neutral `expect` engine (Track 7 R1). It owns the front end, the per-test matcher state and the global matcher slot. A dialect supplies everything else through an `ExpectTable` (`@provino/types` `expect.ts`): the matchers, the asymmetric matchers, `this.utils`, and every word the engine prints. `ExpectPolicy.matcherTable` is a `ModuleRef` to the dialect's table factory. B08's notes are in `docs/plan/bundles/B08.md`.

## Map

A call follows Jest's `makeThrowingMatcher` (`expect/src/index.ts` L275–L395) step by step. `MatcherResultError` is the `errorShape: 'matcher-result'` error (Jest's `JestAssertionError`). |

## `errorShape: 'assertion-error'` and the table's other hooks (B25b, T7.6)

- **`ExpectTable.assertionError(result, message, call)`** makes the error a failed result throws under `assertion-error`: a wrong settlement's (`call.settlement`) and a custom matcher's (Vitest's `JestExtendError`); the Vitest table's own matchers throw Chai's `AssertionError` themselves, which the engine anchors at the call like a built-in's. No `matcherResult` is set on it. A table without the hook can't run under that shape (`EXPECT_NOT_IMPLEMENTED`). `errorShape` decides the error's class only. Under `assertion-error` `expect.soft` holds whatever the assertion throws (`handleError`, as Vitest's `wrapAssertion`), not only a failed result.
- **`ExpectPolicy.settlementCheck`**: `at-call` (Jest) checks `.resolves`/`.rejects`'s value when the matcher is called; `at-read` (Vitest, neutral) when `.resolves`/`.rejects` is read (a `TypeError` there), `.rejects` of a function calls it then, and the error captured at that read (`Target.outer`) is the stack a wrong settlement, a settled failure (`internal/restack.ts`'s `restack`: `Error: <message>` over its frames) and an unawaited assertion (`withFramesOf`, whose header reads the message set later and whose frames are taken when the stack is first read) report, as Vitest's `new Error('resolves')` is. An async result's error is anchored where it is made.
- **`ExpectPolicy.messageArgument`**: `expect(actual, message)` takes the message; the matcher reads it as `this.customMessage` and `assertionError` as `call.message`.
- **`ExpectTable.chain(actual, name, call)`**: a name that is no matcher, not `then` and not on `Object.prototype` reads the dialect's chain (Chai's `to`, `be`, …); the engine counts nothing for it. With a chain, a matcher call that passed synchronously returns the assertion it was read from (Vitest's `expect(1).toBe(1).to.equal(1)`). Absent: such a name reads `undefined` and a call returns `undefined`, as on Jest's plain object. **`ExpectTable.equals`**: a custom matcher's `this.equals` (Vitest's own); absent, Jest's. A table with its own `equals` gets no policy equality testers (`errors: 'assert'`, `invalidDate: 'equal'`): its `equals` judges both. A matcher's context also has `customMessage`, `soft` under `expect.soft` and `poll` on a try of `expect.poll`, each set only when it applies (assigned after the literal, so the hot path has one shape).
- **`ExpectPolicy.assertionCalls`**: `per-matcher-call` (Jest, neutral) counts each matcher call that returns a result; `per-expect-call` (Vitest) counts each `expect()`, `expect.soft()` and `expect.poll()` call (the poll counts itself, `poll.ts`), whatever runs on it, and nothing more.
- **`policyMessages`** (`src/policy-messages.ts`): the one copy of the words for the engine's own policies (a required assertion, an unawaited assertion, `expect.poll`'s timeout and refusals, outside a test), which are Vitest's. The engine and `createEndOfTest` put a table's `messages` over it (`ExpectTableMessages`: those five keys optional), so a table words only what it overrides.
- **The snapshot matchers hold a mismatch only when `SnapshotState.mismatch` is `end-of-test`** (D61); under `throw` it throws at the call.
- **`expect.poll`'s timeout error** takes the site's header (`Error: …`), as Vitest's `copyStackTrace` does.

## Rules that aren't obvious

- **Every error the engine makes or rethrows is anchored with `Error.captureStackTrace` above its own frames.** Our source runs from `packages/*/src`, which the harness reads as user code (only `node_modules/` frames are internal). Without the anchor, `userFrame` would point into the engine. The expect corpus compares `userFrame`, so a missing anchor fails it. Each path has its own anchor:
  - a direct call anchors above `throwingMatcher`;
  - `.resolves`/`.rejects` anchor above the named settle callback (`onResolved`/`onRejected`);
  - an async matcher's result anchors above `onMatcherResult`.

  An error a custom matcher throws itself (including from its `message` thunk) keeps its frames, as in Jest. The exception is a matcher library in `node_modules` run from source, where the external trap frame shows (DIVERGENCES DV6).
- **The error a wrong settlement throws** (`.resolves` on a rejection, `.rejects` on a resolution) is made in `expect()`, as Jest does, so it points at the `expect(` column. Only a function or a native promise (`util.types.isPromise`, which reads no property of the value) pays for that stack. Any other thenable gets its error when `.resolves`/`.rejects` is read.
- **Jest's tick counts are kept:** a thenable's own `.then`, then `.catch` on what it returns, with no `Promise.resolve` wrapping. Extra ticks would change races with a test's end (the policy corpus' unawaited cases).
- **`getMessage` keeps Jest's `(message && message())`.** A falsy `message` means "no message", and a string one throws `message is not a function`. The local is named `message` so V8 prints that text.
- **The state is per attempt, not one global.** A new attempt copies the file state (so `expand`, `testPath` and keys set in `beforeAll` carry over) and resets the counters. A key a test sets with `setState` stays in that attempt, where Jest would leak it to later tests (B08 notes).
- **What is counted outside a test follows `ExpectPolicy.outsideTestCounts`** (`createStateSource`'s option, which the worker, the expect corpus and the policy corpus pass). `'drop'` (neutral): the file state's counters reach no test. `'next-test'` (Jest): Jest keeps one state and resets it only at `test_done`, so the counters made at module scope, in a `beforeAll` or in an `afterAll` after a test's end move (`internal/counters.ts` `moveCounters`: calls, passes, `expectedAssertionsNumber` and `hasAssertions()` with their errors, held-back failures) into the next attempt state made, and the file state is zeroed. An attempt that made no assertion takes them when the end-of-test check calls `source.settle` (`hasAssertions()` from a `beforeAll` fails it); `stateOf` is a pure lookup, so the harness's and the sink's later reads move nothing. Concurrent attempts: the first that asserts or settles takes them. A skipped or todo test has no attempt and passes the counts over; each retry attempt takes what came since the one before; under concurrency the first attempt made takes them (Jest shares one state: the declared improvement). What the last test leaves is dropped. `fixtures/expect/policies/assertions-outside-test`, `ecosystem/jest-when`.
- **Built-ins carry Jest's `$$jest-internal-matcher` flag on the function**, defined non-writable as `setMatchers` does. Registering a built-in again with `extend`, or a frozen function, throws Jest's TypeError. The table's `promiseMatchers` aren't flagged, because Jest's `getPromiseMatcher` returns fresh, unflagged functions. Their errors are still re-anchored, since in Jest their frames are in `node_modules`.
- **The Proxy enumerates like Jest's plain object:** `ownKeys`/`has`/`getOwnPropertyDescriptor` report `not`, `rejects`, `resolves` and the matcher names, and other names read through to `Object.prototype`. Wrappers such as jest-expect-message walk those keys. `.not` and matchers are new objects on each read (DIVERGENCES DV4).
- **A snapshot matcher calls `this.dontThrow()` first** (T7.8), as Jest's `_toMatchSnapshot` and `_toThrowErrorMatchingSnapshot` do (`toMatchSnapshot`, `toMatchInlineSnapshot` and the two `toThrowErrorMatching*`): a mismatch goes to `suppressedErrors`, the test's other snapshots are still checked, and `createEndOfTest` fails the test when it ends. `toMatchFileSnapshot` and the matchers' own throws (`.not`, a bad argument, no state) still throw at the call. Both dialects get this today, because the matcher bodies are Jest's; Vitest's own table (T7.6) must decide whether its snapshot matchers hold a mismatch (Vitest's throw at the call).
- **The attempt state carries `currentTestPath` (the title path), `currentTestId` and `testFailing`** beside `currentTestName`: a snapshot's name joins the path with the policy's `keyJoin` (not `nameSeparator`), and a retry rolls back by test id.
- **`.resolves`/`.rejects` capture the state when the matcher is called,** not when the promise settles. A settle callback running outside the test's async context still counts into the test.

## The worker's boot order (U1)

1. `createStateSource(currentTest, { nameSeparator: core.nameSeparator, expand: expect.expand })`
2. `createMatcherRegistry()`, then `installMatchersSlot(source, registry)`, before any matcher module loads.
3. Load the table from `policy.expect.matcherTable` through the `BehaviourLoader`.
4. `createExpect({ policy, table, source, registry, unawaited, pollTimers })`: `unawaited` is `CorePolicy.unawaitedAsyncAssertion` and `pollTimers.advance` the file's fake clock (see "The async policies").
5. `snapshotRegistry(registry, expect)`, after `createExpect` has registered the table's matchers (a snapshot taken earlier would restore them away). Pass `expect`, or a file's `expect.extend` asymmetric forms outlive its restore.
6. Per file, `source.startFile(testPath)`; the worker opens the file's snapshots and puts the `SnapshotState` in the file state (`snapshotState`, which each attempt's state copies); then the setup files and the test file; after the file, `snapshot.restore()` when the environment is file-scoped.
7. Once, after `createRuntime`: `coreRuntime.onAfterTryTask(...)` calls the function `createEndOfTest({ source, messages: table.messages, policy: policy.expect, hasAssertionsWhenFailed })` returned and gives each error it returns to core with `info.fail(error)` (one error each: a thrown value would be one).

Per test, `source.stateOf(testId, { attempt, repeat })` (from the last `test-attempt-end`) gives the counts the result needs (`numPassingAsserts`). Core itself reports 0; the orchestrator's assertion-count sink (`worker/internal/runtime/sink.ts`) fills `assertions` and `passingAssertions` on `test-end`.

## The async policies (T7.8)

Everything here is a policy value or a table message; the engine names no runner.

| What | Switch | Behaviour |
|---|---|---|
| `expect.soft(x)` | `ExpectPolicy.soft` | The assertion runs with `dontThrow` semantics: a failure goes to `state.suppressedErrors` and the test goes on. `.not`, `.resolves`/`.rejects` stay soft (a soft promise assertion never rejects). Outside a test it throws `EXPECT_OUTSIDE_TEST` with `messages.outsideTest`. |
| `expect.poll(fn, { interval, timeout })` | `ExpectPolicy.poll { enabled, intervalMs, timeoutMs }`, `pollFailsOnTimeout` | Returns matchers (and `.not`) that call `fn({ signal })` again every `interval` until the matcher passes. Lazy: it starts on the first `then`/`catch`/`finally`. A try that fails is not an assertion call (the counter is put back); the call that decides counts once. On timeout the `AbortSignal` aborts and the last error is thrown with the stack of the matcher call; under `pollFailsOnTimeout: false` the poll just ends. `resolves`, `rejects`, `toThrow`, `toThrowError` and the snapshot matchers throw `EXPECT_POLL_UNSUPPORTED`. A bad callback, interval or timeout is `EXPECT_INVALID_ARGUMENT`. |
| unawaited `.resolves`/`.rejects`/poll | `createExpect({ unawaited })`, which the worker takes from `CorePolicy.unawaitedAsyncAssertion` | `'ignore'`: nothing changes, the assertion is the plain promise and its tick count is Jest's. `'fail'`: the call returns a thenable (`internal/awaitable.ts`) and puts a `PendingAssertion` in `state.pendingAsync`; `then`/`catch`/`finally` take it out. What is left at the test's end is reported through `messages.unawaited`, on an error captured at the call, so its first frame is the user's line. The underlying promise gets a no-op `catch`, so a failing unawaited assertion is reported as unawaited, not also as an unhandled rejection (Vitest 5 does the same). A poll is lazy under `'fail'` and starts at once under `'ignore'`. |
| `expect.assertions(n)`, `hasAssertions()` | none (always on) | Set the state; `end-of-test` compares `assertionCalls` with it. |
| `requireAssertions` | `ExpectPolicy.requireAssertions` | A test with no assertion call fails with `messages.requiredAssertions`; not added on top of `hasAssertions`. |
| `expect.unreachable(message)` | the table has `messages.unreachable` | Throws a `MatcherResultError` with the table's text. A table without it leaves `expect.unreachable` undefined. |

- **The end-of-test check** (`createEndOfTest`) returns the errors an attempt gains, in this order: the failures `expect.soft`/`dontThrow()` held back; `assertions(n)` not met; `hasAssertions()` with none made; a required assertion; the unawaited assertions. It reads the attempt's own state with `source.settle(test.id, { attempt, repeat })` (the state `stateOf` gives, or, under `outsideTestCounts: 'next-test'`, one made to take what the file state holds), so each run of a `test.concurrent` test counts alone (P4-P7), and it resets nothing: the assertion-count sink reads `numPassingAsserts` after it. On an attempt that already failed, `hasAssertionsWhenFailed: 'skip'` (`CorePolicy.errors.hasAssertionsWhenFailed`, handed in as an option, because this package reads only its own slice) drops the count errors when `hasAssertions()` was called, which is jest-circus' "only show errors from `expect.hasAssertions()` when no other failure has happened", and adds no required-assertion error; `assertions(n)` is still checked on a failed test, as Jest does. The worker registers it in `worker/runtime/runner.ts` with `coreRuntime.onAfterTryTask`, which runs in the attempt's async context after the last `afterEach` and the teardowns. **Known limits:** Vitest runs its count checks only on a body that did not fail, so for `assertions(n)` on a failed test Provino adds the count error where Vitest has none (the test fails either way; no policy key says which); core adds one error per thrown value, so the worker throws an `AggregateError` when an attempt gains several (two soft failures are one error holding two, where Vitest reports two).
- **`pollTimers`** (`createExpect({ pollTimers })`, `PollTimers`): `setTimeout`/`clearTimeout` default to the real ones found on `globalThis` when `createExpect` runs (before a file can install fake timers); the unit tests inject a manual scheduler. `advance(ms)` moves the file's fake clock: the worker supplies `clock.isInstalled() ? clock.advanceByAsync(ms) : undefined` from the current file's `FakeClock`, and the poll calls it after each wait between tries, as Vitest advances fake timers by the interval. This package imports neither `@provino/timers` nor core, which its manifest forbids.
