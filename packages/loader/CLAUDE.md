# @provino/loader

The module loader (Track 2): a two-phase module-runner engine. One `Loader` per worker; one `FileRegistry` per test file. It runs in **both** halves (manifest `runsIn: both`, U5, D74): the worker's engine, and a coordinator mode that imports a global setup module (see below). It never imports `@provino/mock`, a worker package; the worker passes the module-mock registry in. The contract (`Loader`, `FileRegistry`, `LoaderOptions`, `CreateLoader`, `ModuleMockRegistry`) lives in `@provino/types`. The spec is Track 2 R1–R2 and F3; B06's notes are in `docs/plan/bundles/B06.md`, B13c's (mocks in the loader, T2.5 + T4.8) in `docs/plan/bundles/B13c.md`.

## Two halves

- **Worker-wide: `src/internal/records.ts`.** Each user module has one `ModuleRecord` per worker:
  - transformed once: the `ModuleTransformer` (the pipeline, with the dialect's hoist policy), then `toModuleRunner` from `@provino/transform` for files with ESM syntax, or with `import()` and no other module syntax (format `unknown`, which a CommonJS `vm` script can't run). A file that calls `require` or uses `module`/`exports` is `cjs`, `import()` or not, and keeps the CommonJS wrapper;
  - its static deps resolved once; one that doesn't resolve is a `missing` target, and a user module that doesn't transform (a `.css` file) a `failed` one, each thrown only when its edge runs and decides on the real module (B13c Gap 7; so a factory for `./styles.css` never transforms it);
  - compiled once per mode, as a `vm.Script` with `filename` set to the module's id (the real path, plus any query or fragment the specifier carried, so two URLs of one file are two scripts; a `data:` module's URL) (`ModuleRecord.compiledSync`/`compiledAsync`, a `WrapperScript`). The compile listeners hear of each script once, when it is compiled. **A run of the script makes the wrapper function, and a registry of one file runs it again for every evaluation** (`compile`'s `fresh`, the registry's `#freshWrappers`): V8 keeps a function's feedback (its inline caches and the optimized code built on them) in a cell that every closure made by one enclosing function object shares, so a module evaluated in every file through one cached wrapper function (a per-file external, D127/D129/D132, or any user module under `registry`) gave every file's copy of its functions one feedback vector. Each file's new classes (new hidden classes: React, a UI library, jsdom) added maps to the same inline caches until they went megamorphic, and every file after about the 11th heavy one paid seconds of native CPU in a real React suite. A new run of the same script is a new function with feedback of its own, from the script's compiled code (no parse), as Jest's compile of each module for every test file; a registry shared across files (`none`, and the coordinator's) evaluates a module once and calls the function of the script's first run (`WrapperScript.shared`). `Script` reuse rather than `runInThisContext(source)` per evaluation: both give fresh feedback (`bench:loader megamorphic`, `local`), but a kept script does no compilation-cache lookup per evaluation and is one V8 script per record and mode, whatever the cache evicts, which V8 coverage counts by. The cost (`local`, Node 24): the run itself 0.3 to 4.5 µs; the module body then runs from cold feedback, as in Jest (evaluations 2 to 30 of a 35 KB CommonJS wrapper of 300 functions: 14.8 µs cached, 27.2 µs fresh; of 728 KB and 6,000 functions: 472 against 665 µs). V8 precise coverage sums a function's counts over the closures of its script, and block counts live on the function's shared code, so both providers read as before. The script itself comes from V8's code cache when an earlier worker left an entry for its text (`LoaderOptions.codeCache`, "V8's code cache of the wrapper scripts" below).
  - forgotten by `dropRecords(paths)` (watch mode, B23c): the next registry reads, transforms and compiles those modules again (the dropped record leaves `Records.importers` and `graphsDirty`, and the record made next marks its importers for `markAsyncGraphs`); the others stay. The orchestrator's runner calls it with `FileJob.staleModules` before a file starts.

  `linkAsync`/`linkSync` walk the static graph. A record's `lateDeps` (D38) are never linked. Externals (anything under `node_modules` that `inline` doesn't match and no transform makes a user module, plus addons and builtins) are shared by the worker: under `interopDefault: 'node'` the async path preloads them with native `import()` (Node's namespaces); under `babel` nothing is preloaded, and an edge `require`s the external when it runs, as Jest's CommonJS output does, so a mocked package never loads. An external's own imports are Node's to resolve; the worker adds one resolve hook for its lifetime, so a bare import of a subpath into a package with no `exports` map (`next/server`) resolves as `require` would (`installLegacySubpathFallback`, `src/legacy-subpath.ts`; NOTES.md → "An external's own imports"). `asyncGraph` marks top-level-await subgraphs and `lateGraph` the subgraphs that reach a module with late deps, both as one fixed point over cycles. `markAsyncGraphs` is incremental (B23e): it looks only at `Records.graphsDirty` (a record whose `resolved` gained a `user` target through `setResolved`, which every link of a dep goes through, and the importers of a module whose record was just made), as its worklist in place, and walks `Records.importers` (a reverse edge index `setResolved` keeps, only ever added to as a defence: should a `user` target be overwritten, the stale entry costs a needless look, never a missed flag) from a record that gained a flag, so a link costs the edges around what changed, not a scan of every record in the worker (that scan, after every `require` of a module evaluated per file, was the quadratic cost of a worker's first file over a UI library's graph). The flags only rise, so the result is the scan's to a fixed point; `async-graphs.test.ts` holds it to that scan on cycles, a top-level-await leaf reached through a cycle, late deps, a dropped module made again, a runtime `require` that resolves a new edge after linking, two `linkAsync` walks suspended at an `await` with a `linkSync` between them, and 40 seeded random graphs linked in random order.
- **Per file: `src/internal/registry.ts`.** A stack of instance maps; the top one is live, and `isolateModules` pushes a fresh one. Evaluation calls a wrapper made by a fresh run of the record's script (under `none`, the one the worker made) with fresh linkers, so module state and V8 feedback are per registry while compiled code is shared. The registry carries the running file's `FileContext` (`{ mocks, scope }`); under `none` the registry is shared and each file sets its own.
  - `resetModules` empties every layer in place and keeps the stack's depth, so a reset inside `isolateModules` leaves the registry (under `none`, the worker's shared one) usable.
  - `isolate`/`isolateAsync` remove the map they pushed, by identity, not whatever is on top: overlapping async isolates each drop only their own map. The loader's `FileRegistry.isolateModules` also opens the module-mock registry's overlay, which refuses nesting with the dialect's `nested-isolation` text.

**Coordinator mode (U5, `src/coordinator.ts`).** `createCoordinatorLoader(root, config, policy)` is `createProjectLoader` with the mock side taken away and one tier, `none`: `config.hoist` and `moduleScope` are cleared (no mock registry for a hoisted call to reach, no `jest` binding: a module that names `jest` sees the global of that name, which a coordinator has none), `mocksReachShared` is off (no lexer, no graph), and every file is imported at tier `none`, so a setup and its teardown share module state. `import(file)` resolves with the module's exports as an `import` sees them under `interopDefault`: for `module.exports = fn` and for a compiled `export default` alike, `default` is the function (the orchestrator also unwraps a `__esModule` default, for `node` interop). **It installs nothing process-wide**: the engine compiles with `vm` and links itself, so there is no `module.registerHooks` or `require.extensions` hook, and the coordinator's own imports resolve as before (`coordinator.test.ts` pins the extension table and counts calls to `module.registerHooks` and `module.register`, zero). A Jest transformer (`config.transform`) loads in the coordinator's process, from its own path. It reports nothing of what a module loaded (`FileRegistry.loadedModules()` is the worker's).

`FileRegistry.loadedModules()` is **per file** (the `deps` event reads it): under `registry` it is the file's own instances; under `none`, where the registry outlives the file and a module an earlier file evaluated is found, not evaluated again, `Registry.#touched` counts the modules the file asked for (the runner's own loads, the actual paths, and each new instance `#newInstance` makes; an instance found by an edge isn't added again, the walk below reaches it) and `loadedByFile()` follows their dependency edges to the loaded modules they reach (a module is loaded when some map of the stack holds it: no copy of the registry is made per file). **The edges are read, not resolved:** the walk takes the targets a record's `resolved` map already holds (every static dep as `linkDep` linked it, and any specifier a `require` resolved since), so the walk, which runs once per file over every module the file reaches, asks the resolver for nothing (`reading a file’s closure resolves nothing…` counts the resolver's calls). `userEdgesOf`, which does resolve, is the graph walk's and `#maybeInline`'s, for a module that may not be linked. A late dep (D38) is never in `resolved`; it comes through the dynamic loads below. Over-approximate for a CommonJS module (its `require` calls as the scan sees them). **A module's dynamic loads are part of its edges:** while a file is counted, `requireFrom`, `importFrom` (a runtime `import()` and the async late import) and the sync late import note, per importing module, the user module each one loaded (`Registry.#dynamicLoads`; a `require` whose target the record had already linked isn't noted, the walk follows it), so a `require(variable)` or a runtime `import()` an earlier file ran is still followed when a later file reaches that module without evaluating it again. It is kept per importer, not per evaluation: a lazy `import()` that an earlier file's code ran later (from a function it called) counts for the next file that reaches the importer too, an over-approximation like the static scan's. **Known over-approximation, not fixed:** `#touched` is one set for the shared registry, not one per file, so a load a file left in flight (an `import()` it did not await, still linking when its file ended) adds its module to whichever file is being counted when the load evaluates, the next one when it has begun. Telling the files apart would need the file in each load's async context (an `AsyncLocalStorage` entered by every entry point), and a test body's `import()` and a module's closures run outside any entry point and outlive their file under `none` (the closure a module gets at evaluation serves every later file), so it is a change to every edge, not a small one. The cost is an extra dep on the next file, never a missing one. `loader.test.ts` pins both tiers and both dynamic forms.

`src/loader.ts` holds `createLoader` and the tiers (`tierFor` is `src/tier.ts`'s). `registry` creates a new `Registry` per file; `none` reuses one per loader.

`src/project.ts` holds `createProjectLoader(root, config, policy.module)`: the worker's way in. It builds the resolver and the transform pipeline from a clone-safe `SerializedLoaderConfig` (the worker entry may not import either; `config.hoist` is the dialect's hoist policy, by value), loads the config's mappers by `ModuleRef` (so it is async), and calls `createLoader` with the runner engine and `config.moduleScope`'s names. `config.cacheDir` (set by the coordinator, absent under `--no-cache`) turns the transform cache on: the pipeline reads a file's record before any work and writes it after (T3.6, `packages/transform/CLAUDE.md`), so a hit restores `staticMocks` and `lateDeps` with the code. `config.transform` (T3.8) loads the project's Jest transformers there (`createJestHost`, by path, in the worker) and hands them to the pipeline: a file a transform matches goes through its transformer, every other file through Oxc (`transformers.test.ts`).

- **`define`:** `config.define` (the config's `define` key as plain source-text strings) goes to `createPipeline({ define })`, so it is in the transform cache's fingerprint and every file takes Oxc's transform (no in-place strip, D116). Only modules the pipeline transforms take it, never a `node_modules` file Node loads itself.
- **`tsconfig`:** `'auto'` and `false` pass through. Any other string is a file path, resolved against `root` (never the process cwd) for both the resolver and the pipeline, and it must be a file: otherwise `createProjectLoader` rejects with `LOADER_TSCONFIG_NOT_FOUND`, naming the resolved path.
- **Resolver keys (T3.3, B17c):** `config.aliases` (Jest's `moduleNameMapper`, regex sources in order) become one `createNameMapper` that runs before the loaded mapper factories; `moduleDirectories`, `modulePaths` (the retry after a miss) and `resolver` (a `ModuleRef`, loaded by the behaviour loader, a function or `{ sync }`, called with Jest's `(path, { basedir, conditions, defaultResolver, extensions, moduleDirectory, paths, rootDir })`) go to `createResolver`. A mapper rule that matches but doesn't resolve is a `not-found` result carrying `mappedBy`, `tried` and `declared` (the targets before `$n`); the loader raises the text `ModulePolicy.mapperMiss` gives (a behaviour, loaded by `createProjectLoader` into `LoaderOptions.formatMapperMiss`, handed `{ specifier, rule, declared, tried, resolver }` with `resolver` from `LoaderOptions.resolverName`; Jest's is `formatMapperMiss` in `dialect-jest/runtime`), else `module-not-found`. Recorded: `resolve/mapper-miss`. `ModuleScope.mappable` names the served modules a matching rule takes over (`mapperTakes`, checked in `resolveOrMissing` and `#served`).
- **An edge's kind (`src/internal/edge-kind.ts`):** `resolveOrMissing` resolves each edge as the kind `ModulePolicy.edgeResolveKind` gives it. `as-written` (neutral, Vitest) keeps the edge's own; `importer-format` (Jest) gives every edge of a module `require` (Jest's CJS conditions), or `import` when the module runs as an ES module: Node has `vm.SyntheticModule` (`--experimental-vm-modules`) and the file is `.mjs`, `.wasm`, a `.js` under a `"type": "module"` package, or has an extension in `LoaderOptions.esmExtensions` (Jest's `extensionsToTreatAsEsm`, through `SerializedLoaderConfig.esmExtensions`), as `jest-resolve`'s `shouldLoadAsEsm`. Answers are kept per importer for the worker, and a `package.json` is read once, and the nearest one is found once per directory (`manifestByDir`: a walk up with `statSync(…, { throwIfNoEntry: false })`, no ENOENT thrown, stopping at a `node_modules` directory as `module.findPackageJSON` does and at the first directory already known; none, or one that does not parse, is CommonJS). A mock call's specifier keeps `mockResolveKind` (`exact`), and `import.meta.resolve` its own kind. An edge the importer's kind finds no file for (a package with only an `import` entry) is `missing`, as in Jest: nothing retries it as written, so a virtual mock (`decideUnresolved`) or a mapper still answers it (`review-regressions.test.ts` in the bench, B23e review High 1), and a third-party import-only package imported from a CommonJS-run file fails with Jest's "Cannot find module" (`loader.test.ts`). `provino` itself, which a Jest-dialect test file imports, has a `default` entry beside `import` on every subpath, so a `require`-kind lookup finds the same ES module, which Node's `require(esm)` loads (`provino`'s `exports.test.ts` holds that no entry has top-level await). Not applied: the node_modules graph's edges (`buildThirdPartyGraph`, for a mock's reach), and a shared external's own imports, which Node resolves (with Node's conditions too: an external whose closure Node would resolve to another file is inlined, see "Node's other resolution"). **Limit: `provino run` with `dialect: 'jest'`.** `esmExtensions` comes only from a Jest config's `extensionsToTreatAsEsm` (`to-neutral.ts`); a `provino.config.*` project has no resolver keys and no public key for it, so under `--experimental-vm-modules` its `.mjs` and `"type": "module"` `.js` files resolve as ES modules and a `.ts` file always as CommonJS-run (shown with a dual package's `node` branch: `.mjs` takes `node-import`, `.ts` `node-require`, where Jest with `extensionsToTreatAsEsm: ['.ts']` gives both `node-import`); a DIVERGENCES candidate. Recorded: `env/conditions-import-*`; `edge-kind.test.ts`, and `loader.test.ts`'s `edgeResolveKind` cases.
- **`module-sync` (`ModulePolicy.moduleSyncCondition`, `edgeConditions` in `edge-kind.ts`):** `never` (neutral, Vitest) adds nothing; `import-and-sync-require` (Jest) adds `module-sync` to the conditions of every lookup that resolves as an import (an `import`, `import()`, `import.meta.resolve`, and every edge of an ES-module-run module under `importer-format`), and to a `require`-kind one only when Node evaluates an ES module graph synchronously (`vm.SourceTextModule.prototype.hasAsyncGraph`: 24.9 and later, under `--experimental-vm-modules`), as jest-runtime's `Resolution.ts` L35-48 gates it on `supportsSyncEvaluate`. The capabilities are probed once per loader, on the first lookup that needs them (`RuntimeCapabilities`, the seam the tests pass), so a policy of `as-written` with `never` (the neutral one) never reads them. The module-mock registry's conditions (`ModuleMocksContext.conditions`) are the lookups of `mockResolveKind`, so a registration's id is the edge's (`review-regressions.test.ts`, B23e review Medium 2), and a name-mapper check uses the same. Recorded: `env/conditions-import-module-sync` (the `import` half); the `require` half differs by Node version, so `edge-kind.test.ts` holds it on the seam, and `loader.test.ts`'s `moduleSyncCondition` case the wiring in this process (no flag: a `require` adds nothing).
- **Mappers:** each factory's result must be an object with a string `id` and a `map` function. A factory that throws (the error is the `cause`) or returns anything else rejects with `LOADER_INVALID_MAPPER`, naming `loader.mappers[<i>]`. Factories are called synchronously, as `ModuleMapperFactory` says.

`FileRegistry.invalidate(specifier, parent?)` drops the live instance of the user module the specifier resolves to, in the top map of an `isolateModules` stack. It resolves the specifier as an `import` and as a `require` and drops both ids, since a package's `exports` can map the two to different files and either may be the loaded one (a kind that doesn't resolve is skipped). Under `none` the registry is shared, so it reaches every file of the worker.

## Mocks (T2.5 + T4.8, B13c)

- **The worker builds the module-mock registry, not the loader** (Gap 1): it also needs the mock slice and the file's mock registry, which the loader never reads (non-negotiable 3). `FileRegistryOptions.moduleMocks` is a factory the loader calls once, with `{ loadActual, resolver, conditions }`. Without one, nothing is mocked and `registerMock`/`unregisterMock` throw `LOADER_NO_MODULE_MOCKS`. `FileRegistry.dispose` disposes it too.
- **Every edge decides.** A static import (`#importEdge`), a `require` (`requireFrom`, with the record's linked targets), an `import()` (`importFrom`) and a late import resolve, then ask `decide(id, importer, 'esm' | 'cjs' | 'builtin', specifier)`; a `missing` target asks `decideUnresolved` and throws its `ModuleNotFoundError` only if nothing stands in. A mocked edge gets `materialize`'s value: under `factoryShape: 'module-value'` an `import` sees it through the CommonJS interop; under `awaitFactory` a Promise is a result to wait for (`Pending`), which a sync edge refuses with `ERR_REQUIRE_ASYNC_MODULE`. Each wrapper passes its mode to its edges, so a plain wrapper never binds a Promise; an ES module loaded by `import` takes the async wrapper when its graph awaits (`asyncGraph`), reaches late deps (`lateGraph`), or may meet a pending mock (`awaitFactory` with mocks in play). The runner's own loads (`import`/`require` with no `parent`: setup files and the test file) never ask about the module itself.
- **The actual paths** (`requireActual`, `importActual`, and the registry's `loadActual`, which follows `ModulePolicy.actual`) bypass the mock of the module they name only; its own imports still decide. An ES module comes as its exports' view. `loadActual(id, importer, { scratch: true })` (automock) evaluates in a scratch instance map dropped afterwards, as Jest's `_generateMock` does; the registry swaps its mock values for the synchronous part. The scratch map is carried in an `AsyncLocalStorage` (`#inScratch`), so a load running beside an async scratch load (`Promise.all`) never lands in it, and `#actualAsync` keeps the instance it evaluated rather than looking it up after an `await`. Two automocked modules that import each other end: the module-mock registry serves an empty automock on re-entry, as Jest does.
- **A CommonJS module whose evaluation threw is forgotten,** as in Node and Jest, so the next `require` (after a `doMock`, say) runs it again. An ES module keeps its error.
- **Late imports (D38).** The hoister writes `await __provino_import__('./a')`; the wrapper passes `__provino_import__`. A record with late deps compiles in both modes as needed: an `import` that reaches it, directly or through static imports (`lateGraph`), evaluates async (the `await` stays, so a late dependency with top-level await works); `require` of it evaluates sync with the `await` stripped, so `require()` of an ESM helper that hoists works as in Jest, and a late dependency with top-level await then throws `ERR_REQUIRE_ASYNC_MODULE` ("… can't be loaded synchronously").

## Tier selection (`src/tier.ts`, T2.11)

`tierFor(testFile, { configured, docblock?, learned? })` -> `{ tier, source, warnings }`, also `Loader.tierFor`. The project's tier is the floor; the file's `@provino-isolate <none|registry|realm|process>` pragma and a tier an earlier run learned (the results cache's `FileHistory.tier`) can only raise it. A request below the floor changes nothing and says nothing; a value that is no tier (`''`, `Registry`, `jail`) is a warning and the file keeps what the other sources gave; a repeated pragma counts each value; `source` is `config`, `docblock` or `learned` (the first of them that names the chosen tier). `process` is the coordinator's: the orchestrator turns it into a worker of its own through `WorkerKey.isolation` (`packages/orchestrator/CLAUDE.md`). The loader's own `createFileRegistry` still never sees `process`. `isolatePragmaOf(source)` and `readIsolatePragma(path)` are the coordinator's narrow docblock reader (jest-docblock's grammar for one pragma: the first comment only, `*` prefixes, `//` dropped from the value; the first 4 KiB, all of the file only when the comment is open there); the worker reads the full docblock for the environment (`@jest-environment`), and no `@jest-environment` value maps to a tier. `tier.test.ts` holds the raise, refuse-to-lower and unknown-value cases.

## The graph (`@provino/loader/graph`, D52)

`src/graph/`: its own subpath entry and manifest node (layer 2, `runsIn: both`; it may import `@provino/types` and `es-module-lexer`, never the loader's root), so Track 9's affected-test selection can use it in the coordinator. `scanSource` (`scan.ts`: `es-module-lexer` for ES syntax, one pass over `require`/`module.require` for CommonJS, over-approximate; a computed or aliased `require`, `createRequire` and a file the lexer rejects are `dynamic`), `buildThirdPartyGraph` (`build.ts`: lazy, entries added with `add`, edges resolved with the worker's resolver, `visitNode(path)` one file's edges as a walk that may stop early sees them (added and stamped on first visit, without building a closure: the loader's reach walks and `indexClosure` use it), `reachable(path)` the closure, `edgesOf(path)` its deduplicated edges (the loader no longer reads them), `save()`; memoised closures are dropped only when a file's node is replaced; a file that couldn't be read or an edge the resolver threw on is `dynamic` and never saved), `importersOf` (`query.ts`), `packageDirOf` (`package-dir.ts`: the package directory of a node_modules file, `null` outside one; the loader's `packageClosure` and the orchestrator's learned-externals versions both use it), `cache.ts` (`<cacheDir>/graph/<key>.json`; the key hashes the lockfile's hash, which the loader takes from `@provino/transform`'s `lockfileHash` and passes as `GraphOptions.lockfileHash`, the install marker's size and mtime, the format, the lexer's version and the resolver's fingerprint and conditions; no lockfile hash means memory only; each node carries its file's mtime and size, checked with one `stat` the first time a walk visits it in a worker, and rescanned on a mismatch; a node is built from its stored form on that first visit; read once, written once per worker, from the loader's `dispose`, with a nonce-named temp file and a rename, merged with the copy on disk in stored form; a corrupt file is rebuilt). `conditions.ts` holds the one `conditionsOf` default. `pnpm bench:loader graph` holds it to 300 ms cold and 20 ms warm over a 1,246-file corpus (`local`).

## Source-mapped stacks (`src/stacks.ts`)

`installSourceMappedStacks(loader)` (the worker's runner calls it once, after `createProjectLoader`, and its `stop` calls the uninstall it returns) sets an `Error.prepareStackTrace` that maps each frame in a module the loader compiled through `getSourceMap(path)` (the record's map composed back to the source: a Jest transformer's or Oxc's, then the hoister's, then the module-runner edits), then hands the frames to the formatter it found (Node's own, so a coded Node error keeps its `[CODE]` header). The loader's own step keeps a frame's file and V8's function name (the own-map step below can move it to another file); its line and column move only when the map has a segment on the frame's own line at or before its column (`findEntry` of `node:module`'s `SourceMap`, held to the same line as `source-map-support` and trace-mapping do: no new dependency). Any other frame, and any failure while mapping, stays as V8 gave it. Maps are decoded once each, on the first frame that needs one, so a run pays only for the files whose stacks are read (core reads each test's location at registration, which includes the test file). The formatter also carries its mapper under the registered symbol `provino.mapCallSites` (`MAP_CALL_SITES`), which the coordinator's `--detectOpenHandles` uses on the structured call sites it captures (it swaps the formatter out to get them, in the process an inline worker runs in). **Node's source maps (B27h2):** while `process.sourceMapsEnabled` is on, a frame in a file the loader compiled goes on through the map the file names itself (its last `sourceMappingURL` comment, a `data:` URL or a file; read once per record, sources resolved against the map's URL, the file printed as a path), so a built `.mjs` with a map reads as its `.ts`, as Node maps a file it loaded (Node's `module.findSourceMap` never has the loader's `vm` scripts). A file Node loaded is left to Node's own formatter, which the frames are handed to and which maps it. Off, it costs one flag read per stack (`speed`). The name stays V8's (Node's takes the map's name at the caller's position: not reproduced). `stacks.test.ts` holds both. Not mapped: `eval` frames. **Function names (DV88):** under `StackOptions.frameNames: 'mapped-name'` (`ModulePolicy.stackFrameNames`: Jest's value; the worker's runner passes the policy's) a frame is named as Jest's source-map support names it (jest-source-map `SourceMapSupport.ts`, `wrapCallSite`: the name at the frame's *own* mapped position, not the caller's), so a failed matcher reads `at Object.toBe (x.test.ts:6:15)`, and is laid out as `callSiteToString` lays it out. The name is the map's `names` entry when it has one (Babel's, a Jest transformer's), else the identifier the original source holds at the mapped position (`sourcesContent`; Oxc's maps carry no names), a reserved word (`new`, `throw`) naming nothing; `engine` (the default; neutral and Vitest) keeps V8's name. A table row of `test.each` is called with no `this` (core's executor), so its frame has no type name, as Jest's. `stacks-names.test.ts` pins both values; `provino`'s `failure-frames.test.ts` holds `provino jest` to `cli/failure-frames`. `stacks.test.ts` holds a frame below a multi-line import and one on line 1 to the file's positions; `provino`'s `stack-frames.test.ts` holds `provino jest` to Jest 30.5.2's (`cli/stack-frames-after-imports`) under Oxc, `@swc/jest` and babel-jest.

## Interop (`src/internal/interop.ts`, Gap 3)

Pure functions, by `ModulePolicy.interopDefault`, held to B13b's fake loader's rules by `interop.test.ts` (the mod corpus ran against them before the fake went):

- `esmExports`: an ES module's exports object. `babel`: a plain object with a hidden `__esModule`; `node`: a null-prototype `Module` namespace.
- `cjsNamespace(value, interop, cache)`: a CommonJS value (or a module-value mock) seen through `import`. `babel`: Babel's wildcard (a value with `__esModule` is its own namespace; otherwise `default` first, then the own enumerable keys, copied as they stand); `node`: every key sorted with `default` among them, `Module` tag. A `Module` namespace stays as it is. Built once per value (the registry's cache), except from a CommonJS module still evaluating.
- `actualView`: getters over the live exports; `babel` hides `__esModule` and sorts the names, `node` is a `Module` view in source order.

## Scope bindings (Gaps 2 and 5)

`LoaderOptions.moduleScope.names` (the dialect's, through `config`: Jest's `jest`) and, for ES modules under `injectCjsGlobals`, `require`, `module`, `__filename` and `__dirname`. `module` is a fresh object per evaluation (the CommonJS wrapper's `newModuleObject`: `id`, `filename`, `exports: {}`, `loaded: false`; the names come from the wrapper's parameters, `CJS_WRAPPER` minus `exports`). It is detached: a write to `module.exports` in an ES module exports nothing, and a `typeof module` feature check takes the CommonJS branch, as `typeof require` already did (Jest's CommonJS output sees a real module there). `require.main` is `undefined`, so `require.main === module` is false for an imported file, as under Jest. A word scan at the first compile (`scopeOf`) keeps the names the source uses; a module that names none gets no outer function and pays nothing. The scan matches the word anywhere (strings, `.module`), so such a module pays the wrapper and one small object per evaluation (measured about 2 ms more scan over 6.5 MB of source, `local`; correctness unaffected). A module that names one is compiled as `(function (jest, …) { return function (<wrapper params>) { … } })`, so its own `const require = …` shadows the binding instead of clashing with a parameter. The values come from `FileRegistryOptions.moduleScope(from)`, once per module evaluation; a name with no value falls back to the global of that name.

## Message codes (`src/internal/messages.ts`, Gap 4)

Read from `ModulePolicy.messages`, like the module-mock registry's. `require-esm` (`{path}`; no neutral text; see "`node_modules` files a transform takes"), `transform-failed` (`{file}`, `{where}`, `{message}`; a code frame follows after a blank line; neutral `{file}{where}: {message}`, Jest `{file}: {message}`), `transformer-failed` (a diagnostic with `thrown`, i.e. a hosted transformer threw: `{message}` as thrown, no path added, neutral `{message}`; the `LoaderError` keeps its code `LOADER_TRANSFORM_FAILED` and takes the thrown class as `name`, `Error` for a thrown string, so the file fails with Jest's text), `module-not-found` (`{specifier}`, `{from}` relative to the root, `{importer}`; Jest's is jest-resolve's), `unresolved-mock-import` (no neutral text; Vitest's profile appends ` imported from {importer}` when the test file's load fails on `unresolved-relative-mock`; an import from inside a test isn't wrapped). **A parse error** (a module the loader parses itself: a plain-JavaScript ES module, or a CommonJS file that calls `import()`, since the pipeline reads neither) is a `SyntaxError` of the worker's own realm, as Node's and V8's are, not a `TransformError`: the parser's message and ` (file:line:column)` (a `data:` module names its own URL, not the transform's stand-in path), with the `TransformError` as `cause` (`runnerFormOf` in `records.ts`, which tells it by `TransformError.parse`); it has no policy message, so every dialect gets the same text, and any other transform failure keeps its class. A not-found error is a `ModuleNotFoundError`, whose `name` stays `Error` (Node's and jest-resolve's are), code `MODULE_NOT_FOUND` for a `require` and `ERR_MODULE_NOT_FOUND` for an `import`.

## The wrapper shape (the module-runner transform's output: oxc's shape, our own transform)

- **Imports** become `const __vite_ssr_import_N__ = await __vite_ssr_import__('./x', { importedNames })`. Uses become `__vite_ssr_import_N__.x`, which stays live.
- **Exports** become getters on `__vite_ssr_exports__`, hoisted above the imports, so cycles see live bindings.
- **`export *`** becomes `__vite_ssr_exportAll__(ns)`: one argument, bound to the module's own exports.
- **Other rewrites:** `import()` becomes `__vite_ssr_dynamic_import__`, and `import.meta` becomes `__vite_ssr_import_meta__`. The hoister's rewritten imports are `__provino_import__` calls.
- **Positions:** the wrapper opens on the body's first line, so `compile()` passes `columnOffset: -prefix.length` and every frame, line 1 included, is a position in the body: the code the record's map starts from.
- **Sync evaluation:** the plain `function` wrapper, with `await __vite_ssr_import__(` and `await __provino_import__(` stripped. Only `asyncGraph` modules, and an `import` of a module with late deps, use the `async function` wrapper. The compile listener fires once per wrapper script compiled, never per run.
- **CJS** user files use Node's `(exports, require, module, __filename, __dirname)` wrapper. `require()` of an `asyncGraph` ESM module throws `ERR_REQUIRE_ASYNC_MODULE`. A CJS file that calls `import()` takes the module-runner form (for CommonJS that is the source with `import()` rewritten to `__vite_ssr_dynamic_import__`) and its wrapper a sixth parameter of that name, bound by the registry that evaluates it (`ModuleRecord.dynamicImport`): a `vm` script has no import callback, and one script serves every registry in the worker, so a bare `import()` would fail with `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` (T2.3 found it). A CJS module with no `import()` keeps the five-parameter wrapper.
- **`require.cache` is Node's own cache** (`native.cache`), which the registry never reads or writes: a module the registry loaded is not an entry, and `delete require.cache[id]` does not make the next `require` evaluate it again (DV79, pinned by `require-cache-user-module`). Node's is a live view of what `require` loaded, and Jest's is a read-only Proxy over its registry where delete and assign do nothing; which one a dialect gets is a `ModulePolicy` key (D7), proposed as a decision, not built here. The `module` object a CJS wrapper gets is the same small object an ES module's scope binding is (`id`, `filename`, `exports`, `loaded`; `newModuleObject` in `registry.ts`), with `loaded` never set true.
- **A query or fragment** (`import('./x.ts?v')`, `?provino-load=<id>` from `@provino/config`) stays on the id the resolver gives, so each URL is its own record and instance, evaluated once; `ModuleRecord.path` is the file it reads (`fileOf`), and the scripts are named by the id. `import.meta.url` keeps the query, `filename` and `dirname` don't (`dynamic-import-query-and-fragment`). **A `data:` URL is a user module** whose source is the URL (`text/javascript` or `application/json`, base64 or percent-encoded, as Node decodes it; the transforms see it as `<root>/[data].mjs`; `decodeDataUrl` in `internal/source.ts`), so it is evaluated per registry, as jest-runtime does per test file (`dynamic-import-data-url`, `loader.test.ts`). Its imports resolve from `<root>`, so a relative one works, where Node lets a `data:` module import only builtins and absolute URLs (a DIVERGENCES candidate). `internal/module-id.ts` holds `fileOf`, `urlOf` and the schemes; `importServedByHooks` (`records.ts`) the native fallback. **An `import()` of a URL the resolver misses** (any other scheme but `file:` and `node:`) that no mock answers is a native `import()`, for a scheme a `module.registerHooks` hook serves; when Node refuses the scheme or finds nothing, the loader's own not-found error is thrown. **Limit:** a static import, or a bare specifier, in code the loader runs never meets those hooks (`@provino/dialect-vitest`'s `vitest/config` stand-in).
- **`import.meta`** has no prototype, as Node's; `import.meta.resolve` answers a relative, absolute or `file:` specifier the resolver does not find with the URL it names (Node never looks), and throws only for a package or builtin that is not found.
- **A hashbang** is legal only at the start of a script or module, and the wrapper puts the body inside a function, so `compile()` writes `//` over a body's leading `#!`, for both formats, before wrapping. The length is the same, so `wrapperColumnOffset` and the maps hold; the transform keeps the `#!` and puts its generated block after it.
