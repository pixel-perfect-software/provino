# @provino/loader reference notes

Reference sections moved verbatim out of `CLAUDE.md` to keep it short. Open only the section a task names.

## Node's loader as found (`module.nativeLoadPatches`, B23e; `src/internal/node-loader.ts`)

A shared external loads natively, so its own `require`s go through `Module.prototype.require`, `Module._load` and `Module._resolveFilename`, which code the process loads outside the test files may have replaced: Next.js's require hook, installed by next/jest's config and transformer, rewrites a `.shared-runtime` request to its server runtime (which reads `Request` as it loads, absent in a jsdom file since #113) and aliases `styled-jsx`. jest-runtime loads a test's modules itself, so under Jest none of that reaches them. Under `skip` (Jest) `#requireExternal`'s native load runs inside `withNodeLoader`, with the three as first seen in the process (the record `provino`'s bin writes under the registered symbol `provino.nodeLoader` before it reads a config, else this module's own capture when it loads, which in a worker precedes every transformer), and the process's are put back after it (a function the load itself replaced stays). Nothing is swapped when the loader is as found; `apply` (neutral, Vitest pending T11.16) never swaps. **Limit:** a `require` a native module makes later, outside its load (inside a function a test calls), meets the process's patches. Recorded: `cli/module-patch-outer-realm` (a `globalSetup` patches all three, in band; `provino`'s `jest-module-patch.test.ts`); `node-loader.test.ts` holds the swap, its control, a load's own patch and the bin's record.


## An external's own imports (`src/legacy-subpath.ts`; P51, DV221)

The full explanation is the header of `src/legacy-subpath.ts`. The worker's runner installs `installLegacySubpathFallback()` after `installSourceMappedStacks` and removes it in `stop` (in a thread, for that thread; an inline worker's is removed when its run stops); the coordinator's loader installs nothing (`coordinator.test.ts`). **The cost (`speed`):** every resolution Node makes in the thread goes through the hook, about 3 µs more per native `require` and nothing measurable per `import` (3,000 modules, about 9,000 resolutions: CommonJS 204 against 232 ms, ES modules 428 against 425, median of 9 interleaved, `local`, Node 24). Installing it lazily, on a native load's first such failure, costs nothing until then (Node 24 resolves a failed import again), but misses an `import()` a package makes later, from a function a test calls; not done (proposed to Tyler). **Not covered:** an extensionless relative import inside an ES module package (`import './x'`), which plain Node fails too; D130 makes such a package a user module when a transform claims it. Tests: `src/legacy-subpath.test.ts` (the target over temp trees; install and removal in a child process), `provino`'s `test/native-esm-dependency.test.ts` (a native run on every pool).

## Mock-aware auto-inlining (T2.6, B13d)

A shared external (a node_modules file) loads natively, so its own `require`s never meet the mock registry. When `ModulePolicy.mocksReachShared` is set (Jest and neutral `true`, Vitest `false`; recorded by `mod-shared-dep` and `mod-shared-dep-root`), an edge that reaches an external asks `Registry.#maybeInline` whether the external's graph closure holds an edge the file's mocks take. If so the external is a user module for that file (a `user` target, a record with role `dependency`, so no hoisting, and `CompiledModuleEvent.thirdParty`), and its own edges decide in turn.

- **`decide()` is the authority** (`src/internal/inline.ts`, `mockedReach`): each distinct edge of the closure (its specifier as written, its resolved id, `esm`/`cjs`/`builtin`) is put to `decide`; an edge that didn't resolve to `decideUnresolved` (a virtual mock). `decide` has no side effect that matters here (it remembers a specifier for an id, and under automock-all adds a deep unmock's imports, each of which the real edge does a moment later).
- **The walk goes through user modules.** A closure edge that leaves `node_modules` (a workspace package linked into it resolves to its real path) is followed through the loader's own record of that module (`userEdgesOf` in `records.ts`: its deps resolved as an edge would), and back into any `node_modules` file those reach, so a package that requires a workspace package that requires a mocked module is inlined, as under Jest (`a package reaches a mock through a workspace package…` pins it, on a pnpm-style tree). The graph itself stays types-and-resolver only.
- **A verdict is kept** per mock registry until its `generation()` changes (a registration, an unmock, `setAutomock`, a `resetModules` that clears them): `resetModules` and `isolateModules` don't decide again. A negative verdict holds for every node_modules file the walk covered. The walk (`walkClosure`, shared with `cachedReach`) goes node by node through `ThirdPartyGraph.visitNode` and ends at the first mocked edge, in the order a walk over the whole closure's edges meets them (the node_modules files depth first as `reachable` lists them, then the user modules an edge leads out to), so the id it reports, the budget's key, is that walk's first.
- **No mock, no scan.** The gate is `ModuleMockRegistry.active()` (a registration, automock-all, or root mocks to apply: `decide`'s fast path, inverted). With it `false` the graph isn't even built. `with no mock, nothing is scanned or cached` pins it.
- **A served module keeps its instance** (Gap 3): `Registry.#memory` holds, per instance map, how each external was served: shared (`false`), inlined for the file's mocks (`'mocks'`) or inlined for another reason (`'kept'`: a served module, or evaluated per file); a `doMock` after the first load changes nothing, `resetModules` clears every layer's memory, `isolateModules` decides afresh in its own layer. Under `none` the shared registry outlives the file, so `FileRegistry.dispose` calls `dropInlined()`: the instances inlined for the file's mocks (the `'mocks'` entries) and every verdict but a `'kept'` one go, and the next file sees the shared module. An external inlined for a served module keeps its instance, as no module is evaluated again under `none`.
- **What it covers:** every edge kind (static import, `require`, `import()`, late import) and the actual paths (`requireActual`'s real module is inlined too, so its own imports stay mocked). An inlined module not linked ahead is linked on the spot (`#linkNow`). Addons never inline. A node_modules path matching `LoaderOptions.inline` is an ordinary user module (role `source`), as before.
- **Warnings** (`LoaderOptions.onWarning`, default `process.emitWarning` with the code, debug level dropped): `PROVINO_INLINE_BUDGET` once per mocked id per worker when more than `inlineBudget` (400) modules inline for it in a file (it still inlines); `PROVINO_INLINE_DYNAMIC` (debug) when a shared closure holds a computed `require` while mocks are active, an edge the graph can't see. Inside an inlined module every `require` is an edge we see, so dynamic ones are checked at run time. The worker doesn't route either to reporters yet (Track 9).
- **`LeakReport.inlinedForMocks`** is what the file inlined (`FileRegistry.dispose()`'s report).
- **The lexer:** `createProjectLoader` awaits `initLexer()` (`init()` of es-module-lexer's wasm build) once per worker when the policy asks for inlining; a loader made directly (tests) compiles it on the first scan. `RegisterMockOptions.hoisted` is not read: the lexer is ready before a file loads, so there is no warm-up to do (B13d Gap 4 allowed this).
- **Not covered:** Jest's transitive node_modules rule under automock-all (`applyTransitive`, not built in `@provino/mock`).

## Externals evaluated per file (D127, D129, D132; `src/internal/reevaluate.ts`)

Jest evaluates node_modules again in every file's registry; here a shared external loads natively once per worker. Under `ModulePolicy.reevaluateHookingExternals` (Jest and Vitest `true`, a native project `true` (D221, #233: `@testing-library/dom` builds `screen` over `document.body` as it loads, so a shared copy searched the first file's body), neutral `false` for speed; Vitest's recorded by `module/vitest-externals-two-files`) an external whose first load read a per-file global is inlined from then on (the per-file set, the first of `#maybeInline`'s reasons).

- **Writes too (B23f, D149 as amended; `ModulePolicy.reevaluatePatchingExternals`, Jest, Vitest and a native project `true`, neutral `false` for speed).** An external whose first load adds a key to the global or replaces one is learned the same way: same window, same learning, same results-cache entry. The environment's restore takes such a key away after the file, and the shared copy never writes it again, where Jest's evaluation on each file's fresh global writes it every time. msw 3 is the case: `@mswjs/interceptors` 0.45 adds `globalThis.__MSW_INTERNAL_CONNECTION_CONTEXT` (`??=`, as its `net` chunk loads) and `__MSW_INTERCEPTORS_REGISTRY`, and marks msw's own passthrough sockets with the first; without it in the second file a passthrough socket was caught as a new request, passed through again, and an unhandled `fetch` looped for good. msw is ESM-only and loads through `require(esm)`, which is synchronous, so the writes land inside the window of `msw`'s and `msw/node`'s first loads; the learned files are msw's own (`packageClosure`: a `require(esm)` puts no ES module in Node's cache), and `@mswjs/interceptors` and the packages only msw imports join through D132. The loader only opens the window (`reevaluatesExternals`, `src/reevaluation.ts`: any key `ReevaluateKey` names, every `ModulePolicy` key spelled `reevaluate…`; `NO_REEVALUATION` sets each to `false`, and a new key fails to compile there until it is listed: the coordinator's loader spreads it, `coordinatorModulePolicy`, and `coordinator.test.ts` checks every such key of the neutral policy comes out `false`; the orchestrator's run and worker ask the same predicate); what counts is the worker's watcher (`external-probe.ts` in the orchestrator): exactly the keys the environment's restore takes back. **Limits:** a key the load deleted is not a write, nor an accessor that settled into Node's own value (a lazy global's first read); an assignment through a closure-backed accessor (`process`, `performance`), a write made after the load (from a function a test calls), and a replaced builtin export (`http.request`: no builtin is compared) go unseen. msw's patches of `fetch`, `http` and the rest are made by `listen()`, not at load, and its `close()` restores them, so they need nothing. Recorded: `ecosystem/load-time-global`, `ecosystem/msw-setup-file`, `ecosystem/msw-node`; `loader.test.ts` holds an ESM-only package that adds a global as it loads (learned once, evaluated per file from the next file, its own dependency joining, a dependency a shared package imports staying shared) and nothing watched with both keys off.

- **The window.** `#requireExternal`'s first native load of an external (from a user module, an inlined one, or the runner's own `load`/`loadSync`, which now go through `#maybeInline` with the mock check off) is `watchedLoad`: each `Loader.watchExternalLoads` watcher is told the path and returns the call that ends the window and says whether a per-file global was read. A load inside an open window is part of it, so a read in RTL's `@testing-library/dom` counts for RTL. With the policy off, `watchExternalLoads` registers nothing and no window opens. The async preload (`interopDefault: 'node'`, which a native project uses, #233) is the first native load too, and is watched the same way (`watchedLoadAsync`): one window is open at a time, so a preload that starts while another's window is open waits for it, and code that runs during the `await` counts for the window (an over-approximation: it can only learn a package that did not need it).
- **What is learned:** the external, the files of its own package its static closure reaches (`packageClosure`: a `require(esm)` puts no entry in Node's cache for the ES modules it evaluates, and a package split between a per-file entry and shared internals is two half copies), and every node_modules file the load added to Node's cache (`isEvaluableExternal`: no addon, no `.wasm`). It goes to `pending`, made `active` when the next file's registry is created (`promoteLearned`), so the file that learned it keeps the shared instance throughout. A load that threw after such a read is learned too: the next file evaluates it (and meets its error) through its registry, as Jest's would, instead of watching it again.
- **Exception safety.** Every watcher is asked inside the `try`, so one that throws as it opens (the load is then not run, and its error is thrown) still has the windows opened before it closed; every end is called whatever another end threw (the first end's error is thrown after the load, unless the load threw). A watcher returns `null` when it does not watch a load (no file is running), and Node's cache is read only once some window is open.
- **Carried between runs:** `takeLearnedExternals()` (what a watched load learned since the last call, each file once: never a seeded one, and no allocation when nothing was learned) and `reevaluateExternals(paths)` (seeds `active`, skipping a path that is not an evaluable node_modules file or no longer exists); `createProjectLoader` seeds from `SerializedLoaderConfig.reevaluate`. The orchestrator keeps the set in the results cache.
- **The per-file set: the rule (D127, D129, D130, D132; `evaluatedPerFile` in `inline.ts`, `settlePerFile` in `reevaluate.ts`).** An external is evaluated per file when it is a **seed** (`active`, or, under the same key, a `node_modules` file the claims made a user module: `ClaimsState.users`, D130), when it **reaches** a member through any chain of known edges (a component library that requires a learned `react` would otherwise `require` Node's cached file-1 copy while the file's own code gets its own, an "Invalid hook call"; and in a run seeded from the cache the learned file would be evaluated twice in file 1), or when it is a **dependency that joins**: the greatest set of files below the members (the **region**) whose every importer is a member or in that set, so a cycle (`reg/index` and `reg/a` requiring each other) or a barrel the registry imports back joins whole, which no least fixed point admits. A region file with an importer outside both is dropped, with what reaches the set only through it, and the rest joins, followed by the reach rule. So a registry a per-file package writes into as it loads is the file's own, and a dependency the shared part of the graph imports too (`react` under a component library) stays shared: the set never cascades upward. An importer inlined in every file for a served module (`servedReach`) or for Node's other resolution (`conditionalReach`, below) counts with the set and never keeps a dependency shared. A user module a closure goes through (a workspace package linked into `node_modules`) is an ordinary region file, so it is shared exactly when a shared package loads it (then it is Node's copy, and so is what it loads). A file that scans as dynamic (a computed `require(name)`, `createRequire`, a file that could not be read) and is outside the set blocks every region file of its own package or of a package its `package.json` declares (`dependencies`, `optionalDependencies`, `peerDependencies`): under a strict layout a computed `require` finds only those, while the packages its static closure reaches would be no bound at all. Such a refused join is reported once as `PROVINO_INLINE_DYNAMIC` (debug). Addons, `.wasm` and builtins are never members.
- **The per-file set: the known graph, and the order.** `ReevaluateState.perFile` holds the edges, both ways, of the static closure of every external the worker loaded natively from a file (`Records.required`, indexed whenever the seeds grow, so a shared importer an earlier file loaded counts) and of every external an edge asked about since, read from each file's graph node (`graph.reachable`; the closure's deduplicated edge list names only a request's first importer), through user modules as the other walks go. **No region join is decided during a worker's first file (D132 as amended 2026-11-19, speed; `PerFileGraph.file`).** A worker seeded from the results cache has its seeds from its first question, before any file has loaded a shared importer of their dependencies, so a join decided then would see no importer and take each seed's whole closure; a cold worker learns the same seeds in its first file and joins them at its second, knowing what that file loaded. So in the first file the seeds are members (and what reaches them, by the reach rule) and their dependencies stay shared, as everything is in a cold worker's first file; the probes wait, and the second file's first settle decides them knowing every external the first file asked about, with its closure: what a cold worker knows when its seeds join. A dependency no shared importer the worker has seen imports then joins from the second file, so a per-file plugin writes into the shared registry once, in the first file, and into its own from then on. A cold worker is unchanged (its seeds join at its second file), and a worker that runs one file decides nothing. **The set only grows, and a file sees it as it stood when the file's registry was created**, plus what reaches a member since (`members`): a join, or a seed found, once the running file has asked about an external waits in `pending` and becomes a member when the next file's registry is created (`promoteLearned`, as for `active`). So a file that already holds Node's copy of a package never gets a second one when the worker learns more of the graph halfway through it, and a package is not per file in one file and shared in the next. **Limits:** a shared importer the worker has not yet loaded or asked about when a dependency joins does not keep it shared; once it is seen, it reaches a member and is inlined instead. The same holds for a dynamic file seen after the join. A module an environment loads with its own `require` (outside the loader, never in `Records.required`) is no importer the graph can see. Mocks apply to one file only, so an importer inlined for the file's mocks (`mockedReach`) counts as shared.
- **The per-file set: the cost.** Each file of the graph keeps its importers with a count of those in the set and in the region; an indexed edge updates the counts and probes only a region file whose importers changed, and an edge between two files outside both probes nothing, so settling is linear in the edges the worker indexes, plus a probe's walk over the region files below it with no shared importer. Each external's closure is indexed once per worker, node by node through `visitNode`, and the walk does not descend into a file already indexed (each walk indexes a whole closure, so that file's is indexed too; B23e: 96 ms against 101 on `bench:loader per-file`, `local`); a question about an indexed external is a `Set` lookup. `pnpm bench:loader per-file` (no bar, `local`): a file that requires 20 unseen packages while a hub has 3,000 per-file importers and one shared one, 3828 ms with the set rebuilt from its seeds per indexed external, 107 ms now, most of it the one-time indexing of the 3,001 externals the first file loaded. The cost on real packages (react-dom, jsdom) is unmeasured since the walk became an index; the reach walk it replaced was about 0.1 ms for `react-dom` and 0.5 ms for jsdom's 1,107 files, once per worker per external, `local`.
- **Steady state:** an edge to an external pays a `Set` lookup and the per-map memory; a native load after the first pays nothing.
- **A no-op under isolation `none`.** The shared registry outlives its files and keeps every module it evaluated, so no file is evaluated again under `none` by design; the registry's `sharedAcrossFiles` flag (set only for the shared one) turns both halves off for it (no window, no inlining). `loader.test.ts` pins it.
- **Limit: ES modules.** An ESM-only external that loads through native `import()` (the `interopDefault: 'node'` preload, or a `require(esm)` Node evaluates asynchronously) opens no window: an async evaluation would interleave with other loads, so its reads can't be told apart. Such a package stays shared (a DIVERGENCES candidate). No dialect with the key on preloads today.
- **Node's other resolution (`conditionalReach` in `inline.ts`; under `reevaluatesExternals`, so Jest's value).** The loader and the graph resolve with the environment's conditions (`LoaderOptions.conditions`: `['browser']` under jsdom, from `customExportConditions`), as jest-resolve does for every module; a native load's own requests go through Node's resolution, with Node's conditions. A package whose `exports` maps a build per condition gives a native `require` its other build. Emotion's `@emotion/react`, `styled`, `cache`, `utils` and `use-insertion-effect-with-fallbacks` map `browser` to a `.browser.cjs.js` build, so in a worker's first file, before anything was learned, MUI's native `@mui/styled-engine` got Emotion's Node builds while the file's own imports got the browser builds (two Emotions, each with its own contexts and cache); from the next file on, with the stack learned and inlined, every copy was the browser build, as under Jest. So an external whose closure has an edge Node would resolve to another file (or to none) is inlined from its first load (`'kept'`, a `cachedReach` walk like `servedReach`'s, verdicts in `InlineState.conditional`), and counts with the set (`elsewhere`). The test stays cheap: `divergingConditions` is the symmetric difference of the loader's conditions and Node's (`browser` and `node` under jsdom; none under the node environment, where nothing is asked and nothing changes); only a specifier a manifest maps (a package, a `#` import) can differ, only through a package whose `exports` or `imports` names one of those conditions (each manifest read once per worker, `InlineState.conditioned`), and only such an edge is resolved again, with Node's conditions. `loader.test.ts` holds a package over a `browser`/`default` split: the environment's build in the first file, one copy, per file after; shared and Node's build under `['node']`. **Limits:** Node's conditions are taken as the loader's default, `['node']`, so `module-sync`, `node-addons` and a `--conditions` flag are not compared (a package that maps `module-sync` differs between a native `require` and the registry's, as it did before). A target outside `node_modules` (a workspace package) is not read. The `browser` field is never applied, as Jest's resolver does not apply it.
- **Served modules from an external edge.** When the dialect serves modules (`moduleScope.modules`, Jest's `@jest/globals`), an external whose closure has an edge to one is inlined for every file (`servedReach`, over the same closure walk as `mockedReach`, kept per worker), so its `require('@jest/globals')` gets the served value as a user file's does, not the real package that throws outside Jest. `createProjectLoader` starts the lexer for it too, and hashes the lockfile, so the graph cache serves later runs. The external's own edges are read first (the graph's node for it when the graph already holds one, else its text, then a scan): one that requests a served module itself is inlined without building its closure. `servedReach` and `claimedReach` share `cachedReach`'s lookup, walk and verdicts: the walk ends at the first edge `takes` names and at a file with a verdict already (a positive ends it, a negative is left out), so a positive costs the files visited before it (`reach.test.ts`). Otherwise the closure is walked once per worker (a negative walk over jsdom's 1,107 files: about 170 ms cold, about 35 ms from the graph cache, `local`, B23e), and a negative verdict covers every file it walked. **Limit:** a request the scan can't read (a computed `require(name)`, the closure's `dynamic` flag) is not seen, so a package that reaches a served module only that way stays shared.
- **Tests:** `loader.test.ts` (an external that registers `afterEach`, one that reads `expect`, one that reads `document`, and one that reads nothing, under `registry`: watched once each, the three inlined in the second file with their closure, the plain one shared; a seeded set inlines from the first file; nothing watched or inlined under the neutral value; a watcher that throws as it opens, an end that throws, a load that throws after a read, a no-op under `none`; a library that requires a learned singleton, sharing the file's copy in file 2 and evaluated once per file from a seeded set; D132: a registry a per-file plugin writes into through a re-export barrel evaluated per file with it (no duplicate id in later files), a dependency the plugin shares with a shared package evaluated once per worker, the same evaluations and instances in a worker seeded with what a cold one learned (the seeds' dependencies shared in its first file, the registry its own from the second), a shared importer of the registry first loaded in a later file inlined with it, a join found partway through a file (by a late package, and by a claimed file found then) taking effect from the next file, a registry whose files import each other, an importer inlined for a served module, a workspace package between the plugin and the registry (joined, and shared when a shared package loads it too), and a computed `require` that keeps the registry shared with its warning; `reevaluate.test.ts` holds `settlePerFile` on small graphs (chains, cycles, back edges, the order the edges came in, a warm worker that decides no region join in its first file and, from its second, keeps the cold worker's set whether or not its first file loaded the shared importer, pending joins, `elsewhere`, user modules, dynamic files, what probes nothing); `packages/provino/test/ecosystem-per-file.test.ts` holds `ecosystem/per-file-registry` and `per-file-registry-cycle` to Jest 30.5.2; a served module through an external, and one requested directly, decided without its closure; one inlined for a served module under `none`, evaluated once per worker).

## `node_modules` files a transform takes (B23e, D115, D130; `src/internal/claims.ts`)

Jest asks `ScriptTransformer.shouldTransform` of every module, `node_modules` ones included: a file a transform rule's pattern matches and no `transformIgnorePatterns` pattern does (joined with `|`) is transformed, its `import`s become `require`s, and jest-resolve finds an extensionless import by extension. `LoaderOptions.transformClaims` (`TransformClaims`, regex sources, from `SerializedLoaderConfig.transformClaims`) carries the patterns that take a file (the rules', and when `transforms` is empty the ones Provino's pipeline stands in for: Jest's default `babel-jest`, `NeutralProject.standInTransformPatterns`) and the ignore patterns, whether or not a transformer host is built. The claims have their own state (`ClaimsState`, as `reevaluate.ts` and `edge-kind.ts` do): the verdicts, the compiled patterns, and the few things a verdict reads (the edge-kind state, the inline state's graph, `required`, `externals`), never `Records`. `third-party.ts` holds `isThirdParty`, `source.ts` the file read and the shared wrapper and hashbang helpers, `require-esm.ts` the error below.

- **Transformed only when Node can't load it natively** (speed, D115, D130). A `node_modules` file the claims take (tested on the resolved real path, so a pnpm `.pnpm/<name>@<v>/node_modules/<name>/…` path reads as Jest reads it) has a verdict per worker (`claimVerdict`, `ClaimsState.verdicts`): `ignored` (no rule's pattern, or an ignore pattern matches), `user`, or `native`. It is `user` when Node can't load it: an extension Node doesn't run as JavaScript (anything but `.js`, `.cjs`, `.mjs`, `.json`, `.node`, `.wasm` or none: `.ts`, `.tsx`, `.jsx`, and assets such as `.css`, `.svg`, `.md`, since Jest runs the claiming transform on any claimed file and Node's own `require` of one is a `SyntaxError`), or ES module syntax (`.mjs`; a `.js` under `"type": "module"`, through `edge-kind.ts`'s manifest cache, `packageTypeAt`; else the graph's node when it has scanned the file (`GraphNode.esm`, recorded by `scanSource`), else the file's text through `esmSyntaxOf`: the `import`/`export` word test, then es-module-lexer's `hasModuleSyntax`, a file the lexer rejects counting as ESM), whose imports Jest resolves as `require`s. `.json`, `.node` and `.wasm` files are `native` and never read as source. A `user` file resolves as a `user` target, not `external`: transformed (role `dependency`, `CompiledModuleEvent.thirdParty`) by the host when a rule takes it, else by Oxc (which passes a `.js` file through as the default `babel-jest` with no Babel config does), and evaluated per file in the file's registry, so its own edges decide with the file's mocks and served modules like any user module's. Any other claimed file is `native`: shared, and Node loads it. `resolveOrMissing` and `targetOfId` both ask `isExternal`.
- **A native load that fails to parse** (`demoteOnParseFailure`, from `Registry.#loadClaimedNatively`): `#maybeInline` makes a `native` file's first native load itself (`claimedLoad` reads its verdict once: `user`, `untried` or `native`), so a `.js`/`.cjs` file whose load throws a `SyntaxError` (CommonJS with JSX, Flow or TypeScript syntax: a React Native package under `transformIgnorePatterns: ['node_modules/(?!react-native/)']`, which es-module-lexer reads as CommonJS) is compiled once as Node's CommonJS wrapper (`vm.compileFunction`, hashbang and BOM dropped). If that fails, nothing of it ran: its verdict becomes `user` for the worker and the edge takes the user route (and every later edge, a stale `external` target in a record's `resolved` included). If it compiles, the `SyntaxError` was the module's own (`JSON.parse`, `new Function`) or a file it requires: the error stands, and every later edge probes and runs the file again, as Jest does. Asked only after a native load threw, so a load that works pays nothing; the compile is about 8 ms per MB.
- **A shared external that reaches a claimed user module is inlined** (`claimedReach` in `inline.ts`, `#maybeInline`'s third reason, kept `'kept'` in the per-map memory): a native CommonJS package whose static closure has an edge to a `user` claimed file would `require` Node's copy of it (a second instance beside the file's, or a crash on an extensionless import Node can't find: mixpanel's CommonJS build requiring its ES module helpers). The walk is `cachedReach` over the graph `servedReach` already builds, its verdicts in `InlineState.claimed` (beside `served`), cleared when a `native` file becomes `user`. Under `reevaluateHookingExternals` a claimed user module is also a seed of the per-file set (D132, through `markUser`, the one writer of `ClaimsState.users`), so a dependency only it and other per-file files import is evaluated per file with it.
- **Cost:** with no claims, nothing. **Jest's default patterns are no claims, decided in `@provino/config`:** `resolveTransformClaims` returns no claims when an ignore pattern matches every `node_modules` path (`/node_modules/`, `node_modules`, with or without the slashes), so no verdict or closure walk runs (the config's resolve-transform tests pin it). A caller that builds a loader with such patterns itself gets claims whose every verdict is `ignored`. Otherwise one `Map` lookup per resolved `node_modules` target after its first (its first: the joined ignore pattern, then the rules' tests and the syntax check), and one closure walk per shared external per worker, cached.
- **Validation:** `compileClaims` compiles each rule's pattern and the ignore patterns joined with `|` (`ignoreRegExp` from `@provino/transform`, the one join Jest and the host build); a bad one is `LOADER_INVALID_TRANSFORM_CLAIMS`. `@provino/config` refuses the same earlier (`CONFIG_INVALID`), so a project never gets here with one.
- **`require-esm`** (`require-esm.ts`): a shared external whose native load throws rethrows as `RequireEsmError` (`name` `Error`, code `ERR_REQUIRE_ESM`, `cause` Node's error) with the dialect's text (Jest's `Must use import to load ES Module: {path}` and the three ways out), under jest-runtime's conditions (`CjsLoader.ts` L171-L180): the file's source has ES module syntax (`esmSyntaxOf` is `true`: a file the lexer rejects counts as none, as jest-runtime's `esmLexer.ts` reads it; an addon, `.wasm` or `.json` file is never read), it is not explicitly CommonJS (`.cjs`, or a `.js` under `"type": "commonjs"`: `isExplicitlyCommonjs` in `edge-kind.ts`), and Node can't evaluate an ES module graph synchronously (`RuntimeCapabilities.syncEvaluate`, Jest's `supportsSyncEvaluate`, where Jest loads it as an ES module instead). Jest's third condition, `error.name === 'SyntaxError'`, is its own CommonJS compile's, which every file with ES module syntax fails; Node loads one as an ES module (`require(esm)`), so any error stands for it (`ERR_MODULE_NOT_FOUND` for an extensionless import, recorded by `cli/transform-node-modules-ignored`, where Jest prints the text). Asked only after a load failed; with no text in the policy Node's error stands. The conditions are one neutral rule and the dialect's message only replaces Node's text (as `unresolved-mock-import` does). The async preload (`interopDefault: 'node'`) is not wrapped.
- **Limits (DIVERGENCES candidates):** a `native` claimed file is shared by the worker (its state is per worker, not per file) and a transform's plugins never run on it. A native file that `require`s a claimed file Node can't parse (a plain `index.js` re-exporting a Flow file) fails with Node's `SyntaxError`: the parent ran up to the `require`, so the error stands, and the walk does not compile every claimed file ahead (about 8 ms per MB per worker) to find the child; once the child became `user` by another route, the walk inlines the parent.

## V8's code cache of the wrapper scripts (B23e; Tyler, 2026-11-16, `speed`)

Node's compile cache covers only the modules Node loads; a worker's first file compiles the shared graph (a real React suite: about 13,000 records, 11 to 18 s, the profile in `Script` and lazy compilation). `LoaderOptions.codeCache` (the transform cache's directory) makes `wrapperScript` compile through `openV8Pack` (`@provino/transform/v8cache`, `packages/transform/CLAUDE.md`): the packs in `<cacheDir>/v8/`, each pack's index read once per worker (on its first compile), and one positioned read per script. A hit is V8's data for exactly that text: the key is a hash of the wrapped text, the filename and the column offset, inside V8's version and flags (the pack's tag), so an edited module misses alone, at any length, and the others still hit.

- **When it writes** (`Records.codeCache`, `CODE_CACHE_WRITE_BATCH`): a script with no entry, or whose entry was refused (a checksum that fails, `cachedDataRejected`), is queued; `FileRegistry.dispose` (a test file's end) serializes the queue (`createCachedData`) once 64 are waiting, and `Loader[Symbol.dispose]` the rest. So an entry is made after its record ran (it holds the functions the file's tests compiled lazily too); a worker's first file, which compiles the shared graph, writes at its end (a worker killed later keeps it); a later file that compiled itself and a few modules adds no pack of its own. The write is synchronous (a worker exits right after its stop) and never throws. Its cost, paid by a cold run only: about 0.5 ms per script of 7.7 KB with 40 functions run, 0.25 ms at 1.9 KB and 10, 7 µs at 300 characters (serialize and write, 3,000 scripts, `local`, a loaded machine); the `bench:loader ui-library --functions 30` graph's first pack is 12.7 MB for about 2,800 scripts.
- **Measured** (`local`, Node 24.22, both checkouts in `$TMPDIR`: a checkout under the agent sandbox's worktree path pays about 50 µs a file open, which skewed a first run; 7 warm runs, interleaved, against origin/main): `bench:loader ui-library` file 1 579 against 605 ms, files 2..12 22 against 21 (its modules are a few hundred characters: compile is about 40 ms of file 1); `--functions 30` file 1 625 against 817 ms, wall 1285 against 1487, files 2..12 35 against 34. A cold code cache (none on disk, so the run writes it) costs that graph +103 ms on file 1 and +194 ms of wall, once. `megamorphic` stays flat (files 2-5 against the last 5: x0.94; origin/main x1.00). `arrayBuffers` read 13 MB higher without a forced collection; after one (a probe of 3,000 scripts and a 13.7 MB pack) 0.1 MB, the same as with no cache: a script keeps none of its data.
- **Who turns it on:** `createProjectLoader` gives it only with `config.cacheDir` (none under `--no-cache`), `ProjectLoaderOptions.codeCache: 'on'` (default `'off'`), and no Istanbul `coverage` (`cacheModeFor`). The worker's runner passes `'off'` under either coverage provider: V8 reports no block ranges for a function restored from a code cache (T3.7). The coordinator's loader has none.
- **Tests:** `src/code-cache.test.ts` (in fresh children, through the records and a registry: a warm worker hits every script and V8 accepts each entry; an edited module of the same length misses alone; a damaged entry is rejected and rewritten; in this process: the file-end and dispose writes, and a project loader with and without one: `--no-cache`, `'off'`, the default, Istanbul coverage), and the orchestrator's `coverage-collect.test.ts` ("a warm code cache": coverage over a cache a run without coverage filled equals coverage with none, V8 and Istanbul, and a covered run writes none).
