# provino

The umbrella package (layer 6, composition root). B11 built its first part: `provino/node`'s `run()` and the `provino run` bin. B14c added the dialect commands: `provino jest`, `provino vitest` (refused) and bare `provino`. It names the built-ins nobody else may (`jestDialect`, `@provino/env-node`) and wires config, orchestrator and reporters together; `slices: []` in the manifest, so no source file here may name `Policy` or a slice type (the Biome rule `slice-discipline` fails the lint; reading `project.policy.report` by property access is fine).

## Build and exports (B21e, T1.10)

`pnpm --filter provino build` writes one bundle to `dist/` (`tooling/packaging/CLAUDE.md` → "The umbrella"): every `@provino/*` package inlined, `dependencies` the third-party packages they need (`pnpm hygiene` checks the list), seven files from the package in a worker's cold start (the transform, resolver and loader and their Oxc natives are one chunk, `loading.js`, that the `expect` runtime does not import). `exports`: `.`, `./globals`, `./config`, `./node`, `./reporters`, `./environment`, `./jest` (each `provino-source`, `types`, `import`) and `./package.json`; any other path throws `ERR_PACKAGE_PATH_NOT_EXPORTED`. `bin` is the source for the workspace and `publishConfig.bin` the built `dist/cli.js`. `provino --version`, `--help` and `-h` are answered by the bin before it imports the rest (`src/cli.ts` uses a dynamic import of `internal/cli.ts`). `quickAnswer` in `internal/quick.ts` is the one implementation: the bin and `main` both call it (`internal/usage.ts` holds `USAGE`, `internal/version.ts` the version), so they load no Oxc native binding. That import is also where a missing binding surfaces: `internal/native-binding.ts` (`missingBindingMessage`) turns it into one message naming this platform's `@oxc-parser/binding-<platform>`, `@oxc-transform/…` and `@oxc-resolver/…` (those it can't resolve from where the base package is installed), exit 1, no stack. The probe decides first: if any of the three can't be resolved, that is the message, whatever the error says; only when all resolve does the text count (`dlopen` or `.node`, naming an Oxc package: swc's identical loader text passes through), and any other error is rethrown. `bindingTriple` is held to the installed packages' `optionalDependencies` keys by `native-binding.test.ts`. `test/native-binding.test.ts` runs the built bin under `test/block-oxc-bindings.ts` (a `registerHooks` resolve hook that fails the binding packages), and `pnpm smoke:install` deletes them from a real tarball install (T10.3, Provino's half). API reports are `etc/provino*.api.md`. `/plugin` (no package) and `/vitest` (T11.16) wait. `test/exports.test.ts` runs the **built** package (turbo `test` depends on `build` here, `turbo.json`): the subpaths and what they export, the refused paths, the bin, and a real project whose test imports `provino`, with a `registerHooks` recorder (`test/load-recorder.ts`) counting the files a worker loads from `dist` (at most 10; it is 7), and a second test that importing `provino` and the worker-side `expect` loads no `loading.js`, coordinator or Oxc file.

## `run()`

Flow: check `config` and `maxWorkers` → `loadProject(config against cwd, { dialects: [jestDialect], environments: { node: env-node }, ci })` → build the reporters and the bus → `runProject` (pool kind and `maxWorkers` only when given, `cache: false` only when asked (otherwise `runProject` keeps its own default cache in `node_modules/.cache/provino`), `stderr` for the workers' own stderr) → `exitCodeFor(summary, { policy, passWithNoTests, reporterFailures })`.

- **Bad input never rejects.** A `UsageError` (no config path, `maxWorkers` not a whole number of at least 1, an unknown reporter), a `ConfigError` (with its issues and `cause` chain) and `OrchestratorError` `ORCH_BAD_PATTERN` or `ORCH_BAD_OPTION` (a `bail`, `workerMemoryLimit`, `maxFilesPerWorker` or `fileTimeoutMs` that makes no sense: the orchestrator is the one place those limits are checked, and its message names the option and the value; `bail: 0` is off and filtered before the call) are written to `stderr` as `Provino: <message>` and become `{ exitCode: ExitCode.UsageError (2), summary: null }`. Every other error is a bug and rejects. The pattern is checked by `runProject` before anything starts, so no reporter has said anything.
- **Output.** `default` writes to `stderr` (as Jest does, so stdout can carry the JSON); `normalized-json` writes to `outputFile` (resolved against `cwd`) or `stdout`, with `suite` the root directory's name, `runner` `provino:<dialect name, or neutral>`, `runnerVersion` this package's version, and the policy's `orchestrator.unhandledErrors`, so the file's `success` agrees with the exit code. `json` is the same reporter under a second name; `junit` writes its XML the same way (`outputFile` or `stdout`). `reportersFor` registers the document reporters (`json`, `normalized-json`, `junit`) last, whatever order they were named in, so each sees every other reporter's failure before it writes. Two reporters that both write to stdout, an empty `outputFile`, and an `outputFile` that resolves to a directory are usage errors (exit 2), found before the run starts. **The environment chooses the reporters when none are named (B21c, T9.7):** `agent` replaces `default` when an agent runs the process (the `agent` reporter: failures and totals), and `github-actions` is added on GitHub Actions; `FORCE_COLOR`, `NO_COLOR`, the terminal (`stderr.isTTY`) and `--colors` decide colour, and a terminal that is not CI, not dumb and not an agent's gets the live block. `RunOptions.env` (default `process.env`) is what `detectOutput` and `isCi` read, so a caller can fix it; `CliIo.env` and `JestCommandIo.env` are the same for `main` and `runJestCommand`. The composition roots (`run()`, `runJestCommand`) resolve it once, `env ?? process.env`, and `executeProject` and `reportersFor` take it as given (required), so no module below reads `process.env`. A reporter named on the command line or in `reporters` is never replaced. A reporter that throws fails the run (exit 1), and `run()` also says so on `stderr`, since only `default` shows reporter errors.
- **Re-entrant.** No `process.exit`, no module-level state: the pool and the cache belong to one call, so calls follow each other or overlap on different projects. A config file is read afresh on every call (`loadConfigFile` busts Node's module cache for it; the files it imports are still cached).
- `ci` defaults to `isCi(env)` (`@provino/reporters`' one rule for `CI`, which `detectOutput` and the `normalized-json` reporter use too): `CI` set, and not empty, `0` or `false`, ignoring case and spaces (`CI=FALSE` and `CI=' false '` are not CI). That is the one answer for the run: the project is loaded with it, and the `normalized-json` reporter is given the same value (`env.ci`), so the file never disagrees with `--ci`, the `ci` option or the variable. `signal` aborting ends the run with exit 130.

## `provino jest` (B14c, T11.13, U3)

`runJestCommand`: parse the arguments with the Jest dialect's own parser (`jestNodeDialect.cli`, T11.7) → read the config with `createJestConfigReader({ argv, cwd })` (find from `cwd` or `-c`; no config file means Jest's defaults over `cwd`: an inline `{}`), `resolve` and `toNeutral` → print every diagnostic (the reader's warnings, the parser's refusals and "read but not applied" warnings) → one of four modes → `resolveNeutralProject` per project (`ci` is the global config's) and then:

- **run:** `executeProject` with the pool from the global config (`maxWorkers` as Jest normalized it, `-i` is 1; `--workerThreads` is the threads pool), `-t` from `globalConfig.testNamePattern`, the request's file filters (`selectFiles`, so a filtered run still prunes the results cache against the whole set) and no cache with `--no-cache` or `cache: false`. Several projects (the config's `projects`) run in one pool through `runProjects` (D29, B17d): `executeProject`'s `others` and `root` (the config's `rootDir`); exit codes are those of one project. `--projects` is still refused (no task yet). **`--selectProjects` / `--ignoreProjects`** (D69, `select-projects.ts`) keep or drop projects by `displayName` as `jest-core`'s `getConfigsOfProjectsToRun` does (an unnamed project is never selected and never ignored; `--clearCache` still clears every project), and write Jest's texts (the missing-names warning, `Running one project: x` / `Running N projects:` with a sorted list, or why none runs, without Jest's colours) to stdout, or to stderr under `--json`/`--useStderr`. A selection that leaves no project runs nothing and prints Jest's `No tests found` text (`--passWithNoTests`: its one line); exit is the dialect's `noTests` code, or 0 with `--passWithNoTests`. `projects.test.ts` runs each case under live Jest 30.5.2: statuses, stdout and exit code.
- **Global setup (T9.15).** `provino jest` runs `globalSetup`/`globalTeardown` (no "not applied" warning): in the coordinator, through the project's transform, once per distinct path and project, in Jest's sequenced order, then the root config's own hooks (`jest-command.ts` passes `jestRunGlobalHooks(globalConfig)`, from `@provino/dialect-jest/node`, as `RunProjectOptions.globalSetup`), with `(globalConfig, projectConfig)` (`globalConfig.testPathPatterns` a `TestPathPatterns` object as in Jest 30); see `packages/orchestrator/CLAUDE.md`. `test/global-setup.test.ts` runs the bin against the recorded `cli/global-setup-{order,globals,throws,projects,root-projects,sequence,throws-typeerror,throws-object,throws-string,test-path-patterns,no-test-path-patterns}` and `cli/global-teardown-{output,throws}` (order of setup, test and teardown; `globalThis` seen by the teardown but not by a worker's test; the throw's exit code and message, its class and a non-Error as pretty-format prints it; two projects, the root's hook, the sequenced order; every member of `testPathPatterns`; a teardown's output and failure below the totals, in order) and real Jest 30.5.2 beside it for a TypeScript setup under babel-jest and ts-jest (`packages/transform/fixtures/global-setup`), and for the in-band leak (`--detectOpenHandles` runs both in band; `-i` still starts a worker here, T9.9).
- **`-u` / `--updateSnapshot` and `--ci`** (B17b, T7.9): `-u` is the request's `update`, which `executeProject` hands to `runProject` (snapshots that differ are rewritten and obsolete ones removed); `--ci` (or the `CI` variable, as Jest reads it) is the project's `ci`, so a CI run writes no snapshot and fails a missing one. `resolveUpdateMode` in `@provino/snapshot/node` turns the two into Jest's `all`, `new` or `none`. `test/jest-snapshots.test.ts` runs the bin against the `snapshot/*` goldens recorded from Jest 30.5.2 (`update-all`, `new-ci`, `obsolete-ci`): exit code and `.snap` bytes.
- **`--listTests`:** every project's discovered files, filtered, once each and sorted, one path per line, or a JSON array with `--json` (written to `--outputFile` when given, as Jest does). It starts no worker. A project's own `testEnvironment` (jsdom, `jest-fixed-jsdom`, a custom class) runs through the Jest adapter (`JEST_ENVIRONMENT` in `built-ins.ts`, D44): `environmentsFor` maps its absolute path to the adapter, and `jest-environment-node` stays the built-in `node`.
- **`--showConfig`:** `{ globalConfig, configs, version }` as JSON (keys as our reader normalized them; Jest's own output is not compared).
- **`--clearCache`:** removes each project's Provino cache directory (`node_modules/.cache/provino`, or `<cacheDirectory>/provino` when the Jest config sets `cacheDirectory` itself, D70; the transform cache `t/` goes with it) and prints `Cleared <dir>` once per directory (projects share one). ## The bin

`provino run --config <file> [--maxWorkers n] [--pool forks|threads|inline] [--reporter name]… [--outputFile path] [-t pattern] [-u] [--ci] [--passWithNoTests] [--no-cache]`. A missing command, an unknown command or flag, a missing `--config`, a bad value, or `--outputFile` without `--reporter normalized-json` prints the message and the usage text to stderr, exit 2. `--help` prints the usage text to stdout, exit 0. A bug prints its stack, exit 1. The bin sets `process.exitCode` and calls `process.exit` in two places only, both in `src/cli.ts`: after `--forceExit`, once stdout and stderr are flushed, and 750 ms after a second signal. A signal that came ends the process with its code (130 for SIGINT, 143 for SIGTERM, 129 for SIGHUP) even if the run had nothing left to interrupt, and one that comes after the run (a leaked handle in an inline pool keeps the process up) ends it at once with that code, not by the signal. `process.exitCode` is set as the first signal lands, not when `main` returns: a run left with nothing to hold the event loop (a reporter promise that never settles) would otherwise end on the unsettled top-level `await` with Node's 13. SIGHUP is handled like SIGTERM (without a handler Node's default action ends the bin at once and a worker in a synchronous loop survives); the run's summary calls it `hangup`, and `run()` aborted with `'SIGHUP'` returns 129 as the bin does. With forks or threads the pool has stopped every worker, so the process ends on its own (`test/cli.test.ts` runs it with a deadline). **With `--pool inline` it may not:** the worker shares the process, so a test's leaked handle (timer, socket) keeps it alive, as with Jest's `--runInBand`, unless `--forceExit` ends it.

- **`--shard <i>/<n>`, `--timings <file>`, `--update-timings` (B21d, T9.6):** `RunOptions.shard`, `timingsFile`, `updateTimings`. A bad shard is a usage error (exit 2); a timings file that is there and wrong stops a sharded run (`ORCH_BAD_TIMINGS`, exit 2); `--update-timings` with `--shard` is a usage error too (`ORCH_BAD_OPTION` from the orchestrator: exit 2 under `provino run`, Jest's 1 under `provino jest`, `test/shard.test.ts`). **`provino jest`** takes Jest's own `--shard=i/n` (the config reader validates it with Jest's texts, the exit code is Jest's 1; `--listTests --shard` lists the shard's files) and, as Provino's own extras taken out of the arguments before Jest's parser sees them, `--timings <file>` and `--update-timings`. Without a timings file the Jest dialect runs the files Jest runs for each shard (recorded: `cli/shard-*-of-3`, `test/shard.test.ts`); see `packages/orchestrator/CLAUDE.md` → "Sharding and the timings file".
- **The lifecycle flags (B21a, T9.5, T9.10):** `--bail[=n]` (`RunOptions.bail`; a bare `--bail` is 1, `--bail 2` is 2, 0 is off; `parseArgs` has no optional values, so `bailWithCount` rewrites it first), `--forceExit` (`CliIo.onForceExit`, answered by the bin; `provino run` says it is force exiting unless `--detectOpenHandles`), `--detectOpenHandles`, `--workerMemoryLimit` (Jest's units: `512MB` is 512,000,000 bytes, `512MiB` is 2^29), `--maxFilesPerWorker`, `--fileTimeout` (`RunOptions.fileTimeoutMs`). `RunOptions.signal` aborted with the reason `'SIGTERM'` is exit 143, `'SIGHUP'` 129 (the summary's `reason` is `hangup`), any other abort 130; `forceSignal` is the second Ctrl+C. **`provino jest`** reads the merged global config, not the command line alone: `bail` (a count: `--bail=2` is false in Jest 30.5.2, so a count comes from the config), `detectOpenHandles` (in band), `forceExit` (Jest's warning, `Force exiting Jest: Have you considered using \`--detectOpenHandles\`…`, unless `--detectOpenHandles`) and `workerIdleMemoryLimit` (`workerRecycle` takes the number the Jest reader has already normalized with `stringToBytes`, as jest-runner hands it to jest-worker: 0 is every file (a share that floors to 0 bytes is 0 too), any other a count of bytes; a DIVERGENCES entry: jest-worker compares the child's `heapUsed`, the pool a forked child's RSS (a thread's used heap, as jest-worker does), and jest-worker's thread workers read 0 as no limit while the pool replaces after every file).

`-u` / `--updateSnapshot` (`RunOptions.updateSnapshot`, B17b) rewrites the snapshots that differ and removes the obsolete; without it new snapshots are written, and none in a CI run (the `snapshot` policy, resolved by `runProject`).
- `--reporter` takes `default`, `verbose`, `dot`, `agent`, `json`, `junit`, `github-actions` and `normalized-json`; `--outputFile` goes to the one document reporter among them (`json`, `normalized-json` or `junit`: none, or two, is a usage error). `-<short>=<v>` is rewritten to the long option before `parseArgs` (which would keep the `=` in the value), for every string option with a short name in the options table (today `-t` and `-c`). A repeated `--reporter` name is a usage error.
- An inline pool runs one worker (the orchestrator caps it). An inline worker doesn't capture console, so a test's `console.log` reaches stdout: use `--outputFile` for normalized-json with `--pool inline`. With forks or threads, the workers' own stdout goes to stderr.
