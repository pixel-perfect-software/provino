# @provino/orchestrator

The coordinator (`.`) and the worker entry (`./worker`), as two manifest nodes in one package. They never import each other: shared types come from `@provino/types` and shared runtime code from `@provino/rpc`. B09 built the transports, the per-worker connection and the worker-side packer. B10 built the worker runtime (U1): `./worker/main`, the entry that wires the loader, the environment, the dialect's globals, `@provino/expect` and `@provino/core` behind `startWorker`. B11 built the coordinator's run: discovery, the results cache, the sequencer, the pool, event dispatch, `runProject` and the exit codes (see "The coordinator"). B21a added the run lifecycle (T9.5's rest, T9.10: see "The lifecycle"). Watch, sharding and the other reporters come later (see "Not built yet").

## How a worker runs

1. The transport spawns `bootstrap.ts` and passes the entry module URL: `argv[2]` for a fork, `workerData.entry` for a thread. Inline has no bootstrap: the transport imports the entry itself and builds the port over a `MessageChannel`.
2. The entry's default export (`WorkerMain`; `./worker/main` for the real worker) gets a `WorkerPort` and calls `startWorker`. That sends `ready`; the transport answers with `start` and only then resolves `create()`. The `start` send is the one check that the init can cross: a value the link can't write kills the worker and rejects with `ORCH_BAD_INIT`.
3. Each `run` gets a fresh console, goes through `runner.runFile`, then yields one macrotask (every microtask the file left behind runs, so a floating `.then` that logs is still in the file's output), flushes stdio, and queues `fileDone` with `packer.afterSent`. Every event emitted before that call precedes `fileDone`, by construction. A runner that throws (in `runFile`, or in `start`, which then fails every file) is charged to the file as an `unhandled-error`, and the file still gets its `fileDone`: no failure can stall the worker's queue. A `cancel` aborts the running file and every file already queued.
4. `stop` drains the queue, calls `runner.stop` (when `start` came; a throw is charged as an `unhandled-error` with no owner, and `stopped` is sent anyway), sends `stopped` and closes the link. The bootstrap then **exits on purpose** (`process.exit(0)`), after a fork's IPC disconnect, so a handle a test leaked can't keep the worker alive. If the coordinator dies, the link closes and the worker exits the same way.
5. **A link that closes before any `stop`** (the coordinator died, or `terminate(true)`) aborts the running and queued files and restores the console at once, then queues a best-effort `runner.stop`, whose errors and output are dropped (nothing can be sent). `startWorker`'s promise settles only after that stop has. It matters for an inline worker, which lives in the coordinator's process: without it the matcher slot, the loader and the environment stay installed and the next inline worker fails `start` with `EXPECT_SLOT_TAKEN`. The stop queues behind the file running now, and `cancel` can't reach core until T5.12, so a file still running delays it. A fork or thread just exits.
6. **"The worker ended" is one definition for every kind: its `main` has settled and the link has closed** (the bootstrap does `await main(port); await closed`). The inline transport reports its exit on the same condition: when the coordinator's end of the link closes it waits for the entry's `main` promise, then reports `{ type: 'exit', code: 0 }` (or `code: 1` for a `main` that threw, which is printed to the `stderr` sink first). Because `main` settles after the best-effort stop, a `terminate(true)` (or any kill) of an inline worker does not return before that teardown has finished, even one that does real I/O, so the next inline worker in the process boots with the slot free. `kill()` closes only the coordinator's end; the worker hears of it as a `close` event on its port. **The wait is bounded** by the transport's teardown timeout (`teardownTimeoutMs`, default 10 s; `settlesWithin`): a `main` that can't settle (a file that can't be cancelled until T5.12 holds the stop behind it) is reported as it is once the bound passes, so `terminate` can't hang. A `terminate(false)` on such a worker waits that bound twice at most (the stop timeout, then this one after the SIGTERM).

## The runtime (`createRuntimeRunner`)

The environment and the dialect's globals load **by ref** (`config.environment`, `config.globals`), never by import: this node knows no dialect and no environment package.

- **One `parts` object.** `boot` fills it in as it goes (slot, loader, runtime, state source, prepared environment, globals, snapshot, tier and `scope`), `runFile` checks `isBooted(parts)` once (`ORCH_NOT_STARTED`), and `stop` takes the whole object and leaves `{}` behind, so a worker whose `start` threw half-way is undone and `stop` runs twice without harm. `scope` (`'worker'` under `none`, else `'file'`) is computed once from the tier; a worker-scoped environment is stored as `{ instance, name }`.
- **`start`, once.** Parse the config → one behaviour loader and one project loader (`createProjectLoader`) → source-mapped stacks (`installSourceMappedStacks`, `@provino/loader`; `stop` puts the formatter back after the loader is disposed) → expect in its documented boot order (state source, matcher registry, slot, the dialect's table, `createExpect`) → `createRuntime` with the assertion-count sink in front of the packer → the environment's `prepare` once → the globals factory once, if `policy.core.injectGlobals`, with a `RuntimeGlobalsHost` → **then** `snapshotRegistry(registry, expect)`, so a matcher the factory adds (`expect.extend`) is in the baseline each file's restore returns to, not a leak of the first file. A throw here fails every file with its code (`startWorker`'s `startFailure`).
- **`RuntimeGlobalsHost`** (`@beta`, exported from `./worker`) is `GlobalsHost` with core's `api` and the worker's `expect` typed. `GlobalsFactory` is bivariant in its host, so the compiler wouldn't catch a wrong host at the call; `packages/bench/test/worker-host.test-d.ts` asserts it is assignable to the Jest dialect's own host (the bench is the one package that imports both).
- **`runFile`, per job.** Wait for the packer's `writable()` (a cancelled file never starts) → the mock registry, then `loader.createFileRegistry(file, { tier, moduleMocks, moduleScope })` (`process` runs as `registry`; `realm` throws `LOADER_NOT_IMPLEMENTED` here, before anything is set up) → environment `setup` (scope `file`, with the file's `signal`; scope `worker` under `none`, set up once for the first file, with `testPath` that file's path and a worker-lifetime `signal` the runner aborts in `stop`; every context carries `processObject`, the policy's `orchestrator.processObject`, so the environment installs a copy of `process` for the file: see `@provino/env-node`) → install the globals `globalsBeforeSetupFiles` lists on `instance.global`, every file (the rest after `setupFiles`) → `source.startFile` → `runtime.runFile(file, { testNamePattern, testIds })`, whose `importFile` imports each of `setupFiles` and then `setupFilesAfterEnv` and then the test file, inside collection (under `none` each of them, the test file included, is `invalidate`d first; the other tiers have a new registry, so they skip the extra resolver call) → teardown.
- **The fake clock (T4.9, B17a).** Each file gets `createFakeClock(instance.global, policy.timers, { bind: currentTest.bind })` once its environment exists, on the environment's global, and `host.timers()` returns it (read at call time, like `host.mocks()`; `host.timersPolicy` is `policy.timers`). `timers.enableGlobally` installs it before `setupFiles`; `SerializedProjectConfig.fakeTimers` is the `defaults` option. The host also gives the dialect `seed` (`SerializedProjectConfig.seed`, else drawn at boot), `environmentTornDown()` (`FileScope.tornDown`, true once the file's teardown ran, and for code with no file) and `setDefaultTimeout(ms)` (core's `Runtime.setDefaultTimeout`, cleared when the file ends). Teardown disposes it first (the real timers are back before the mock teardown and the environment's own check), under `none` too, since the environment outlives the file. A callback a fake timer fires runs in the context of the test that scheduled it.
- **Process errors (T5.11, B17a).** `boot` calls `coreRuntime.captureProcessErrors()` (the worker's `process`, for the worker's lifetime; `stop` removes the listeners first), so an uncaught exception or a rejection with no handler is charged by `errors.lateErrors`. `startWorker` already yields one macrotask after `runFile`, with the clock back to real, which is when Node reports a rejection a file's last test left: core charges it then (a late `unhandled-error` event, before `fileDone`).
- **The end of a test (T7.8).** `boot` passes `createExpect` the core leaf `policy.core.unawaitedAsyncAssertion` (`expect` reads only its own slice) and `pollTimers.advance`, which moves the current file's fake clock (`(fileScope.getStore() ?? fallback)?.clock`, when `isInstalled()`), then registers `coreRuntime.onAfterTryTask` with `@provino/expect`'s `createEndOfTest` over `table.messages`, `policy.expect` and `policy.core.errors.hasAssertionsWhenFailed`. Soft failures, a missed `expect.assertions`/`hasAssertions`, `requireAssertions` and unawaited async assertions fail the attempt there. Core adds one error per thrown value, so several are thrown as one `AggregateError`. Tested in `test/runtime.test.ts` ("the end of a test").
- **The mock registry (B13a).** The worker owns a `MockRegistry` (`@provino/mock`), not core: a new one per file, or under `none` one for the worker, made for its first file ("`none` keeps everything"). `host.mocks()` returns the current one and is read at call time, like `host.registry()`; `host.mockPolicy` is `policy.mock`. Both stay in the worker (never `CloneSafe`-bound). **A file's async work keeps the file's registries.** `jest` is one object on a shared global, so a callback a file leaves behind (`setTimeout(() => jest.resetAllMocks())`) would find whichever file runs when it fires. The runner enters a module-level `AsyncLocalStorage` (`fileScope`, built at load like core's `currentTest`) holding `{ registry, mocks }` around `runtime.runFile`; `host.registry()` and `host.mocks()` read it first and fall back to one current-file `{ registry, mocks }` (`importFile`, the globals' setup and the teardown run outside it, and a callback that lost its async context, such as a native addon's, still needs it; keep it), and outside any file they throw `ORCH_NO_ACTIVE_FILE`. A second active store costs about 8 ns per await on Node 24 and about 20 ns on Node 22 (`local`, measured 2026-11-06), accepted over threading a context through core's `newStore` sites. A stale callback therefore acts on its own, by then disposed, registries and its `resetAll` is a no-op; under `none` the registry is shared and nothing changes. `stop` also clears the current mock registry, so `host.mocks()` throws after it instead of returning the disposed one. Remaining limit: a stale callback's `jest.spyOn` installs on its disposed registry, so it is never restored. **Cleanup between tests (T4.10, B17a)**: `boot` registers `coreRuntime.onBeforeTryTask(() => activeMocks().beforeEach({}, policy.mock.between))`, so the registry's `beforeEach` runs ahead of every attempt's first `beforeEach`, in the attempt's own async context, on the file's registry (read when it runs). The project's `clearMocks`/`resetMocks`/`restoreMocks` reach it as `policy.mock.between` (the Jest config reader maps them, so `provino jest` applies them, checked through the bin in `packages/provino/test/jest-mock-cleanup.test.ts`; `run()` has no key for them).
- **Snapshots (B17b).** `boot` loads the snapshot slice's behaviours once (the key function, the dialect's printer, a path resolver if the policy has one). `runFile` opens the file's snapshots after `source.startFile` (`openFileSnapshots`: the `SnapshotState` and the lifecycle), puts the state in the file state (`snapshotState`), and the sink in front of the runtime hands every event to the lifecycle first (`observingSink`). `importFile` adds `policy.snapshot.serializers` through the file's registry before the setup files. After `runtime.runFile` the lifecycle finishes (obsolete settled, `.snap` saved) and the report goes out as `FileOutcome.snapshot`, left out when it says nothing. A header the policy can't read or a file that never collected writes nothing.
- **The module-mock registry (B13c).** `boot` makes the module-mocking pieces once (`parts.modules`: the policy, `roots` `[rootDir]` until B14c, the loader's extensions, and `createRootMockIndex` over them, so the root `__mocks__` trees are listed once per worker), and, when `config.moduleScope` is a ref, loads the dialect's module-scope factory and calls it once with the same host the globals get (`parts.moduleScope`; it exists whether or not globals are injected, and serves the imports; the bindings a wrapper declares are `config.loader.moduleScope`, empty when `injectGlobals` is off). `runFile` hands `createFileRegistry` a `moduleMocks` factory that builds the file's `ModuleMockRegistry` (`createModuleMockRegistry` over the policy's `module` and `mock` slices, the file's mock registry, and the loader's own resolver, conditions and `loadActual`) and `moduleScope`. Every tier gets one per file, `none` included (B13c Gap 9). `host.moduleMocks()` returns the current file's, read at call time like `host.registry()`. `config.loader.hoist` (the dialect's, by value) reaches `createProjectLoader`.
- **Teardown order**, always, each step running whatever the earlier ones threw: **the module-mock registry's `dispose()` first** (its mocks live in the mock registry; under `none` too), then **`mocks.dispose()` (file scope)**, so spies and replaced properties are restored while the environment is alive (env-node only compares the global's own keys, so an unrestored `jest.spyOn(Math, 'random')` would leak into the next file), then the environment's `teardown` (file scope), the matcher restore (file scope), `registry.dispose()`. The file-scope steps are left out of the list under `none`, not skipped inside the steps; there the worker's mocks are disposed first in `stop`. What threw is rethrown after all of them (an `AggregateError` for several), and `startWorker` charges it to the file as an `unhandled-error` and still sends `fileDone`. A `teardown` that throws is still a failure charged to the file.
- **Globals the environment can't remove are a warning (D22).** `teardown()` may return an `EnvironmentTeardownReport` (`{ leakedGlobals }`, `@provino/types`). For a **file-scoped** teardown the runner sends one `console` event through the context's sink after the file's own events and before it finishes: `taskId: null`, `stream: 'stderr'`, `level: 'warn'`, `origin: null`, text `Provino: <file> left N globals behind that the environment could not remove: a, b. Later files in this worker can see them.` (singular: `1 global ... see it`). It returns `{ leakedGlobals }` on the `FileOutcome`, which `startWorker` sends as `fileDone.leakedGlobals` (always present, `[]` when clean), so B11's pool can recycle the worker on `RecyclePolicy.onLeak`. A **worker-scoped** teardown (isolation `none`, in `stop`) sends `Provino: the environment could not remove N globals when the worker stopped: a, b.` before `stopped`, with nothing on any `fileDone`. If another teardown step of the same file also threw, the file is charged for it and its `fileDone.leakedGlobals` is `[]` (an error replaces the outcome), but the warning was still sent.
- **`stop`.** The worker's mock registry (isolation `none`) `dispose()`, `runtime.dispose()`, the worker-scoped environment's `teardown` (its report becomes the warning above), `loader[Symbol.dispose]()`, `slot.uninstall()`, then the worker-lifetime signal is aborted; errors collected and rethrown after all of them. It copes with a worker whose `start` threw half-way, and runs twice without harm.

## The coordinator (`runProject`)

Flow: pattern check (`ORCH_BAD_PATTERN`, `new RegExp(p, policy.core.testNamePatternFlags)`) → cache (`ResultsCache | false`; omitted means the default dir) → the worker entry and the pool (`createPool` throws `ORCH_BAD_OPTION` for a `recycle` or `fileTimeoutMs` that makes no sense, and `runProjects` for a `bail.count` that isn't a whole number of at least 1; the transport resolves the bootstrap), **all before anything reaches the bus, so a bad option never leaves reporters with a `run:start` and no `run:end`** → discover (`discoverProject`: `project.discovery` when the Jest reader gave rules, else `include`/`exclude`) and filter (`options.fileFilters`) → no files: `run:start`, `run:end`, an empty summary → `cache.prune` → sort → `run:start(RunInfo, files)` → `file:queued` per file in order → every file requested from the pool, then `pool.drain()` (workers retire as they go idle) → all files done → `cache.write()` starts and is awaited together with `pool.close()` (every worker has exited) → `run:end`. `planQueue` does prune, inputs, sort and queue. The worker entry defaults to `import.meta.resolve('@provino/orchestrator/worker/main')` (a string, not an import); `entry` overrides it.

- **If anything throws after `run:start`** (a bus that rejects; the reporter bus itself never does), the pool is closed, the bus gets `error(…, 'coordinator')` and then `run:end` with `reason: 'failed'` and the files that had finished, and the error propagates. A failure of that report is a line on `stderr`, and the original error still propagates. A throw before `run:start` (discovery, the pool) closes the pool and emits nothing.
- **`file:start` and `file:end` pair, always.** Every `file:start` is followed by exactly one `file:end`, and a `file:end` never comes without its `file:start` (the doc comments on `ReporterEvents` say so, and `test/coordinator.test.ts` asserts it with a recording reporter). A file goes `file:start(file, workerId)` when a worker takes it, its own events, then `file:end`. A file whose worker failed to start has no worker that took it, so `file:start` comes right before its `file:end` with the id of the worker whose failed start its error is (`PoolOutcome.workerId`; for the files left when the pool gave up, the last failed one). A file cut off by an abort after `file:start` gets `file:end` (`fail`, one `Interrupted` error naming the file) and is in `summary.files`; a file that had not started gets neither event and is not in the summary.

- **The pool owns the queue.** `run(request)` never rejects and resolves a `PoolOutcome` (`done`, `crashed`, `failed`, `start-failed`, `aborted`); waiting files are served in request order. A worker is started only when a file waits and fewer than `maxWorkers` are alive, **counting workers that are still stopping** (the cap is strict). An idle worker with another key is retired to make room. `drain()` (`runProject` calls it right after it has requested every file) retires a worker as soon as it is idle with nothing waiting, so shutdown overlaps the files still running; without it the pool keeps idle workers for a next file, and `close` is what waits for every worker. The `maxWorkers` cap is also capped by `TransportFactory.maxWorkers`. After a file whose `fileDone.leakedGlobals` is non-empty the worker is stopped, not reused (`recycle.onLeak`, default on; D22), after `maxFilesPerWorker` files and after a file whose `fileDone.memoryBytes` is over `memoryLimitBytes` (RSS in a fork, the isolate's used heap in a thread, never `external`: oxc-parser's raw transfer buffer is a 6 GiB `ArrayBuffer`, so a thread of 150 MB reads about 6.4 GB of it; an inline worker, `sharesProcess`, is never replaced for memory: it measures the coordinator, which no replacement frees, as with Jest's `--runInBand`); `runProjects` defaults the limit to `defaultWorkerMemoryLimit(maxWorkers)`, `max(512 MiB, 25% of process.constrainedMemory() (never above the machine's memory, which it is without a cap: a cgroup with no limit reports about 2^64) / maxWorkers)`.
- **Crashes and starts.** A worker that exits mid-file (`ORCH_WORKER_EXITED`, the `WorkerExit` as `cause`) fails that file: `FileResult.workerExit` plus one `WorkerCrash` error (`The worker running <path> exited: <describeExit>`). A worker that fails to start fails the file it was taking (with `workerExit` when the cause is an exit or a start timeout), and that file is not retried. After three starts in a row fail, the pool starts no more workers, but it **gives up only when no worker is alive or still starting**: files left wait for the workers that are, and a start that works resets the count. Once none is left, every file still waiting gets the last failure's error (and its worker id), with no more attempts. A handler that throws (`ORCH_BAD_EVENT`, or a reporter bug) is `failed`: the file fails with that error and the worker is replaced, since its state is unknown.
- **The lifecycle (B21a, T9.5's rest and T9.10).**
  - **A file's deadline** (`fileTimeoutMs`, off by default, ours: Jest has none): a timer starts when the job is sent and, past it, `terminate(true, { phase: 'file', limitMs })`. The transport reports `{ type: 'timeout', phase, limitMs }` as it does the start and stop timeouts, and `describeExit` is the one place that words it ("killed for running past its deadline of N ms"). The worker then takes no file, so a `fileDone` landing in the same turn keeps its result. An inline worker can't be killed for a synchronous hang.
  - **An OOM** is a fork whose exit is SIGABRT after V8's "heap out of memory" line: `{ type: 'oom', limitMb }`, the limit from `memoryLimitMb`, else its `--max-old-space-size`, else V8's default (`oomExit`, shared with threads). Only a SIGABRT waits for stdio to close (its exit is read from the last of stderr); any other exit is reported on exit plus IPC disconnect, so a grandchild holding the pipe doesn't cost the 1 s grace (`reportChildExit`). `stderr-watch.ts` keeps a sticky flag per chunk, not a tail: V8 prints about 8 KB of native stack after the line. Without it a SIGABRT stays `{ type: 'signal', likelyOom: true }`; a thread's `ERR_WORKER_OUT_OF_MEMORY` is `oom` too. `RunPoolOptions.heapLimitMb` sets it for both.
  - **`bail: { count }`** counts failed tests (a `test-end` of state `fail`) across files. Under `orchestrator.bail.checkAfter: 'file'` (Jest) the count is made in `FileRequest.onDone`, which the pool calls before the worker takes another file, so no file starts after the one that reached it; the queue is cancelled (`cancelQueued`) and the pool closed, which kills the files running. **Those get no `file:end` and are not in the summary**, as Jest reports a killed file no further: the one exception to `file:start` having a `file:end` (a running file can't be cancelled before T5.12). Under `'test'` (Vitest) the count is made at each failing `test-end`, the queue is cancelled and the running files go on to their end, reported whole. The run ends `failed`. A file that fails to load or crashes its worker is not a failed test and adds nothing to the count, as in Jest (`cli/bail-on-load-error`; TestScheduler's check reads `numFailedTests` alone).
  - **Signals.** `RUN_SIGNALS` (`exit-code.ts`) is the one table: each signal's summary `reason` and exit code (`SIGINT` `interrupted` 130, `SIGTERM` `terminated` 143, `SIGHUP` `hangup` 129; a test checks the codes as 128 plus the signal's number). A `signal` aborted with one of the names (`isRunSignal`) ends the run that way, any other abort is `interrupted`, and one that lands after the last file (the pool closing, the cache write, the handle collection) still counts. `forceSignal` (a second Ctrl+C) kills every live worker, those in a graceful stop included, so `close` doesn't wait out `teardownTimeoutMs`. For an inline worker it gives up on the running file (`aborted`) and on its wind-down; code looping synchronously in-process can't be interrupted (the bin's exit timer ends the process). The bin owns the handlers (`provino`'s `signals.ts`).
  - **`detectOpenHandles`** puts the files in the inline pool (async_hooks sees this process only) and, after the last worker has stopped, `RunSummary.openHandles` holds each resource that is still alive and holds the loop (a Timeout that is `unref`'d doesn't), with its creating stack, innermost first, from the user's files only (under a project root, not `node_modules`, not Provino's own packages), and Jest's code frame. Handles with the same stack are one entry, kinds joined by `,`. The hook runs with `trackPromises: false` (an `await` costs several times more otherwise; Node before 22.15 ignores it). A TypeScript test file's frames are mapped through the transform's source map, as `.stack` maps them: `callSites` applies the mapper the worker's formatter carries (`provino.mapCallSites`, `@provino/loader`'s `stacks.ts`) to the sites it captures while that formatter is swapped out, so the frame and its code frame are Jest's (`3:3`, where the transformed code's tab made it `3:2`).
- **Abort.** `signal` aborting (or `close`) resolves waiting files `aborted`, force-kills a worker running a file, and stops the rest. `runFile` knows whether the file had started (`onStart` ran): if so it ends with a `fail` result (`Interrupted`) and a `file:end` and is in `summary.files`; if not it is dropped silently. The run's `reason` is the signal's (`RUN_SIGNALS`).
- **A file's result** is its `file-end`: `pass`/`fail` as sent, `skip`, `todo` and `queued` as `skip` (nothing ran) unless a test of the file ended `todo`, when the policy's `todoOnlyFile` decides (`pass` under Jest, which marks a suite skipped only when every test is pending, DV50; the neutral and Vitest value is `skip`), `running` as `fail` (never finished). `stateOf` decides it once, so the reporters, the results cache (which does not remember a `skip` file) and `normalized-json` agree; `createFileDispatch` counts the tests that ended `todo` (`todo`). A `fileDone` with no `file-end` fails the file. `summary.files` is in queue order, not completion order. `summary.unhandled` holds **every** unhandled error of the run, including ones tied to a file (the default reporter prints them at `run:end`); with policy `unhandledErrors: 'fail-run'` any of them makes `reason` `failed`. A file's `FileResult` does not turn `fail` for one.
- **Dispatch** pairs each `RuntimeEvent` with its node from the file's `file-collect-end`, awaits `bus.emit` inside `onEvents` (so a slow reporter holds the ack and the worker waits), and throws `ORCH_BAD_EVENT` for an id it never saw or a node of the wrong kind. `file-collect-start` and `file-end` have no bus event; the `coverage` event is ignored for now, and a `deps` event is rebuilt into `FileDispatch.deps` (T9.12 reads it). What a worker sends while it runs no file (a worker-scoped environment's stop) goes to `createIdleDispatch`: `console` under the file the worker ran last, unhandled errors as `unhandled(null, …)`. Because `drain()` stops a worker as soon as its last file is done, `runProject` holds those events back until that file's `file:end` has been emitted, so they still arrive after it.
- **The cache** is read synchronously when it is created, for `get`; a missing, unparsable or other-version file (or entry) is empty, never an error. `write()` **reads the file again**, drops what `prune` did not keep, puts this cache's own `record`ed entries on top, and writes a temp file plus a rename, so two runs that overlapped keep each other's history (two writes in the same instant can still lose one: the history is a hint for the order, not a ledger). `runProject` calls `prune(project, <every discovered path>)`: discovery is unfiltered, so any other file's history is stale. **A filtered run prunes against the whole discovered set, not the filtered one** (`planQueue`): the history of the files it left out stays. A run that finds no files neither prunes nor writes. A file that is `skip`, interrupted or whose worker never started is not recorded. A failed write is a line on `stderr`, not a failed run.
- **Worker `t` clocks differ.** Each worker's events carry its own `performance.now()`, comparable only within one worker (`RunInfo.startTime` is the coordinator's).
- **`CoordinatorMethods`** served to workers: `readTimings` returns the cache's duration. Snapshots have no RPC: the worker resolves the path and writes the `.snap` itself (build-plan §6), and the inline-edit RPC is T7.11's.
- **Snapshots in a run (B17b):** `runProject` resolves the update mode once (`resolveUpdateMode`: `RunProjectOptions.update` for `-u`, `project.config.ci`, `env` for the policy's variable) and puts it on every `FileJob.updateSnapshots`; it adds each `fileDone.snapshot` to a `createSnapshotAggregate` (Jest's `addResult` sums) and puts the result in `RunSummary.snapshots`, and `reason` is `failed` when `snapshotRunFails` says the obsolete snapshots fail the run (`snapshot.obsolete`, by mode: `failCI` under `none`, `failLocal` under `new`, never under `all`). `exitCodeFor` returns `exitCodes.failure` for it, after a failed file.
- **`exitCodeFor`** tries, in order: a run a signal ended (`RUN_SIGNALS`), no files without `passWithNoTests` (`exitCodes.noTests`), a failed file (`failure`), an unhandled error under `fail-run` (`unhandled`), a reporter failure (`failure`), else 0. It takes the whole `Policy`, which the orchestrator may.
- **An internal error in Provino exits 1, the same as a test failure** (a documented choice, as Jest does it): Track 9's `ExitCode` has no internal-error value, so a `runProject` that rejects (`ORCH_NOT_IMPLEMENTED`, `ORCH_BAD_PATTERN`, a bug) is the caller's to turn into exit code 1. `exitCodeFor` only ever sees a summary.

## Sharding and the timings file (T9.6, B21d)

- **`--shard=i/n`** (`RunProjectOptions.shard`, `provino run --shard`, Jest's own flag under `provino jest`): applied after discovery and the file filters, to the one list of every project's files, as Jest does (`runJest` shards `allTests`), before the order. The results cache is pruned against the whole file set, so the history of the files a shard leaves out stays. A shard with no file ends as a run that found none.
- **Two splits, both pure in (files, shard, timings).** `sha1Shard` is `TestSequencer.shard` (jest-test-sequencer 30.5.2, Vitest's `BaseSequencer` agrees): sort by `sha1` of the path relative to the project root, take contiguous slices by count, the first `length % count` one longer (recorded: `cli/shard-1-of-3` to `-3-of-3`). `sliceShard` sorts by path (then project) and puts each file in shard `floor(count * middle / total)` of its own span of the cumulative predicted time (Bun's method: neighbouring files share a shard, so per-shard caches stay warm). A file with no time counts as the median of the files that have one, and with no time at all every file counts the same, which is slices by count. `shardInputs` picks: any file with a time (`ScheduleInput.timingMs`) means `sliceShard` for every dialect, else the policy's `orchestrator.shard.fallback` (`sha1-slice` for Jest and Vitest, `path-slice` neutral). Every file lands in exactly one shard for any input order (`shard.test.ts`, a seeded property test). Two projects' files with one relative path hash alike: the project's place in the config breaks the tie (`shardFiles` numbers its members; never a name or an identity: an unnamed project's identity holds the run's random seed, so each shard's machine would break the tie its own way), which Jest leaves to its crawl order, the same order. `provino jest --listTests --shard` calls the same `shardFiles`.
- **`provino.timings.json`** is `{ "version": 1, "files": { "<path>": <ms> } }` (Bun's shape), keys relative to the run's root (so unique across projects), read from the run's root or `RunProjectOptions.timings.file`. It is read only when the run shards or updates. **A file that is there and wrong stops a sharded run** (`ORCH_BAD_TIMINGS`, exit 2): shards that read it differently would lose test files. A missing file is no timings. `--update-timings` (`timings.update`) writes after the run: each file that ran to its end (`outcome: done`; a crash, a kill and a failed start say nothing about a duration) with its time in whole ms, merged over what the file held (the entries of files that did not run to their end stay), keys sorted, a temporary file and a rename. A run with no file filter also drops the entries of files that are gone. A write that fails is a line on stderr, not a failed run. **A run with `-t` writes nothing** (a line on stderr says why): only the matching tests of each file ran, so its durations are not the files' and would skew the next shard. `--update-timings` over a file that is not one replaces it (with a line saying so). **`--update-timings` together with `--shard` is `ORCH_BAD_OPTION`**, checked beside the shard itself before anything runs (exit 2 under `provino run`, Jest's usage code under `provino jest`): shards that run one after another in one checkout would each read the timings the last one wrote, switch from the dialect's split to cuts by time half-way, and run some files twice and some never. Refresh the timings file on an unsharded run, then commit it for the shards to read.
- **The numbers** (`schedule-sim.test.ts`, `local`, 40 seeded trials, 1,000 files, 4 shards of 2 workers, ordered as the sequencer does): the sha1 split's slowest shard +11.0% over ideal (spike +11.8%), contiguous cuts +6.7% (spike +6.2%); the sha1 split moves 0.7% of the files when 5% more appear (spike 0.7%); Jest's order +0.2% over the LPT bound at 150 files. **Not reproduced, and not asserted (Tyler closed T9.6 on the medians, 2026-11-13):** the "worst of 40" figures (each is one random draw, and the spike's seeds are gone; only "contiguous is better than sha1" is held) and the churn of the contiguous cuts and the LPT bin-pack (the doc does not say where the new files sort: contiguous 0.3% with random new paths and 3.2% with paths sorted last against the spike's 2.8%, LPT 40.9% and 33.7% against 64.6%). The churn tests assert only what holds under both readings: the contiguous cuts, and the sha1 split, move far fewer files than the LPT bin-pack (`schedule-sim.ts` has it as a baseline, nothing ships it), trial by trial. sha1 < contiguous holds only with the new paths sorted last, so it is not asserted.

## The isolation tier of a file (T2.11, B21d)

`runProjects` asks `tierFor` (`@provino/loader`) for each file it queues: the project's tier, raised by the file's `@provino-isolate` docblock (`readIsolatePragma` reads the first 4 KiB, no pragma costs one `includes`) or by the tier the results cache learned (`FileHistory.tier`); never lowered; a value that is no tier is a `Provino: warning:` line on stderr. A project whose tier is already `process` reads no docblock. The tier is part of the worker key (`WorkerKey.isolation`, and `WorkerInit.isolation` is the key's): a file at another tier gets a worker booted at that tier, and the pool retires a `process`-tier worker after its one file, so a `process` file always has a fresh process (or thread, or inline worker). A tier the loader doesn't build yet (`realm`, T2.8) fails the file naming that task.

## Global setup (T9.15)

`runProjects` calls `runGlobalSetup` once the files are known and **before the reporters hear `run:start`** (Jest's order: its reporters start inside the scheduler, after `runGlobalHook`), only for the projects that have a file to run. It imports each module with the loader in coordinator mode (U5: `import('@provino/loader')` when the first hook runs, so a run with no global setup never loads it; one `createCoordinatorLoader` per project, from `member.project.config.loader`, which carries the transform cache directory) and calls it as `policy.orchestrator.globalSetup.signature` says. The manifest allows the coordinator node to import the loader (D74).

- **Once per distinct path**, project by project in the order Jest's one sorted list of every project's files reaches them (`sequencedProjects` in `run.ts`: the sequencer over all the files with each project's history, through the `scheduleInputOf` and `sequencerFor` the queue's own `planQueue` uses; it is worked out only when some project that has a file, or the run itself, names a hook and more than one project has files, since that order only decides the hooks'; the queue itself stays project by project), then **the run's own hooks** (`RunProjectOptions.globalSetup`: Jest's root `globalSetup` and `globalTeardown`, which `provino jest` passes from the global config; a path no project names, called with the first project's config, as `runGlobalHook` falls back to `allTests[0]`). The module is loaded with the first project that names it, in that order, and that project's `projectConfig` is what a path several share gets. Recorded: `cli/global-setup-root-projects` and `cli/global-setup-sequence` (the larger test file's project is first, so the order differs from the config's).
- **`global-and-project-config` (Jest):** `callJestHook(hook, path, project)` imports the module and calls its function, both inside one `guarded` (so an import that fails, a module that exports no function and a hook that throws are reported the same way). The function is the module's `default` (`interopDefault` from `@provino/config`: also a `__esModule` default under `node` interop); `fn(globalConfig, projectConfig)` from `ResolvedGlobalSetup.args` as the reader built them (no JSON and no revival: they never leave the coordinator, so Jest's `TestPathPatterns` object and a transformer's function arrive whole, the same objects to a project's setup and teardown), `{}` each when the reader gave none. A module that doesn't export a function is `<hook> file must export a function at <path>`. Each `globalTeardown` path is imported when the teardown runs, as Jest does.
- **`project-with-teardown` (Vitest, and the neutral default):** `default` or a named `setup` is called with `{ provide, onTestsRerun, project: { name, root } }`; a function it returns, or a named `teardown` export, is its teardown. `provide` collects what `WorkerInit.provided` hands every worker (a value `structuredClone` refuses is a `TypeError` naming the key); `inject` is T11.16's. `onTestsRerun` keeps the callback for the watch loop (T9.11). No config reader gives a neutral project a `globalSetup` yet: the paths are tested with hand-made projects.
- **Teardown** runs after `run:end`, in a `finally`, in the order `teardownOrder` says (`in-order`: Jest, recorded by `cli/global-setup-projects`; `reverse`: Vitest's, from its source). That is Jest's own place: `onRunComplete` (the summary) is dispatched inside `scheduleTests`, and `runJest` runs `runGlobalHook(globalTeardown)` after it, so a teardown's output and its failure come below the totals (recorded: `cli/global-teardown-output`, `cli/global-teardown-throws`). It runs when the run was interrupted or threw too, so a SIGINT tears down (Jest dies without; Track 9's T9.9 asks for this). A teardown that throws doesn't stop the later ones (Jest stops at the first): the first error is thrown after all ran, and fails a run that ended well, while after a failed run it is a line on `stderr`.
- **Signals (`GlobalSetupOptions.signal`, `forceSignal`).** A run already interrupted when the setup would start sets nothing up (it still announces `run:start`, then ends with the signal's reason). Each setup is raced against the signal (`raceAbort` over an `AbortSignal.any` of the run's two): a hook that hangs can't be cancelled, so it is given up on, the run ends with the signal's reason, and what had set up is torn down: the functions setups returned, not a Jest teardown module, whose pairing with a setup is not ours to guess (as when a setup throws). A teardown running when the signal comes is given up on and the next one starts; one that begins after the run was already interrupted gets its time, and only the force signal (second Ctrl+C) cuts a hanging one short and skips the rest. A hook that holds the event loop open keeps the process alive after the first signal until the second (`afterRun`'s handlers end it).
- **A hook that throws** rejects with `ORCH_GLOBAL_SETUP_FAILED`. What it throws is handed to the policy's `globalSetup.failure` behaviour (`GlobalSetupFailure`, through the behaviour loader) with the hook and the path, and the `Error` it returns is the error's `message` and its `cause`. Jest's (`@provino/dialect-jest/global-setup`, a leaf the coordinator loads instead of the worker's whole `/runtime`) rewrites an `Error`'s message in place to `Jest: Got error running globalSetup - <path>, reason: <message>` and returns it, class and frames kept (`cli/global-setup-throws`, `-typeerror`), and for any other value, or a message that can't be rewritten, returns a new `Error` with the value as pretty-format prints it at depth 3 (a thrown object is `Object {`, a string is quoted; `-object` and `-string`) and a stack that is its header alone. The neutral behaviour (and Vitest's, until T11.16) is `<hook> <path> failed: <message>` with the thrown error as `cause` and its frames under the header. `hookFailureReport(error)` is what `provino` prints, and has no rules of its own: the cause's `<name>: <message>`, then the lines of the cause's stack that are `    at ` frames, so a message that runs over lines is not shown twice. It happens before `run:start`, so reporters hear nothing and no file runs; `provino` prints it and exits with the runner's failure code. When a later setup throws, the teardowns of what had set up (functions a setup returned) run first; a Jest teardown module is not run then, as Jest runs none.
- **`deps` events (U5).** The runtime runner reads `registry.loadedModules()` before the teardown empties the registry and returns it as `FileOutcome.deps`; `startWorker` queues one `deps` event (`{ fileId, added, ids, t }`) before `fileDone`. **Each path crosses the link once per worker** (a file that loads 1,500 modules was 93 KB of paths and about 364 µs of clone `local`; 18 KB and 39 µs at 300): the worker interns every path (`interned`, per `startWorker` call) and sends `added`, the paths it had not sent, and `ids`, one number per loaded module in the worker's order, so `ids` is always as long as the list and `added` is empty for a file that loads nothing new. The coordinator keeps one `DepsTable` per worker (`src/deps-table.ts`, `run.ts`'s `depsTables` by worker id; a replaced worker starts empty) and `createFileDispatch` rebuilds the list into `FileDispatch.deps` (`undefined` until the event arrives). The table takes `added` in even though nothing reads the list yet, because the next file's ids refer to it; an id the worker never named is `ORCH_BAD_EVENT`. T9.12's affected-test selection reads `FileDispatch.deps`.

## The transform cache (T3.6)

`runProjects` gives every member `withTransformCache(project, transformCacheDir(rootDir))` unless `options.cache === false` (`--no-cache`): `<rootDir>/node_modules/.cache/provino/t` (or `<cacheDirectory>/provino/t` when the project's config set one, `ResolvedProject.cacheDirectory`, D70; `defaultCacheDir(rootDir, cacheDirectory?)` decides), under the results cache's directory. That wipes the directory when the lockfile hash changed (before any worker starts), and puts `loader.cacheDir` in the project's `WorkerInit.config` (`parseProjectConfig` checks it is absolute). After the run, `writeCache` prunes each distinct directory to 512 MB. Workers only read and write entries.

## Several projects (`runProjects`, D29)

One pool, one bus, one `maxWorkers` (the cap counts every project's workers), one `run:start` and `run:end` (`RunInfo.projects` lists every name, `RunInfo.root` is `options.root` or the first project's). Per project (a `Member`): its results-cache key and cache (default: one per root directory; a cache passed in is shared), its update mode, and its `WorkerKey`. **A worker is bound to one project at `WorkerInit`**: `WorkerKey.project` is the project's name, or `name#hash` (`projectCacheKey`) when another project of the run has the same name, with `@<index>` added when even that collides (two unnamed projects with the same discovery inputs but a different environment, setup or transform: each keeps its own worker config and file ids). The pool counts **start failures per worker key** (three in a row end that key's starting and fail only its waiters; other keys' files go on). When two projects run the same file (same root, same match) each gets a `runPath` `<path>#<identity>` so normalized-json ids stay unique. Each project's snapshots are judged by its own policy and update mode (`snapshot-members.ts`; `RunSummary.snapshotsFail`, with `snapshots` the merge for display). A project with no `seed` gets one the run draws, shared by every worker (`jest.getSeed()`). and the pool's `init` finds the project by it (config, isolation), so a file goes only to a worker of its own project. Files are queued **project by project in the config's order**, each project's by the sequencer, so a worker changes project at a boundary and not on every file; a worker whose project has nothing left is stopped when idle (`drain`) or retired to make room for another project's file (the pool's existing rule). File ids use the same identity (`fileIdOf(identity, path)`), so two unnamed projects with the same relative path get different ids; with one project it is `project.name`, as before. `FileInfo.runPath` (set only when it differs from `path`) is the path from the run's root, which `normalized-json` writes so two projects' `a.test.js` stay two files. Run-wide values (pool kind, `unhandledErrors`, the snapshot summary's mode, the exit policy) take the first project's. `ORCH_NO_PROJECTS` for an empty list. `test/projects.test.ts` runs it over forks.

## Rules that aren't obvious

- **Environment pragmas, `globals` and the resolver keys (B17c).** `runFile` reads the file's leading docblock (`internal/runtime/pragmas.ts`, `jest-docblock`'s extract) and passes it as the environment's `pragmas`. A value for one of `policy.orchestrator.environmentPragmas` (`jest-environment`) picks the file's environment: `config.environmentResolver` (the dialect's `ModuleRef`, loaded once) turns the name and `<pragma>-options` (JSON) into an `EnvironmentRef`, prepared once per kind (ref plus options) per worker and cached in `parts.pragmaEnvironments`. Under isolation `none` the worker keeps one environment instance and its kind (`workerEnvironment.prepared`): a file that wants another kind tears the current one down first (its leaked globals are reported as the worker's) and sets the next up, so each environment is on the global only while its own files run (`provino/test/env-docblock-none.test.ts`). Modules cached under `none` keep what they captured. `config.globalValues` (Jest's `globals`) is defined on the environment's global, copied for each file, before anything else. `loader.aliases`, `moduleDirectories`, `modulePaths` and `resolver` are validated by `parseProjectConfig` (T3.3).

- **Globals come in around `setupFiles` by `core.globalsBeforeSetupFiles`** (B14a). The worker splits the dialect's globals once (`splitGlobals`): the listed names (or all, under `'all'`) are installed with the environment, the rest after `setupFiles` and before `setupFilesAfterEnv` (`FileScope.installLateGlobals`, called from `importFile`). Jest 30.5 lists only `jest` (`policy/core-globals-at-setup`; the bench's worker test runs those files and traces what the golden traced). Under `none` the environment persists, so a later file's `setupFiles` still see the earlier file's late globals: a DIVERGENCES limit.
- **Setup files are fresh for every file, in every tier, and so is the test file.** Under `none` the registry is shared, so the setup module and the test file itself (queued twice, or imported by an earlier file) are invalidated and imported again (their dependencies stay shared); `isolateModules` would re-instantiate those too. They run inside collection, so a hook they register belongs to the file, and a throwing one fails the file with no tests.
- **Back-pressure is per file, not per test:** a file waits for `sink.writable()` before it starts, which bounds the worker's buffer to about one file's events beyond the 8-pack window. A per-test wait would need an async hook in core's executor (T5.8).
- **The behaviour loader keeps its default importer; D21 is checked in the config, not at import.** `parseProjectConfig` enforces absolute refs for the environment, the globals, the mappers and the paths, and for **every behaviour ref in the policy**: it walks `policy` for `{ module, export }` refs (a dialect's, and `neutralPolicy`'s own) and throws `ORCH_BAD_CONFIG` naming the key path, such as `policy.core.formatEachTitle.module`, for a bare specifier or a relative path. `neutralPolicy` writes its three refs (`core.formatEachTitle`, `snapshot.key`, `orchestrator.environmentConditions`) with `import.meta.resolve('@provino/policy/behaviours')`, a `file:` URL (the package names itself through its `exports`, which works under `--conditions=provino-source` and once built), so a worker needs no package resolution to load any of them. The importer itself stays the default one: a `WorkerError` thrown from `importModule` would reach the caller wrapped in a `POLICY_BEHAVIOUR_LOAD_FAILED`, and the config check names the key instead.
- **A path in the config that crosses is absolute.** `environment.module`, `globals.module` and each mapper factory's `module` are an absolute path or URL (`file:` from `import.meta.resolve`); `rootDir`, `setupFiles`, `setupFilesAfterEnv` and a path `loader.tsconfig` are absolute paths. A bare package specifier or a relative path is `ORCH_BAD_CONFIG` naming the key, because the worker would resolve it from this package or its own working directory, not the project. B11's coordinator resolves them.
- **`none` keeps everything:** the environment, the globals, the custom matchers (`snapshot.restore()` is file scope only, as in Vitest's `isolate: false`) and the registry. They go at `stop`.
- **`FileJob.collectOnly`** (B23a) imports a file and runs no hook or body (`--collectTests`); the worker installs the loader's source-mapped stacks with `policy.module.stackFrameNames` (`mapped-name` under the Jest dialect: DV88).
- **`FileJob.fileId` is the coordinator's id (D23).** The coordinator entry exports `fileIdOf(project, relativePath)`: SHA-1 over `<project>\0<POSIX relative path>`, 10 hex characters (the formula `@provino/core` uses when it runs standalone, which `test/file-id.test.ts` checks). The runner hands `job.fileId` to core's `runFile`, and every event and task id of the file derives from it. The worker node cannot import the coordinator entry, so it never computes one; the bench and `test/support.ts` import `fileIdOf` and pass the path relative to the root.
- **A fork's exit is reported after `exit` *and* the IPC `disconnect`.** `exit` can arrive before the child's last messages are read, so closing the link on `exit` would drop them. A 1 s fallback covers a grandchild that holds the channel open. That's also why `childProcessLink` closes on `disconnect`, not `exit`.
- **A child's `processLink.close()` waits for queued writes** before it disconnects, because a disconnect cancels pending IPC writes, `stopped` included.
- **Links queue while nobody listens** and hand the queue, in order, to the next listener. The handshake listener unsubscribes on `ready`, and nothing after it is lost.
- **A timeout overrides the raw exit.** A worker killed after the start or teardown timeout reports `{ type: 'timeout', phase }`, not the signal used to kill it.
- **An inline pool runs one worker.** The inline transport declares `TransportFactory.maxWorkers: 1` (`--runInBand`) and `createPool` caps `maxWorkers` by it, whatever the caller or `defaultMaxWorkers()` says: the expect slot is process-global, so a second inline worker's boot fails with `EXPECT_SLOT_TAKEN`. (The pool's tests drive fakes that declare no cap.) Two inline runs overlapping in one process share that slot and are not supported; use forks or threads.
- **A worker still starting is cancelled.** `TransportFactory.create(init, signal)`: the pool passes a signal it aborts on abort/`close`; the handshake then clears the start timer, SIGKILLs the worker (an inline one loses its link) and rejects, which the pool maps to `aborted`. Nothing waits for `ready` or the start timeout.
- **A worker that ends badly while it runs no file is an error of the run.** After the pool's own abort kill is excluded, an exit other than `{ type: 'exit', code: 0 }` of an idle or stopping worker (a crash, `process.exit(1)`, a teardown that hangs at `stop`: `{ type: 'timeout', phase: 'stop' }`) goes to the pool's `onError` as `ORCH_WORKER_EXITED` (cause: the exit), with `kind: 'worker-lost'` as the callback's second argument (`'other'` for any other error). `runProject` branches on that kind, and emits it as `error(…, 'coordinator')` and adds it to `RunSummary.unhandled`, so `unhandledErrors: 'fail-run'` fails the run. Known gaps: a worker that dies just after its `fileDone` has its crash charged to the next file it was handed (no retry policy yet); `RecyclePolicy.onLeak` covers leaked handles per its doc, but only `leakedGlobals` is checked until T2.7.
- **Worker stdout.** `RunProjectOptions.stdout` is where forks and threads have their stdout copied (default: the process's); `provino` passes its `stderr`, so `--json` on stdout stays clean. An inline worker shares the process, doesn't capture console (B09's rule) and so a test's `console.log` or `fs.writeSync(1, …)` still reaches the process's stdout.
- **Inline workers don't patch globals.** Console capture installs on `globalThis.console` and `process.stdout`/`stderr` only when `init.key.pool !== 'inline'`: an inline worker shares the coordinator's stdio, and `node:test` reports over it. Inline runners use `context.console`; tests pass stand-in streams. The real runtime hands `context.console` to the environment's `setup` but does not install it itself, so a test's `console` in an inline worker prints to the coordinator's stdout (forks and threads capture it through the patched global).
- **The worker takes its timers at load** (`worker/timers.ts`), so fake timers installed by a test file can't stall a flush or the end-of-file yield.
- **Stdio is flushed only when bytes are buffered** (`writableLength > 0`). With capture installed nothing reaches the real stream, and in a thread an empty write's callback waits on the coordinator's event loop.
- **A pack that won't send never throws.** It goes again with each unclonable event replaced by an `unhandled-error`; the window and pack numbers stay intact.
- **No coalescing.** Every `RuntimeEvent` is a transition reporters see (§6's one event model). The brief's "coalesce per task" came from Track 9's retired `task:update` shape (DECISIONS P4).
- **`WorkerMethods.memoryUsage` replaces `Transport.memoryUsage`.** A parent can't read a forked child's RSS, so the worker measures itself: RSS in a fork, `v8.getHeapStatistics().used_heap_size` (the isolate's own heap, as jest-worker's `process.memoryUsage().heapUsed`) in a thread or inline. RSS is the whole process's in a thread, and `external` counts reserved `ArrayBuffer`s, not memory held. `test/coordinator.test.ts` runs real threads under the default limit and checks one worker serves every file.
