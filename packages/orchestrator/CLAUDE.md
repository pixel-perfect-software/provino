# @provino/orchestrator

The coordinator (`.`) and the worker entry (`./worker`), as two manifest nodes in one package. They never import each other: shared types come from `@provino/types` and shared runtime code from `@provino/rpc`. B09 built the transports, the per-worker connection and the worker-side packer. B10 built the worker runtime (U1): `./worker/main`, the entry that wires the loader, the environment, the dialect's globals, `@provino/expect` and `@provino/core` behind `startWorker`. B11 built the coordinator's run: discovery, the results cache, the sequencer, the pool, event dispatch, `runProject` and the exit codes (see "The coordinator"). B21a added the run lifecycle (T9.5's rest, T9.10: see "The lifecycle"). B23c added the watch session (see "The watch session"); Jest's watch loop comes later (see "Not built yet").

## Module map

The module map (every file, what it exports and which half runs it) is in [`NOTES.md`](NOTES.md), section "Module map". Read it before moving or adding a file.

## How a worker runs

1. The transport spawns `bootstrap.ts` and passes the entry module URL: `argv[2]` for a fork, `workerData.entry` for a thread. Inline has no bootstrap: the transport imports the entry itself and builds the port over a `MessageChannel`.
2. The entry's default export (`WorkerMain`; `./worker/main` for the real worker) gets a `WorkerPort` and calls `startWorker`. That sends `ready`; the transport answers with `start` and only then resolves `create()`. The `start` send is the one check that the init can cross: a value the link can't write kills the worker and rejects with `ORCH_BAD_INIT`.
3. Each `run` gets a fresh console, goes through `runner.runFile`, then yields one macrotask (every microtask the file left behind runs, so a floating `.then` that logs is still in the file's output), flushes stdio, and queues `fileDone` with `packer.afterSent`. Every event emitted before that call precedes `fileDone`, by construction. A runner that throws (in `runFile`, or in `start`, which then fails every file) is charged to the file as an `unhandled-error`, and the file still gets its `fileDone`: no failure can stall the worker's queue. A `cancel` aborts the running file and every file already queued.
4. `stop` drains the queue, calls `runner.stop` (when `start` came; a throw is charged as an `unhandled-error` with no owner, and `stopped` is sent anyway), sends `stopped` and closes the link. The bootstrap then **exits on purpose** (`process.exit(0)`), after a fork's IPC disconnect, so a handle a test leaked can't keep the worker alive. If the coordinator dies, the link closes and the worker exits the same way.
5. **A link that closes before any `stop`** (the coordinator died, or `terminate(true)`) aborts the running and queued files and restores the console at once, then queues a best-effort `runner.stop`, whose errors and output are dropped (nothing can be sent). `startWorker`'s promise settles only after that stop has. It matters for an inline worker, which lives in the coordinator's process: without it the matcher slot, the loader and the environment stay installed. The runner marks its slots stopped as the link closes (`WorkerRunner.abandon`), so a next inline worker that boots before this stop has run refuses them with `EXPECT_SLOT_TAKEN` rather than adopting them ("A worker inside another worker's process" below). The stop queues behind the file running now, and `cancel` can't reach core until T5.12, so a file still running delays it. A fork or thread just exits.
6. **"The worker ended" is one definition for every kind: its `main` has settled and the link has closed** (the bootstrap does `await main(port); await closed`). The inline transport reports its exit on the same condition: when the coordinator's end of the link closes it waits for the entry's `main` promise, then reports `{ type: 'exit', code: 0 }` (or `code: 1` for a `main` that threw, which is printed to the `stderr` sink first). Because `main` settles after the best-effort stop, a `terminate(true)` (or any kill) of an inline worker does not return before that teardown has finished, even one that does real I/O, so the next inline worker in the process boots with the slot free. `kill()` closes only the coordinator's end; the worker hears of it as a `close` event on its port. **The wait is bounded** by the transport's teardown timeout (`teardownTimeoutMs`, default 10 s; `settlesWithin`): a `main` that can't settle (a file that can't be cancelled until T5.12 holds the stop behind it) is reported as it is once the bound passes, so `terminate` can't hang. A `terminate(false)` on such a worker waits that bound twice at most (the stop timeout, then this one after the SIGTERM).

## The runtime (`createRuntimeRunner`)

The environment and the dialect's globals load **by ref** (`config.environment`, `config.globals`), never by import: this node knows no dialect and no environment package.

- **One `parts` object.** `boot` fills it in as it goes (slot, loader, runtime, state source, prepared environment, globals, snapshot, tier and `scope`), `runFile` checks `isBooted(parts)` once (`ORCH_NOT_STARTED`), and `stop` takes the whole object and leaves `{}` behind, so a worker whose `start` threw half-way is undone and `stop` runs twice without harm. `scope` (`'worker'` under `none`, else `'file'`) is computed once from the tier; a worker-scoped environment is stored as `{ instance, name }`.
- **`start`, once.** Parse the config → one behaviour loader and one project loader (`createProjectLoader`) → source-mapped stacks (`installSourceMappedStacks`, `@provino/loader`; `stop` puts the formatter back after the loader is disposed) → expect in its documented boot order (state source, matcher registry, slot, the dialect's table, `createExpect`) → `createRuntime` with the assertion-count sink in front of the packer → the environment's `prepare` once → the globals factory once, if `policy.core.injectGlobals`, with a `RuntimeGlobalsHost` → **then** `snapshotRegistry(registry, expect)`, so a matcher the factory adds (`expect.extend`) is in the baseline each file's restore returns to, not a leak of the first file. A throw here fails every file with its code (`startWorker`'s `startFailure`).
- **`RuntimeGlobalsHost`** (`@beta`, exported from `./worker`) is `GlobalsHost` with core's `api` and the worker's `expect` typed. `GlobalsFactory` is bivariant in its host, so the compiler wouldn't catch a wrong host at the call; `packages/bench/test/worker-host.test-d.ts` asserts it is assignable to the Jest dialect's own host (the bench is the one package that imports both).
- **`runFile`, per job.** Wait for the packer's `writable()` (a cancelled file never starts) → the mock registry, then `loader.createFileRegistry(file, { tier, moduleMocks, moduleScope })` (`process` runs as `registry`; `realm` throws `LOADER_NOT_IMPLEMENTED` here, before anything is set up) → environment `setup` (scope `file`, with the file's `signal`; scope `worker` under `none`, set up once for the first file, with `testPath` that file's path and a worker-lifetime `signal` the runner aborts in `stop`; every context carries `processObject`, the policy's `orchestrator.processObject`, so the environment installs a copy of `process` for the file: see `@provino/env-node`) → install the globals `globalsBeforeSetupFiles` lists on `instance.global`, every file (the rest after `setupFiles`) → `source.startFile` → `runtime.runFile(file, { testNamePattern, testIds })`, whose `importFile` imports each of `setupFiles` and then `setupFilesAfterEnv` and then the test file, inside collection (under `none` each of them, the test file included, is `invalidate`d first; the other tiers have a new registry, so they skip the extra resolver call) → teardown.
- **The fake clock (T4.9, B17a).** Each file gets `createFakeClock(instance.global, policy.timers, { bind: currentTest.bind })` once its environment exists, on the environment's global, and `host.timers()` returns it (read at call time, like `host.mocks()`; `host.timersPolicy` is `policy.timers`). `timers.enableGlobally` installs it before `setupFiles`; `SerializedProjectConfig.fakeTimers` is the `defaults` option. The host also gives the dialect `seed` (`SerializedProjectConfig.seed`, else drawn at boot), `environmentTornDown()` (`FileScope.tornDown`, true once the file's teardown ran, and for code with no file) and `setDefaultTimeout(ms)` (core's `Runtime.setDefaultTimeout`, cleared when the file ends). Teardown disposes it first (the real timers are back before the mock teardown and the environment's own check), under `none` too, since the environment outlives the file. A callback a fake timer fires runs in the context of the test that scheduled it.
- **Process errors (T5.11, B17a).** `boot` calls `coreRuntime.captureProcessErrors(process)` (the worker's real `process`, from `node:process`, for the worker's lifetime: inside an outer worker's file the global `process` is that file's copy, which nothing emits on; `stop` removes the listeners first), so an uncaught exception or a rejection with no handler is charged by `errors.lateErrors`. `startWorker` already yields one macrotask after `runFile`, with the clock back to real, which is when Node reports a rejection a file's last test left: core charges it then (a late `unhandled-error` event, before `fileDone`).
- **The end of a test (T7.8).** `boot` passes `createExpect` the core leaf `policy.core.unawaitedAsyncAssertion` (`expect` reads only its own slice) and `pollTimers.advance`, which moves the current file's fake clock (`(fileScope.getStore() ?? fallback)?.clock`, when `isInstalled()`), then registers `coreRuntime.onAfterTryTask` with `@provino/expect`'s `createEndOfTest` over `table.messages`, `policy.expect` and `policy.core.errors.hasAssertionsWhenFailed`. Soft failures, a missed `expect.assertions`/`hasAssertions`, `requireAssertions` and unawaited async assertions fail the attempt there. Core adds one error per thrown value, so several are thrown as one `AggregateError`. Tested in `test/runtime.test.ts` ("the end of a test").
- **The mock registry (B13a).** The worker owns a `MockRegistry` (`@provino/mock`), not core: a new one per file, or under `none` one for the worker, made for its first file ("`none` keeps everything"). `host.mocks()` returns the current one and is read at call time, like `host.registry()`; `host.mockPolicy` is `policy.mock`. Both stay in the worker (never `CloneSafe`-bound). **A file's async work keeps the file's registries.** `jest` is one object on a shared global, so a callback a file leaves behind (`setTimeout(() => jest.resetAllMocks())`) would find whichever file runs when it fires. The runner enters a module-level `AsyncLocalStorage` (`fileScope`, built at load like core's `currentTest`) holding `{ registry, mocks }` around `runtime.runFile`; `host.registry()` and `host.mocks()` read it first and fall back to one current-file `{ registry, mocks }` (`importFile`, the globals' setup and the teardown run outside it, and a callback that lost its async context, such as a native addon's, still needs it; keep it), and outside any file they throw `ORCH_NO_ACTIVE_FILE`. A second active store costs about 8 ns per await on Node 24 and about 20 ns on Node 22 (`local`, measured 2026-11-06), accepted over threading a context through core's `newStore` sites. A stale callback therefore acts on its own, by then disposed, registries and its `resetAll` is a no-op; under `none` the registry is shared and nothing changes. `stop` also clears the current mock registry, so `host.mocks()` throws after it instead of returning the disposed one. Remaining limit: a stale callback's `jest.spyOn` installs on its disposed registry, so it is never restored. **Cleanup between tests (T4.10, B17a)**: `boot` registers `coreRuntime.onBeforeTryTask(() => activeMocks().beforeEach({}, policy.mock.between))`, so the registry's `beforeEach` runs ahead of every attempt's first `beforeEach`, in the attempt's own async context, on the file's registry (read when it runs). The project's `clearMocks`/`resetMocks`/`restoreMocks` reach it as `policy.mock.between` (the Jest config reader maps them, so `provino jest` applies them, checked through the bin in `packages/provino/test/jest-mock-cleanup.test.ts`; `run()` has no key for them).
- **Snapshots (B17b).** `boot` loads the snapshot slice's behaviours once (the key function, the dialect's printer, a path resolver if the policy has one). `runFile` opens the file's snapshots after `source.startFile` (`openFileSnapshots`: the `SnapshotState` and the lifecycle), puts the state in the file state (`snapshotState`), and the sink in front of the runtime hands every event to the lifecycle first (`observingSink`). `importFile` adds `policy.snapshot.serializers` through the file's registry before the setup files. After `runtime.runFile` the lifecycle finishes (obsolete settled, `.snap` saved) and the report goes out as `FileOutcome.snapshot`, left out when it says nothing. A header the policy can't read or a file that never collected writes nothing.
- **The module-mock registry (B13c).** `boot` makes the module-mocking pieces once (`parts.modules`: the policy, `roots` `[rootDir]` until B14c, the loader's extensions, and `createRootMockIndex` over them, so the root `__mocks__` trees are listed once per worker), and, when `config.moduleScope` is a ref, loads the dialect's module-scope factory and calls it once with the same host the globals get (`parts.moduleScope`; it exists whether or not globals are injected, and serves the imports; the bindings a wrapper declares are `config.loader.moduleScope`, empty when `injectGlobals` is off). `runFile` hands `createFileRegistry` a `moduleMocks` factory that builds the file's `ModuleMockRegistry` (`createModuleMockRegistry` over the policy's `module` and `mock` slices, the file's mock registry, and the loader's own resolver, conditions and `loadActual`) and `moduleScope`. Every tier gets one per file, `none` included (B13c Gap 9). `host.moduleMocks()` returns the current file's, read at call time like `host.registry()`. `config.loader.hoist` (the dialect's, by value) reaches `createProjectLoader`.
- **Externals evaluated per file (D127, P42).** Under `module.reevaluateHookingExternals`, `boot` reads the global's own string keys and descriptors before any environment exists (`external-probe.ts` `readGlobalBaseline`), and gives the loader a watcher (`watchExternalLoads`; it returns `null`, watching nothing, when no file is running or its environment is torn down): while one external's first native load runs during a file, every configurable key whose descriptor differs from the baseline (an accessor by its getter alone: each environment's per-file snapshot wraps the setters of `Buffer`, `performance` and Node 26's `localStorage`, which puts nothing per file there) (the dialect's globals, a setup file's assignments, the environment's self-references; never `process`, a per-file copy nearly every package reads for `NODE_ENV`) is an accessor that notes a read or write; when the window closes each is put back (a key the load redefined itself is left). An accessor and a read-only data key get their exact descriptor back and the stand-in has a setter only where the original had one (a write to a read-only key still throws in strict code); a writable data key gets its descriptor with the value it holds now. A non-configurable key can't be watched and is left as it is. **The environment's populated keys are not redefined:** an `EnvironmentInstance.globalReads` (`GlobalReadWatch`, `@provino/types`; `@provino/env-shared`'s `populateGlobal` result, which `@provino/env-jsdom` and the Jest adapter return) hears reads through the accessors it already installed (`covers(key, descriptor)`: still its accessor; `watch(onRead)`: one listener, a `null` check per access otherwise), so under jsdom a window redefines about 36 keys, not about 874 (about 80 µs a window, not about 300, `local`). `FileScope.environment` holds the instance until teardown. **Writes (B23f, `module.reevaluatePatchingExternals`):** the watcher is installed when `@provino/loader`'s `reevaluatesExternals` says so (either key), and is told which counts (`watchPerFileGlobals`' `triggers`: `reads` the hooking key, `writes` the patching key). With `writes`, the window's open keeps every own key's descriptor, symbols too (with `reads` on, in the same walk `perFileKeys` makes; with `reads` off, that walk alone: no baseline is read at boot, no covered key is asked and no key is redefined), and the close compares what the load left with it (`wroteGlobal`), reading a key that still holds the window's accessor as the value that accessor holds, before the watched keys go back. What counts is exactly what `@provino/env-shared`'s `snapshotProperties.restore` takes back after the file: an added key it can delete (configurable, no process singleton: the same graceful-fs and undici test, copied, since the worker node may not import an environment package), a changed key it can define back (configurable, or a non-configurable writable data key's value), and an accessor that became a data key unless the value is Node's own (a native function, or what the old getter returns, which is how a lazy global such as `fetch` settles). A deleted key and the same value assigned again are not writes. **Limit:** an assignment through a closure-backed accessor (`process`, `performance`) leaves the descriptor as it was and goes unseen (reading those getters can run code). The cost is the second walk, per window only (a worker's first load of each external): over a global of jsdom's size (874 keys) about 80 µs with reads alone, about 150 µs with writes alone and about 180 µs with both, `local` (`external-probe.test.ts` prints it). What the loader learned during a file and the coordinator has not been told goes out as `FileOutcome.reevaluated` → `fileDone.reevaluated`; `runProject` adds it to the results cache's `externals` for the project, relative to the root and with each package's `package.json` `version` (`learned-externals.ts`), and the next run's workers get it as `config.loader.reevaluate`, read under the same `cacheProject` key it is written under (the identity is taken before the learned set goes into the config); an entry whose file is gone or whose package has another version is dropped (`ResultsCache.forgetExternals`). The steps the worker takes once, before any file, run through `adoptingGlobals(baseline, step)`: every environment's `prepare` (the docblock ones too) and the dialect's module-scope and globals factories; what one changes on the global is the worker's, the same in every file, so it goes into the baseline and is no per-file global (a wrapper an environment's `prepare` puts on a timer function, which a shared package captures as it loads). A file's environment may also name, in its teardown report's `perFileModules`, shared modules the file left holding its own work (a timer of theirs it cancelled); `runFile` hands them to `loader.reevaluateExternals` and adds them to `FileOutcome.reevaluated`, so every later file, and the next run, evaluates them per file. Tested by `external-probe.test.ts`, `learned-externals.test.ts`, `test/runtime.test.ts` ("a shared external that reads a per-file global as it loads", also two projects that share a cache key over two runs, and two D132 cases over forks, cold then warm: a learned package's dependency that a shared package imports, once per worker in both runs, and two workers of which only one loads a registry's shared importer, the other's plugin registering into a registry of its own from its second file) and `cache.test.ts`.
- **Teardown order**, always, each step running whatever the earlier ones threw: **the module-mock registry's `dispose()` first** (its mocks live in the mock registry; under `none` too), then **`mocks.dispose()` (file scope)**, so spies and replaced properties are restored while the environment is alive (env-node only compares the global's own keys, so an unrestored `jest.spyOn(Math, 'random')` would leak into the next file), then the environment's `teardown` (file scope), the matcher restore (file scope), `registry.dispose()`. The file-scope steps are left out of the list under `none`, not skipped inside the steps; there the worker's mocks are disposed first in `stop`. What threw is rethrown after all of them (an `AggregateError` for several), and `startWorker` charges it to the file as an `unhandled-error` and still sends `fileDone`. A `teardown` that throws is still a failure charged to the file.
- **Globals the environment can't remove are a warning (D22).** `teardown()` may return an `EnvironmentTeardownReport` (`{ leakedGlobals }`, `@provino/types`). For a **file-scoped** teardown the runner sends one `console` event through the context's sink after the file's own events and before it finishes: `taskId: null`, `stream: 'stderr'`, `level: 'warn'`, `origin: null`, text `Provino: <file> left N globals behind that the environment could not remove: a, b. Later files in this worker can see them.` (singular: `1 global ... see it`). It returns `{ leakedGlobals }` on the `FileOutcome`, which `startWorker` sends as `fileDone.leakedGlobals` (always present, `[]` when clean), so B11's pool can recycle the worker on `RecyclePolicy.onLeak`. A **worker-scoped** teardown (isolation `none`, in `stop`) sends `Provino: the environment could not remove N globals when the worker stopped: a, b.` before `stopped`, with nothing on any `fileDone`. If another teardown step of the same file also threw, the file is charged for it and its `fileDone.leakedGlobals` is `[]` (an error replaces the outcome), but the warning was still sent.
- **`stop`.** The worker's mock registry (isolation `none`) `dispose()`, `runtime.dispose()`, the worker-scoped environment's `teardown` (its report becomes the warning above), `loader[Symbol.dispose]()`, the lazy slot, the module scope's own `[Symbol.dispose]` when its factory returned a disposable function (the native runtime's takes its `provino.api` slot out, so an inline pool leaves nothing for the next run in the process), `slot.uninstall()`, then the worker-lifetime signal is aborted, and last the slots an outer worker held go back (below); errors collected and rethrown after all of them. It copes with a worker whose `start` threw half-way, and runs twice without harm.
- **A worker inside another worker's process (B27).** A test that runs Provino in its own process (`run()` on an inline pool, `provino jest -i`) under Provino starts an inline worker in the outer worker's process, which holds the slots in `PROCESS_SLOTS` (the matcher slot, the lazy runtime, the native API), its process error listeners and its console capture. The inner worker sets each aside as it starts and puts it back, exactly as found, on every path that runs `runner.stop` (a stop, a start that threw half-way, a kill): `boot` takes the held slots off first and `stop` puts them back last; only when it took any, its error listeners stand in for the outer ones, swapped in one step each way; `startWorker` runs with the console the outer capture replaced (`setAsideOuterConsole` in `console.ts`). **A stopped worker's slots are no one's to adopt:** the runner marks its slot values stopped when its link closes (`WorkerRunner.abandon`) and as it stops, so the next worker in the process, booting while a killed worker's stop still waits behind its file (the transport reported the exit once `teardownTimeoutMs` passed), fails loudly with `EXPECT_SLOT_TAKEN` and takes none of its listeners; inside an outer worker, the outer worker's later tests see the killed worker's slots until that stop runs. A non-configurable matcher slot (Jest's own `expect`) is never taken off. A test of the outer worker running beside the nested run sees the inner worker's slots, has an uncaught error charged by it and logs as plain stream writes: a limit, not handled. The account, with the costs, is the header of `internal/runtime/process-globals.ts`; `test/nested-worker.test.ts` holds it (out of band, in band, two levels, a failed start, a kill, a late stop) and `test/runtime-runner.test.ts` fails when a boot installs a symbol key of `globalThis` that `PROCESS_SLOTS` lacks.

## The coordinator (`runProject`)

Flow: pattern check (`ORCH_BAD_PATTERN`, `new RegExp(p, policy.core.testNamePatternFlags)`) → cache (`ResultsCache | false`; omitted means the default dir) → the worker entry and the pool (`createPool` throws `ORCH_BAD_OPTION` for a `recycle` or `fileTimeoutMs` that makes no sense, and `runProjects` for a `bail.count` that isn't a whole number of at least 1; the transport resolves the bootstrap), **all before anything reaches the bus, so a bad option never leaves reporters with a `run:start` and no `run:end`** → discover (`discoverProject`: `project.discovery` when the Jest reader gave rules, else `include`/`exclude`) and filter (`options.fileFilters`) → no files: `run:start`, `run:end`, an empty summary (with `RunCoverageHooks.reportEmptyRun`, Jest's `--passWithNoTests`, the empty map's coverage is finished first: its reports and thresholds, so a group naming a path fails the run) → `cache.prune` → sort → `run:start(RunInfo, files)` → `file:queued` per file in order → every file requested from the pool, then `pool.drain()` (workers retire as they go idle) → all files done → `cache.write()` starts and is awaited together with `pool.close()` (every worker has exited) → `run:end`. `planQueue` does prune, inputs, sort and queue. The worker entry defaults to `import.meta.resolve('@provino/orchestrator/worker/main')` (a string, not an import); `entry` overrides it.

- **If anything throws after `run:start`** (a bus that rejects; the reporter bus itself never does), the pool is closed, the bus gets `error(…, 'coordinator')` and then `run:end` with `reason: 'failed'` and the files that had finished, and the error propagates. A failure of that report is a line on `stderr`, and the original error still propagates. A throw before `run:start` (discovery, the pool) closes the pool and emits nothing.
- **`file:start` and `file:end` pair, always.** Every `file:start` is followed by exactly one `file:end`, and a `file:end` never comes without its `file:start` (the doc comments on `ReporterEvents` say so, and `test/coordinator.test.ts` asserts it with a recording reporter). A file goes `file:start(file, workerId)` when a worker takes it, its own events, then `file:end`. A file whose worker failed to start has no worker that took it, so `file:start` comes right before its `file:end` with the id of the worker whose failed start its error is (`PoolOutcome.workerId`; for the files left when the pool gave up, the last failed one). A file cut off by an abort after `file:start` gets `file:end` (`fail`, one `Interrupted` error naming the file) and is in `summary.files`; a file that had not started gets neither event and is not in the summary. **The other exception to the pairing** is `watch.interruptedFiles: 'drop'` (the Jest dialect's): a file a watch run's interrupt kills keeps its `file:start` and gets no `file:end`, as Jest's watcher ignores its result. A reporter that tracks started files clears them when the next run starts (the text reporter's live block does, at `run:start`).

- **The pool owns the queue.** `run(request)` never rejects and resolves a `PoolOutcome` (`done`, `crashed`, `failed`, `start-failed`, `aborted`); waiting files are served in request order. A worker is started only when a file waits and fewer than `maxWorkers` are alive, **counting workers that are still stopping** (the cap is strict). An idle worker with another key is retired to make room. `drain()` (`runProject` calls it right after it has requested every file) retires a worker as soon as it is idle with nothing waiting, so shutdown overlaps the files still running; without it the pool keeps idle workers for a next file, and `close` is what waits for every worker. The `maxWorkers` cap is also capped by `TransportFactory.maxWorkers`. After a file whose `fileDone.leakedGlobals` is non-empty the worker is stopped, not reused (`recycle.onLeak`, default on; D22), after `maxFilesPerWorker` files and after a file whose `fileDone.memoryBytes` is over `memoryLimitBytes` (the isolate's used heap in a fork or a thread, as jest-worker's `heapUsed` but read again after one collection when it was over the limit, see the `memoryUsage` bullet; never RSS, which sits near 200 MB in a fresh fork, nor `external`: oxc-parser's raw transfer buffer is a 6 GiB `ArrayBuffer`, so a thread of 150 MB reads about 6.4 GB of it; an inline worker, `sharesProcess`, is never replaced for memory: it measures the coordinator, which no replacement frees, as with Jest's `--runInBand`); `runProjects` defaults the limit to `defaultWorkerMemoryLimit(maxWorkers)`, `max(512 MiB, 25% of process.constrainedMemory() (never above the machine's memory, which it is without a cap: a cgroup with no limit reports about 2^64) / maxWorkers)`.
- **Crashes and starts.** A worker that exits mid-file (`ORCH_WORKER_EXITED`, the `WorkerExit` as `exit`, a field of `OrchestratorError`: plain data is no `cause`, which a reporter prints as an error) fails that file: `FileResult.workerExit` plus one `WorkerCrash` error (`The worker running <path> exited: <describeExit>`). A worker that fails to start fails the file it was taking (with `workerExit` when the cause is an exit or a start timeout), and that file is not retried. After three starts in a row fail, the pool starts no more workers, but it **gives up only when no worker is alive or still starting**: files left wait for the workers that are, and a start that works resets the count. Once none is left, every file still waiting gets the last failure's error (and its worker id), with no more attempts. A handler that throws (`ORCH_BAD_EVENT`, or a reporter bug) is `failed`: the file fails with that error and the worker is replaced, since its state is unknown.
- **The lifecycle (B21a, T9.5's rest and T9.10).**
  - **A file's deadline** (`fileTimeoutMs`, off by default, ours: Jest has none): a timer starts when the job is sent and, past it, `terminate(true, { phase: 'file', limitMs })`. The transport reports `{ type: 'timeout', phase, limitMs }` as it does the start and stop timeouts, and `describeExit` is the one place that words it ("killed for running past its deadline of N ms"). The worker then takes no file, so a `fileDone` landing in the same turn keeps its result. An inline worker can't be killed for a synchronous hang.
  - **An OOM** is a fork whose exit is SIGABRT after V8's "heap out of memory" line: `{ type: 'oom', limitMb }`, the limit from `memoryLimitMb`, else its `--max-old-space-size`, else V8's default (`oomExit`, shared with threads). Only a SIGABRT waits for stdio to close (its exit is read from the last of stderr); any other exit is reported on exit plus IPC disconnect, so a grandchild holding the pipe doesn't cost the 1 s grace (`reportChildExit`). `stderr-watch.ts` keeps a sticky flag per chunk, not a tail: V8 prints about 8 KB of native stack after the line. Without it a SIGABRT stays `{ type: 'signal', likelyOom: true }`; a thread's `ERR_WORKER_OUT_OF_MEMORY` is `oom` too. `RunPoolOptions.heapLimitMb` sets it for both.
  - **`bail: { count }`** counts failed tests (a `test-end` of state `fail`) across files. Under `orchestrator.bail.checkAfter: 'file'` (Jest) the count is made in `FileRequest.onDone`, which the pool calls before the worker takes another file, so no file starts after the one that reached it; the queue is cancelled (`cancelQueued`) and the pool closed, which kills the files running. **Those get no `file:end` and are not in the summary**, as Jest reports a killed file no further: the one exception to `file:start` having a `file:end` (a running file can't be cancelled before T5.12). Under `'test'` (Vitest) the count is made at each failing `test-end`, the queue is cancelled and the running files go on to their end, reported whole. The run ends `failed`. A file that fails to load or crashes its worker is not a failed test and adds nothing to the count, as in Jest (`cli/bail-on-load-error`; TestScheduler's check reads `numFailedTests` alone).
  - **Signals.** `RUN_SIGNALS` (`exit-code.ts`) is the one table: each signal's summary `reason` and exit code (`SIGINT` `interrupted` 130, `SIGTERM` `terminated` 143, `SIGHUP` `hangup` 129; a test checks the codes as 128 plus the signal's number). A `signal` aborted with one of the names (`isRunSignal`) ends the run that way, any other abort is `interrupted`, and one that lands after the last file (the pool closing, the cache write, the handle collection) still counts. `forceSignal` (a second Ctrl+C) kills every live worker, those in a graceful stop included, so `close` doesn't wait out `teardownTimeoutMs`. For an inline worker it gives up on the running file (`aborted`) and on its wind-down; code looping synchronously in-process can't be interrupted (the bin's exit timer ends the process). The bin owns the handlers (`provino`'s `signals.ts`).
  - **`detectOpenHandles`** puts the files in the inline pool (async_hooks sees this process only) and, after the last worker has stopped, `RunSummary.openHandles` holds each resource that is still alive and holds the loop (a Timeout that is `unref`'d doesn't), with its creating stack, innermost first, from the user's files only (under a project root, not `node_modules`, not Provino's own packages), and Jest's code frame. Handles with the same stack are one entry, kinds joined by `,`. The hook runs with `trackPromises: false` (an `await` costs several times more otherwise; Node before 22.15 ignores it). A TypeScript test file's frames are mapped through the transform's source map, as `.stack` maps them: `callSites` applies the mapper the worker's formatter carries (`provino.mapCallSites`, `@provino/loader`'s `stacks.ts`) to the sites it captures while that formatter is swapped out, so the frame and its code frame are Jest's (`3:3`, where the transformed code's tab made it `3:2`).
- **In band (B23d A3, T9.9, D114).** `shouldRunInBand({ policy, runInBand, detectOpenHandles, watch, workerMemoryLimit, maxWorkers, fileCount, timingsMs })` (`src/in-band.ts`, `@public`) is Jest's `shouldRunInBand` with its numbers from the policy's `orchestrator.inBand` (`{ single, fastFileCount, slowMs }`; Jest `{ true, 20, 1000 }`, neutral and Vitest `{ false, 0, 0 }`): asked for (`RunProjectOptions.runInBand`) or `detectOpenHandles` always; never automatically when the caller named a `pool.kind` (`forks` or `threads`: the policy's numbers are then off) unless `pool.automaticInBand` is `true`, which makes the kind the pool for a run that is not in band (`provino jest --workerThreads`: Jest's `shouldRunInBand` never reads it, so one file still runs in band; `automaticInBand: false` turns the choice off with no kind), in `watch` (a field a watch run will pass) or with a memory limit (`pool.recycle.memoryLimitBytes`); else `single` and one file or at most one worker, or at most `fastFileCount` files of which some have a time in the results cache and all are under `slowMs`. `runProjects` asks once the files are known (after the file filters, `RunProjectOptions.fileFilter` and the shard), makes the pool again as an `inline` one (the pool made before discovery has started nothing) and keys the workers against it. An in-band run captures `console` (`WorkerInit.captureConsole`: `globalThis.console` only, never the process's own stdout and stderr, which are the reporters'); a file runs inside an `AsyncLocalStorage` store (`inFile` in `start.ts`), and a console call made outside it (a reporter's own `console.log`) passes through to the console the capture replaced (`install`'s `passThrough`), as Jest in band gives the test a console of its own. After a kill mid-file the console is restored at once and again once the runner has stopped, since the file's environment teardown puts the capture's console back. `RunInfo.inBand` on `run:start` says whether the run is in band (the inline pool, chosen or named), so a reporter host reads the run's decision (Jest's `showStatus`) instead of guessing it. An `inline` pool a caller asks for with `pool.kind` captures nothing, as before. **`fileFilter(project, files)`** is a project's own say over its files (Jest's `--filter`), awaited after `fileFilters` and before the shard; the results cache is still pruned against the whole set.
- **Abort.** `signal` aborting (or `close`) resolves waiting files `aborted`, force-kills a worker running a file, and stops the rest. `runFile` knows whether the file had started (`onStart` ran): if so it ends with a `fail` result (`Interrupted`) and a `file:end` and is in `summary.files`; if not it is dropped silently. The run's `reason` is the signal's (`RUN_SIGNALS`).
- **A file's result** is its `file-end`: `pass`/`fail` as sent, `skip`, `todo` and `queued` as `skip` (nothing ran) unless a test of the file ended `todo`, when the policy's `todoOnlyFile` decides (`pass` under Jest, which marks a suite skipped only when every test is pending, DV50; the neutral and Vitest value is `skip`), `running` as `fail` (never finished). `stateOf` decides it once, so the reporters, the results cache (which does not remember a `skip` file) and `normalized-json` agree; `createFileDispatch` counts the tests that ended `todo` (`todo`) and the tests the file collected (`tests`). **A file that collected no test and ended with no error** (the worker sends `pass` for it: nothing failed) is the policy's `noTestsFile` (B23e): `fail` under Jest, whose scheduler fails any result with no test results ("Your test suite must contain at least one test.", also under `--passWithNoTests`, `cli/empty-test-file*`; a file whose tests are all skipped, todo or left out by `-t` collected some, so it is not this: `cli/empty-test-file-skipped-and-todo`, `-name-pattern`). Neutral and Vitest (read from its `runFiles`, not yet recorded) are `fail-unless-pass-with-no-tests`: the file fails unless the run passes with no tests, `RunProjectOptions.passWithNoTests` (`provino run --passWithNoTests`) first and the policy's `passWithNoTests` otherwise (`failsWithNoTests`, read once per file in `runProjectsOn`; `exitCodeFor` reads the same two for a run that found no file); `pass` is the third value, for a dialect that wants none of it. The result is then `fail` with one `ORCH_NO_TESTS` error (Provino's text, which the Jest dialect's result builder replaces with Jest's: it reads the file's tree, not this error), the results cache remembers it as failed, and `summary.reason` is `failed`. **This is for a file with no error at all.** A file that declares no test and holds an error keeps that error here (`state: fail`, `errors` as sent): which text a dialect prints for it is the dialect's. The Jest dialect's builder follows `onResult`, which tests only the results' length, so a file that loaded and has no test result reads "must contain at least one test." whatever errors it holds (circus's `unhandledErrors`, a throwing timer: `cli/empty-test-file-error-timing`, `-timer-throws`), and one that never loaded keeps its own (`onFailure`). It reads `file-collect-end`'s `loadFailed`, which core sets on a file whose import, collected-listener or `finalize` threw or whose options were invalid; the dispatch passes the event on as `file:collected`. A `fileDone` with no `file-end` fails the file. `summary.files` is in queue order, not completion order. `summary.unhandled` holds **every** unhandled error of the run, including ones tied to a file (the default reporter prints at `run:end` those no file's text showed); with policy `unhandledErrors: 'fail-run'` any of them makes `reason` `failed`. A file's `FileResult` does not turn `fail` for one charged to the run (`ownerId: null`) or to another file's test; one charged to the file or one of its tasks after the runtime's `file-end` (the worker's last turn before `fileDone`, when Node reports a rejection the last test left) turns a `pass` into `fail`, as the runtime would have a turn earlier: `createFileDispatch` leaves `result` as the worker sent it and sets `failedAfterEnd`, which `resultOf` reads from `FileRules` beside `runnerFailed`. `onTestFailed` (what `--bail` counts) is called once per test: at its `test-end` as `fail`, or when an error is charged to it after it ended (Jest's `bail` counts `numFailedTests`, which circus's late `test.errors` add to; an error of the file or the run counts none). Nor does it for any other, **except an error the worker's own runner charged to it** (`origin: 'runner'`, which `startWorker`'s `charge` gives every error it reports: the environment's teardown, a mock or clock dispose or `sendCoverage` threw after the file ran). Jest's `runTest` rejects then and `onFailure` takes that error, so `FileDispatch.runnerFailed` makes the file `fail`, whatever it declared and however its tests ended, and it is never a no-tests file; the Jest dialect's builder (`FileEvents.runnerFailed`) gives it that error and not "must contain at least one test." (`cli/empty-test-file-teardown-throws`).
- **Dispatch** pairs each `RuntimeEvent` with its node from the file's `file-collect-end`, awaits `bus.emit` inside `onEvents` (so a slow reporter holds the ack and the worker waits), and throws `ORCH_BAD_EVENT` for an id it never saw or a node of the wrong kind. `file-collect-start` and `file-end` have no bus event; the `coverage` event is ignored for now, and a `deps` event is rebuilt into `FileDispatch.deps` (T9.12 reads it). What a worker sends while it runs no file (a worker-scoped environment's stop) goes to `createIdleDispatch`: `console` under the file the worker ran last, unhandled errors as `unhandled(null, …)`. Because `drain()` stops a worker as soon as its last file is done, `runProject` holds those events back until that file's `file:end` has been emitted, so they still arrive after it.
- **The cache** is read synchronously when it is created, for `get`; a missing, unparsable or other-version file (or entry) is empty, never an error. `write()` **reads the file again**, drops what `prune` did not keep, puts this cache's own `record`ed entries on top, and writes a temp file plus a rename, so two runs that overlapped keep each other's history (two writes in the same instant can still lose one: the history is a hint for the order, not a ledger). `runProject` calls `prune(project, <every discovered path>)`: discovery is unfiltered, so any other file's history is stale. **A filtered run prunes against the whole discovered set, not the filtered one** (`planQueue`): the history of the files it left out stays. A run that finds no files neither prunes nor writes. A file that is `skip`, interrupted or whose worker never started is not recorded. A failed write is a line on `stderr`, not a failed run.
- **Worker `t` clocks differ.** Each worker's events carry its own `performance.now()`, comparable only within one worker (`RunInfo.startTime` is the coordinator's).
- **`CoordinatorMethods`** served to workers: `readTimings` returns the cache's duration. Snapshots have no RPC: the worker resolves the path and writes the `.snap` itself (build-plan §6), and inline edits ride on `fileDone` (D113, `inline-snapshots.ts`).
- **Snapshots in a run (B17b):** `runProject` resolves the update mode once (`resolveUpdateMode`: `RunProjectOptions.update` for `-u`, `project.config.ci`, `env` for the policy's variable) and puts it on every `FileJob.updateSnapshots`; it adds each `fileDone.snapshot` to a `createSnapshotAggregate` (Jest's `addResult` sums) and puts the result in `RunSummary.snapshots`, and `reason` is `failed` when `snapshotRunFails` says the obsolete snapshots fail the run (`snapshot.obsolete`, by mode: `failCI` under `none`, `failLocal` under `new`, never under `all`). `exitCodeFor` returns `exitCodes.failure` for it, after a failed file.
- **`exitCodeFor`** tries, in order: a run a signal ended (`RUN_SIGNALS`), no files without `passWithNoTests` (`exitCodes.noTests`), a failed file (`failure`), an unhandled error under `fail-run` (`unhandled`), a reporter failure (`failure`), else 0. It takes the whole `Policy`, which the orchestrator may.
- **An internal error in Provino exits 1, the same as a test failure** (a documented choice, as Jest does it): Track 9's `ExitCode` has no internal-error value, so a `runProject` that rejects (`ORCH_NOT_IMPLEMENTED`, `ORCH_BAD_PATTERN`, a bug) is the caller's to turn into exit code 1. `exitCodeFor` only ever sees a summary.

## Rules that aren't obvious

- **Coverage loads on demand (T1.10, T7.12).** `run.ts` imports `coverage-store.ts` and `coverage.ts` (and so `@provino/coverage/node`) by dynamic import, only when a project's worker config has `coverage`; the entry exports `loadCoverageStore()` and the store's type, not the store itself. `provino`'s `exports.test.ts` records a source run's coordinator and fails on any `packages/coverage/src` module without coverage. `finishCoverage` puts the remap's `sources` (the text of sources not on disk, from `sourcesContent`) in `CoverageSummary.sources`, which the reporter hands to `writeCoverageReports`.

- **Environment pragmas, `globals` and the resolver keys (B17c).** `runFile` reads the file's leading docblock (`internal/runtime/pragmas.ts`, `jest-docblock`'s extract) and passes it as the environment's `pragmas`. A value for one of `policy.orchestrator.environmentPragmas` (`jest-environment`) picks the file's environment: `config.environmentResolver` (the dialect's `ModuleRef`, loaded once) turns the name and `<pragma>-options` (JSON) into an `EnvironmentRef`, prepared once per kind (ref plus options) per worker and cached in `parts.pragmaEnvironments`. Under isolation `none` the worker keeps one environment instance and its kind (`workerEnvironment.prepared`): a file that wants another kind tears the current one down first (its leaked globals are reported as the worker's) and sets the next up, so each environment is on the global only while its own files run (`provino/test/env-docblock-none.test.ts`). Modules cached under `none` keep what they captured. `config.globalValues` (Jest's `globals`) is defined on the environment's global, copied for each file, before anything else. `loader.aliases`, `moduleDirectories`, `modulePaths` and `resolver` are validated by `parseProjectConfig` (T3.3).

- **Globals come in around `setupFiles` by `core.globalsBeforeSetupFiles`** (B14a). The worker splits the dialect's globals once (`splitGlobals`): the listed names (or all, under `'all'`) are installed with the environment, the rest after `setupFiles` and before `setupFilesAfterEnv` (`FileScope.installLateGlobals`, called from `importFile`). Jest 30.5 lists only `jest` (`policy/core-globals-at-setup`; the bench's worker test runs those files and traces what the golden traced). Under `none` the environment persists, so a later file's `setupFiles` still see the earlier file's late globals: a DIVERGENCES limit.
- **Setup files are fresh for every file, in every tier, and so is the test file.** Under `none` the registry is shared, so the setup module and the test file itself (queued twice, or imported by an earlier file) are invalidated and imported again (their dependencies stay shared); `isolateModules` would re-instantiate those too. They run inside collection, so a hook they register belongs to the file, and a throwing one fails the file with no tests.
- **Back-pressure is per file, not per test:** a file waits for `sink.writable()` before it starts, which bounds the worker's buffer to about one file's events beyond the 8-pack window. A per-test wait would need an async hook in core's executor (T5.8).
- **The behaviour loader keeps its default importer; D21 is checked in the config, not at import.** `parseProjectConfig` enforces absolute refs for the environment, the globals, the mappers and the paths, and for **every behaviour ref in the policy**: it walks `policy` for `{ module, export }` refs (a dialect's, and `neutralPolicy`'s own) and throws `ORCH_BAD_CONFIG` naming the key path, such as `policy.core.formatEachTitle.module`, for a bare specifier or a relative path. `neutralPolicy` writes its three refs (`core.formatEachTitle`, `snapshot.key`, `orchestrator.environmentConditions`) with `import.meta.resolve('@provino/policy/behaviours')`, a `file:` URL (the package names itself through its `exports`, which works under `--conditions=provino-source` and once built), so a worker needs no package resolution to load any of them. The importer itself stays the default one: a `WorkerError` thrown from `importModule` would reach the caller wrapped in a `POLICY_BEHAVIOUR_LOAD_FAILED`, and the config check names the key instead.
- **A path in the config that crosses is absolute.** `environment.module`, `globals.module` and each mapper factory's `module` are an absolute path or URL (`file:` from `import.meta.resolve`); `rootDir`, `setupFiles`, `setupFilesAfterEnv` and a path `loader.tsconfig` are absolute paths. A bare package specifier or a relative path is `ORCH_BAD_CONFIG` naming the key, because the worker would resolve it from this package or its own working directory, not the project. B11's coordinator resolves them.
- **`none` keeps everything:** the environment, the globals, the custom matchers (`snapshot.restore()` is file scope only, as in Vitest's `isolate: false`) and the registry. They go at `stop`.
- **`FileJob.collectOnly`** (B23a) imports a file and runs no hook or body (`--collectTests`); the worker installs the loader's source-mapped stacks with `policy.module.stackFrameNames` (`mapped-name` under the Jest dialect: DV88).
- **`FileJob.fileId` is the coordinator's id (D23).** The coordinator entry exports `fileIdOf(project, relativePath)`: SHA-1 over `<project>\0<POSIX relative path>`, 10 hex characters (the formula `@provino/core` uses when it runs standalone, which `test/file-id.test.ts` checks). The runner hands `job.fileId` to core's `runFile`, and every event and task id of the file derives from it. The worker node cannot import the coordinator entry, so it never computes one; the bench and `test/support.ts` import `fileIdOf` and pass the path relative to the root.
- **A fork's exit is reported after `exit` *and* the IPC `disconnect`.** `exit` can arrive before the child's last messages are read, so closing the link on `exit` would drop them. A 1 s fallback covers a grandchild that holds the channel open. That's also why `childProcessLink` closes on `disconnect`, not `exit`.
- **A child's `processLink.close()` waits for queued writes** before it disconnects, because a disconnect cancels pending IPC writes, `stopped` included.
- **Links queue while nobody listens** and hand the queue, in order, to the next listener. The handshake listener unsubscribes on `ready`, and nothing after it is lost.
- **A timeout overrides the raw exit.** A worker killed after the start or teardown timeout reports `{ type: 'timeout', phase }`, not the signal used to kill it.
- **An inline pool runs one worker.** The inline transport declares `TransportFactory.maxWorkers: 1` (`--runInBand`) and `createPool` caps `maxWorkers` by it, whatever the caller or `defaultMaxWorkers()` says: the expect slot is process-global, so a second inline worker alive at once would take the first one's slots aside as an outer worker's (above). (The pool's tests drive fakes that declare no cap.) Two inline runs overlapping in one process share those slots and are not supported; use forks or threads. A run nested inside a worker's test (the outer worker awaiting it) is supported.
- **A worker still starting is cancelled.** `TransportFactory.create(init, signal)`: the pool passes a signal it aborts on abort/`close`; the handshake then clears the start timer, SIGKILLs the worker (an inline one loses its link) and rejects, which the pool maps to `aborted`. Nothing waits for `ready` or the start timeout.
- **A worker that ends badly while it runs no file is an error of the run.** After the pool's own abort kill is excluded, an exit other than `{ type: 'exit', code: 0 }` of an idle or stopping worker (a crash, `process.exit(1)`, a teardown that hangs at `stop`: `{ type: 'timeout', phase: 'stop' }`) goes to the pool's `onError` as `ORCH_WORKER_EXITED` (`exit`: how it ended), with `kind: 'worker-lost'` as the callback's second argument (`'other'` for any other error). **A worker that died of SIGINT, SIGTERM or SIGHUP is judged after a 500 ms window** (`GROUP_SIGNAL_WINDOW_MS`): a task runner cancels with one signal to the whole process group, so the workers die of it as the coordinator hears it, and if the run's `signal` (or `forceSignal`) is aborted by then it was the cancellation, no error of the run and no `crashed` file (the file is `aborted`, as for Ctrl+C); with no cancellation it is reported as before. `runProject` branches on that kind, and emits it as `error(…, 'coordinator')` and adds it to `RunSummary.unhandled`, so `unhandledErrors: 'fail-run'` fails the run. Known gaps: a worker that dies just after its `fileDone` has its crash charged to the next file it was handed (no retry policy yet); `RecyclePolicy.onLeak` covers leaked handles per its doc, but only `leakedGlobals` is checked until T2.7.
- **Worker stdout.** `RunProjectOptions.stdout` is where forks and threads have their stdout copied (default: the process's); `provino` passes its `stderr`, so `--json` on stdout stays clean. An inline worker shares the process, doesn't capture console (B09's rule) and so a test's `console.log` or `fs.writeSync(1, …)` still reaches the process's stdout.
- **Inline workers don't patch globals.** Console capture installs on `globalThis.console` and `process.stdout`/`stderr` only when `init.key.pool !== 'inline'`: an inline worker shares the coordinator's stdio (the reporters', or the process of whatever called `run()`). Inline runners use `context.console`; tests pass stand-in streams. The real runtime hands `context.console` to the environment's `setup` but does not install it itself, so a test's `console` in an inline worker prints to the coordinator's stdout (forks and threads capture it through the patched global; an in-band run captures `console` only, see "In band").
- **The worker takes its timers at load** (`worker/timers.ts`), so fake timers installed by a test file can't stall a flush or the end-of-file yield.
- **Stdio is flushed only when bytes are buffered** (`writableLength > 0`). With capture installed nothing reaches the real stream, and in a thread an empty write's callback waits on the coordinator's event loop.
- **A pack that won't send never throws.** It goes again with each unclonable event replaced by an `unhandled-error`; the window and pack numbers stay intact.
- **No coalescing.** Every `RuntimeEvent` is a transition reporters see (§6's one event model). The brief's "coalesce per task" came from Track 9's retired `task:update` shape (DECISIONS P4).
- **`WorkerMethods.memoryUsage` replaces `Transport.memoryUsage`.** A parent can't read a forked child's RSS, so the worker measures itself: `v8.getHeapStatistics().used_heap_size` (the isolate's own heap, as jest-worker's `process.memoryUsage().heapUsed`) in a fork, a thread or inline. Not RSS (a fresh fork sits near 200 MB of it with about 70 MB of heap, so a 1 GB limit replaced its worker every few files), and not `external`, which counts reserved `ArrayBuffer`s, not memory held. `test/coordinator.test.ts` runs real threads under the default limit and checks one worker serves every file.
  - **A heap over the limit is collected once before it is reported (Tyler, 2026-11-16; D115, `speed`).** `createPool` puts its `recycle.memoryLimitBytes` on the `WorkerInit` of every fork and thread it starts (`WorkerInit.memoryLimitBytes`; never for a `sharesProcess` transport, which is never replaced for memory, and not when the pool has no limit), so the worker and the pool compare against the same number. After each file `startWorker` sends `memoryAfterFile(init.memoryLimitBytes)` as `fileDone.memoryBytes`: the used heap, and, only when it is over a limit above 0, one forced full collection (`collectGarbage`, shared with `--detectLeaks`' check) and a second reading, which is what the pool compares. No limit, a limit of `0` (replace after every file: the answer doesn't depend on the heap) and a heap at or under the limit collect nothing. The `memoryUsage` RPC stays the heap as it is (no side effects); only `fileDone.memoryBytes` collects. **Why (`speed`):** measured after a forced collection, a real React UI suite's live heap stayed flat at about 610 MB over 18 files, while garbage pushed `used_heap_size` past a 1 GB limit about every 15 files, and each replacement cost about 5 s of reloading (the shared node_modules records and compiled wrappers are per worker) (`local`). **The cost:** one full collection of a worker that is idle between files, paid only by a worker over its limit: 69 ms median at a heap of 953 MiB with 301 MiB live (`local`; the range and the setup are in `memoryAfterFile`'s doc comment). A collection that throws (V8's flags are process-wide, so a thread can lose its `gc` to another's restore) leaves the first reading as the report, never a lost `fileDone`. **The compat cost:** jest-worker 30.5.1 compares `process.memoryUsage().heapUsed` with no collection (`processChild.js`), so a worker Jest replaces because of garbage is kept; a test can't tell (`JEST_WORKER_ID` and the files a worker runs are the same). It is a DIVERGENCES entry; `packages/provino/test/worker-recycle.test.ts` ("garbage alone") holds both sides against a real jest-worker. Tests: `src/worker/internal/memory.test.ts` (the decision over a stub heap and collector; the real collector frees garbage and leaves `gc` hidden), `src/worker/start.test.ts` (`fileDone.memoryBytes` over the real heap), `src/pool.test.ts` (the limit on the init: forks and threads, `0`, none, `sharesProcess`), `test/pool-chaos.test.ts` (a fork that only makes garbage is kept; one that holds its heap is replaced, as before) and `test/coordinator.test.ts` (real threads).

- **`--detectLeaks` and `--logHeapUsage` (B23d A4).** `RunProjectOptions.detectLeaks` is a predicate over the projects (Jest's `detectLeaks` is a project key; `provino jest` answers from each project's config, the flag setting every project's), kept on each `Member` and put on `FileJob.detectLeaks` for that project's files only; one that says yes for a project of isolation `none` is `ORCH_BAD_OPTION`, naming `none`, before `run:start`, and the others are not asked. `logHeapUsage` is run-wide. The worker measures `heapUsed` (after `gc()` when exposed) after the file ran and before its teardown (`fileDone.heapUsedBytes` → `FileResult.heapUsedBytes`). After teardown `runFile` returns `FileOutcome.isLeaking`, a check made by `createLeakCheck` (`internal/runtime/leaks.ts`) over `WeakRef`s to the file registry, its `leakTargets()` (the loader's `Registry`, which a leaked `require` reaches) and the environment instance; `startWorker` calls it **after the runner has returned** and before the file's controller is dropped, so no frame of the file holds the targets and `cancel` ends the wait (it is part of the file's time for `fileTimeoutMs`, which runs until `fileDone`: ten ticks and a collection). The check is one `setImmediate` (a `WeakRef` keeps its target until the end of the job that made it: without that turn a clean file reads as leaking; measured), `gc` through `v8.setFlagsFromString('--expose-gc')` and `vm.runInNewContext('gc')`, ten ticks, and if still held a heap snapshot (its stream destroyed at once) and ten ticks again (jest-leak-detector's `isLeaking`, without its 100 ms sleep). Under the flag the runner also swaps the file scope's registries for **disposed stand-ins** (`disposedScope`, module-level so it shares no context with `runFile`): the `fileScope` store is held by every async frame made while the file ran (Node's own 10 s `clearBuffersCache` timer, first created inside a cold file, kept the whole scope alive), and a callback the file left behind finds registries that behave as the file's disposed ones do, with or without the flag (`runtime.test.ts`, `leaveCallback`). `fileDone.leaks` makes `runFile` fail the file whole (`leakedResult`: `state` `fail`, `resultsDiscarded`, `FileResult.leaks`, one neutral error that the Jest dialect replaces with Jest's text), as `TestScheduler's` `onFailure` does: its tests count for no `--bail` (`onDone` counts none), as in Jest, where a leak adds no failed test and is no bail check.
