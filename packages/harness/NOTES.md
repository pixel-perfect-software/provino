# @provino/harness reference notes

Reference sections moved verbatim out of `CLAUDE.md` to keep it short. Open only the section a task names.

## Fixture format

A fixture is a directory `fixtures/<area>/<behaviour>/` (named for the behaviour, not numbered):

- `fixture.json`: `{ "description": string, "runners": ("jest" | "vitest" | "vitest-list")[], "env"?: Record<string, string>, "nodeFlags"?: string[], "nodeMajors"?: { [profile]: number[] }, "expectCrash"?: { [profile]: string }, "mockCleanup"?: {...}, "packages"?: { [name]: { [file]: source } }, "jestEsm"?: true, "jestConfig"?: { roots?, unmockedModulePathPatterns? }, "config"?: { jest?, vitest? }, "files"?: { jest?, vitest? }, "run"?: {...}, "scm"?: { "steps": [...] }, "before"?: [{ "argv": [...] }] }`. Anything else is a coded error (`HARNESS_FIXTURE_*`).
- **`scm`** (B23c): `{ "steps": [...] }`, a repository in the work directory for the changed-file flags. After the files and packages are written the recorder runs `git init` (an empty template, so no sample hooks) and the steps in order; a fixture with no `scm` has no repository. A step has exactly one key: `{ "git": [args] }` (not opening with `-c`, `-C`, `--git-dir` or another option the hermetic environment owns), `{ "commit": "msg" }` (`add -A` plus a commit), `{ "branch": "name" }` (`checkout -b`), `{ "checkout": "ref" }`, `{ "write": { path: text } }` and `{ "remove": [paths] }`; no path may be inside `.git`. Anything else is `HARNESS_FIXTURE_BAD_SCM`, a failing command `HARNESS_SCM_FAILED`. The fixture's own files are the first state, so the first step is usually a `commit`. **Hermetic** (`internal/scm.ts`): `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_AUTHOR_DATE` and `GIT_COMMITTER_DATE` `2026-01-01T00:00:00Z`, the settings `user.name=provino`, `user.email=provino@example.invalid`, `commit.gpgsign=false` (so nothing signs through 1Password), `init.defaultBranch=main`, `core.excludesFile` and `core.hooksPath` `/dev/null`, as `-c` flags on the recorder's own git and as `GIT_CONFIG_*` variables for the runner's; every inherited `GIT_*` variable is dropped. The **runner gets the same environment for every fixture**, plus `GIT_CEILING_DIRECTORIES` at the work directory's parent, so a work directory with no repository of its own never finds the checkout's (`changed/only-changed-no-git`). `.git/info/exclude` keeps `.harness-out/`, `.jest-cache/`, `.vite/` and `node_modules/` out of every status. The `.git` is never captured (the leak guard covers the golden as for any fixture), and `runScmSteps` takes any list of steps, so a later `watch` field reuses it (`parseScmSteps` is its parser). Two recordings give one golden because the commit hash is a function of tree, author, date and message (`internal/scm.test.ts`).
- **`before`** (B23c): `[{ "argv": [...] }]`, Jest only. The runner runs once per entry before the captured run, in the same work directory and under the same config (so Jest's cache and its failure history carry over), with the entry's extra arguments, which go through `run.argv`'s reserved-flag check (`HARNESS_FIXTURE_BAD_BEFORE`). Their output is dropped, and the JSON and trace they wrote are removed so the captured run can't read them. `changed/only-failures*` use it: one full run with a failing file, then `--onlyFailures`.
- **`watch`** (B23c Phase 3): `{ "argv": [...], "tty": true | false, "steps": [...], "capture": [...], "keepLines"?: regex, "mask"?: [regex] }`, Jest only (`runners: ["jest"]`), never beside `run`, `before` or a `config.jest.reporters`. Jest runs with the fixture's `--watch` or `--watchAll` and no `--ci`, `--json` or output file (the parser refuses `--ci` in any spelling, since Jest reads no keys in CI, and `--watchPlugins` and `--watchPathIgnorePatterns`, which would replace the recorder's done plugin and ignored directories: a fixture's own go in `config.jest`, which the recorder adds to), in `watchEnv` (`CI=false`, `TERM=xterm-256color`, `FORCE_COLOR=0` because chalk 4 ignores `NO_COLOR`, no `TERM_PROGRAM`), on a 40x120 terminal from the pty relay (`pty.ts` `spawnPty`) or, with `tty: false`, on a pipe (`spawnPiped`: stdout and stderr one stream). Steps, in order (`internal/watch-steps.ts`): `{ "waitRun": n }` (n runs ended: the run log **and** the done file hold n lines; more is `HARNESS_WATCH_FAILED`), `{ "waitText": "…" }` (after the end of the previous match, so a second text in the same read is still found, or after the last key), `{ "key": "p" | "<enter>" | "<esc>" | "<backspace>" | "<up>" | "<down>" | "<ctrl-c>" | "<ctrl-d>" }`, `{ "type": "abc" }` (a character per write, each once the prompt line shows ` pattern › ` and the text so far, the line `printPatternCaret` draws for Jest's prompts and jest-watch-typeahead's: the bare text is no echo, since the match list under the line holds it too; it works only in a pattern prompt, which starts empty, so the line for the text so far is never an earlier, longer one: the text may hold no control character (backspace, DEL, Escape, Enter, line feed: `key` steps; `HARNESS_FIXTURE_BAD_WATCH` naming the step), and a wait that times out says the prompt never drew ` pattern › <text>` and that `type` needs a pattern prompt), `{ "write": {...} }`, `{ "remove": [...] }`, `{ "scm": [...] }` (needs the fixture's `scm`) and `{ "exit": n }` (last; the exit code must be n). A key may not be followed by a key or a `type` (two would reach Jest as one keypress), and no key goes to a pipe. With no `exit` step the recorder kills the session, and `exitCode` can't be captured. `capture` lists `runs` (the run log: `reporters/jest-watch-log.ts`, one line per `onRunComplete` with each file's root-relative path, its status as Jest's `addResult` counts it (`skipped`, then `failed` for a failing test or a `testExecError`, else `passed`; `execError` marks the second), its tests, the snapshot counters, `wasInterrupted`), `transcript` (`internal/watch-transcript.ts`: the work directory replaced by `<root>` in the bytes, so a path the 120-column wrap would split is still found, then the bytes played on a small terminal model, so the live `RUNS` block Jest erases leaves nothing, a redrawn prompt keeps its last text, and each screen clear is a `<CLEAR>` row; then the normalizer, `<time>` for times, `mask`, and `keepLines`, which must keep a line), `exitCode` and `file:<path>`; the golden's `observed` gains `runs` and `transcript`. **Why two logs:** Jest's reporters finish before `watch.ts` sets `isRunning` back to false, so a key sent when the run log grows can land as an interrupt; the recorder's watch plugin (`reporters/jest-watch-done.ts`, appended after the fixture's own `watchPlugins`) writes from `onTestRunComplete`, which runs after it. **`captureFile`** (B23e Phase 4, exact watches only, after a `waitRun`) reads its file once the session's output holds the n-th `Test results written to` line for the n-th capture: the run log's reporter finishes before Jest writes `--outputFile`, so waiting on the log alone read no file, or the run before's. `runWatchSteps` makes that wait (the session's `waitFor` from past the last capture's line, so the session's one deadline, or its end, is the error, with the output's tail), and the host's `captureFile` only reads, parses and normalizes the file; the steps' result holds each capture under `<file>#<n>`. An exact watch's own `argv` must name a `--reporters` (the recorder adds the run log's as one, and a command-line `--reporters` replaces the config's; the log reporter writes only its file, so no kept line changes). Both process groups are killed after the steps (`internal/watch-record.ts`), whatever they did; a kill that fails after a failed step is added to the step's error, never in place of it. The poll counts only newline-ended lines (a half-written line is not a run yet), and the log is parsed once the session has ended; every run it holds must be one a `waitRun` waited for. The relay polls `waitpid(WNOHANG)`, so a grandchild that keeps the terminal open does not keep the session alive. The `watch/` fixtures (25: usage, every key, `u` and the two `i` modes, changes, a pipe, plugins and jest-watch-typeahead 3.0.1) wait for each run before a key, keep no `PASS`/`FAIL` header (worker order) and no time. **They can't be recorded in a sandbox that denies `/dev/ptmx` or FSEvents**, and neither can `pty.test.ts`'s terminal cases, which fail there with `HARNESS_PTY_UNAVAILABLE` (never a skip); the piped cases run anywhere.
- **`PROVINO_RECORD_ROOT`** moves the work directories (default `packages/harness/.record/`). For a sandbox that refuses writes to `.git/config` inside the checkout: use a **real** path (a symlinked one makes Jest read `projects[0] !== process.cwd()`), with a `package.json` in it, because Jest 30.5.2 resolves a config path by traversing up from the work directory even when `--config` names one, and fails when no `package.json` or Jest config is found above (`.record/` finds the repository's). `--watch` can't be recorded in a sandbox that blocks FSEvents (`jest-haste-map ... Error starting FSEvents stream`).
- **The `changed/` fixtures** (B23c Phase 2, 39 Jest-only black-box runs; `watch-no-git`, `--watch` with no repository, came with Phase 3 and is recorded outside a sandbox, which blocks FSEvents): `only-changed-*`, `changed-since-*`, `last-commit`, `with-ancestor`, `pattern-overrides-only-changed`, `all-overrides`, `roots-include-paths`, `deleted-file` and `bad-ref` (git selection); `related-*` (graph rules, no git, `--findRelatedTests`); `only-failures*`; `only-changed-watch-all` and `find-related-no-paths` (the command line's own errors). List fixtures run `--listTests` and capture `file:.harness-out/jest.json` under `sortStdout: "json"` (the set of files), full runs keep PASS/FAIL, the totals and the closing line. **The recorder runs Jest with `--json`, which moves the no-tests texts and the no-SCM line to stderr** (a plain run prints them on stdout). `related-mock-adjacent` requires `./src/foo` with no extension on purpose (jest-resolve-dependencies looks the mock up by the specifier's basename), and `related-extractor-spread` pins that a `require` right after a dot (`...require(`) is no edge. Regenerated trees: edit `fixture.json` and re-record, never the golden.
- **The `ecosystem/` fixtures** (B23e, T11.11, T7.16's Jest half; 36 Jest-only black-box `run` fixtures, read by `provino`'s `ecosystem-*.test.ts` and `jest-window-timers.test.ts`): third-party packages a Jest project loads from its own `node_modules`, the DOM, matcher and network ones on two test files under `-w 1`, so a package loaded once per worker is seen by the second file. Seven DOM (`jest-dom-default`, `jest-dom-jest-globals`, `rtl-cleanup`, `user-event-fake-timers`, `jest-axe`, `jest-canvas-mock`, `jest-styled-components`), seven matcher, mock and network (`jest-extended-all`, `jest-mock-extended`, `jest-when`, `jest-fetch-mock`, `msw-node`, `identity-obj-proxy`, `expect-type`), `image-snapshot-*` (6: add, match, mismatch, `-u`, `--ci`, retry; `image-hashes.txt` holds the sha256 of every image written, since no binary file is committed), `custom-snapshot-*` (10: a matcher that calls jest-snapshot's own matchers with its `this`), `per-file-registry` and `-cycle` (D132), `load-time-global` and `msw-setup-file` (B23f: a package that writes the global as it loads) and `react-scheduler-loop` and `react-work-after-teardown` (timers on a jsdom window). The packages are D124's catalog-pinned devDependencies of this package and `provino`, found by the upward walk from the work directory. Captures are `exitCode`, `stderr` (cut to `keepLines`) and `json:.harness-out/jest.json`, plus `file:` for a `.snap` or the hash file; the goldens are Jest 30.5.2's.
- **The `ide/` fixtures** (B23e, T11.12, D125; 13 `vscode-jest-*` and 4 `neotest-jest-*`, read by `provino`'s `ide-vscode-jest.test.ts` and `ide-neotest-jest.test.ts`): the argv an editor's Jest process receives after the shell, under `run.exact`, from vscode-jest 6.4.4 and neotest-jest `0e7979d`. `fixtures/ide/README.md` is the contract (each request's argv with source file and line, the environment the spawner sets, what the editor reads back, and where the code disagrees with Track 11 F7: the code wins) and the `UPSTREAM.md` in the vscode-jest fixtures that carry the editor's reporter says where its text comes from (the published VSIX, unmodified). vscode-jest's fixtures set `CI=false` and remove `NO_COLOR` (the editor passes `--colors` and sets neither), run the 7-test project of `cli/json-vscode-contract`, capture `raw` (colour codes kept) and, for the nine that write a results file, carry that reporter (a test holds the copies byte equal to `cli/reporters-twenty`'s); `vscode-jest-watch` and `-watch-all` are `watch` fixtures on a pipe, recorded from a terminal with FSEvents. The output file is a relative path inside the project, not the editor's tmpdir name. No editor runs, and there is no JetBrains fixture (D126).
- **`nodeFlags`** (B17a): flags for `node` itself, before the runner's bin (`["--harmony-temporal"]`, which `NODE_OPTIONS` refuses and Node 24 needs for a `Temporal`). A non-empty array of `--flag`s; `--require`, `--import`, `--eval` and the loader flags are refused (`HARNESS_FIXTURE_BAD_NODE_FLAGS`). Vitest runs its tests in a worker, so a fixture that needs the flag there also sets `config.vitest.test.execArgv`.
- **`nodeMajors`** (B17a): `{ "jest": [24] }` checks a profile's golden only on those Node majors (`checkedOnNode`; `runtime-corpus.test.ts` skips the pair with the reason, and `policy-truth` leaves the fixture out of the evidence on the others). For a golden whose text comes from Node's own `util.format` or `util.inspect`, which Jest uses and Provino calls the same way: a Proxy prints its target on Node 22 and 24 and as `Proxy(...)` on 26, and a Date under `%s`, a symbol key and `ArrayBuffer` fields differ on 22. `runtime/each-values` (Jest) is the one fixture that has it; `each-tokens` and `each-truncate` left their Date out instead. Vitest has its own formatter and is checked on every Node. A fixture is recorded on Node 24.
- **`config`** (B14a): a JSON overlay per listed runner on the config the recorder writes (Jest's options; Vitest's whole object, `{ "test": {...} }`), applied last (`runner-config.ts` `applyOverlay`). Objects merge, arrays replace, except Jest's `setupFiles`/`setupFilesAfterEnv` and Vitest's `test.setupFiles`, which are appended after the trace and observe setups. A key the recorder owns (`rootDir`, `transform`, `testMatch`, `testPathIgnorePatterns`, `testLocationInResults`, `cacheDirectory`, `watchman`; Vitest `root`, `cacheDir`, `test.include`, `test.exclude`, `test.includeTaskLocation`; **except that a fixture with a `run` may set `testMatch`, `testPathIgnorePatterns` and Vitest `test.include`/`test.exclude`**, since which files a black-box run finds is what `discovery/*` and `policy/orchestrator-match-path` are about; a JSON `null` removes an option, as `testMatch: null` beside `testRegex`), `projects` (which brings configs the recorder doesn't write; Vitest's `test.projects` is allowed only for a fixture whose manifest says `"vitestProjects": true` (B25c): its directories and config files are the fixture's files, and the golden lists every file that ran, once per project that ran it), one `mockCleanup` or `jestConfig` sets, and `test.sequence.hooks` under `vitest-list` are refused (`HARNESS_FIXTURE_BAD_CONFIG`), and so is a Vitest `test` that isn't an object.
- **`files`** (B14a): `{ "jest"?: { path: text }, "vitest"?: {...} }`, written into the work directory before that runner runs: a `.snap` with one runner's header, or a file D13 keeps out of the repo. A path the fixture already has is refused (`HARNESS_FIXTURE_BAD_FILES`).
- **`run`** (B14a): a black-box run. `{ "capture": [...], "argv"?: { jest?, vitest? }, "keepLines"?: regex, "emptyStreams"?: ["stdout" | "stderr"], "sortStdout"?: true | "json" }`. `capture` lists `exitCode`, `stdout`, `stderr` and `file:<relative path>`; the golden gains `observed` (last key: `exitCode`, the streams normalized and cut to `keepLines`' lines, sorted under `sortStdout`, and each file's text or `null`), under the same normalization and leak guard. `sortStdout: "json"` reads the kept lines (or a captured file) as one JSON array of strings and records its elements sorted, one to a line: Jest's `--listTests` order depends on file sizes and timings, so a list is recorded as the set it is. **`--listTests` with the recorder's `--json` writes the list to the output file** (`file:.harness-out/jest.json`), not stdout, and the recorder keeps a JSON array there as "no results" (a golden with no files) and the list as the captured file (`discovery/*`). `argv` is appended to the runner's command line (Jest's `--ci=false` turns the recorder's `--ci` off); an option the recorder passes or `mockCleanup` sets is refused in any spelling (`--config`/`-c`, `--outputFile`, `--json`, `--root`/`-r`, `--rootDir`, `--reporter`/`--reporters`, the cleanup flags; `--no-` and kebab-case forms too), except `--reporter=<name>` for a text reporter, which Vitest adds beside the recorder's `json` (`report-default`). A captured stream `keepLines` keeps no line of fails the recording (`HARNESS_FIXTURE_BAD_RUN`), unless `emptyStreams` lists it, so a pattern that matches nothing can't record an empty stream as the truth. The completeness rule doesn't apply, and a runner that writes no JSON (no tests found) gives a golden with no files. Streams carry timings, so keep only the lines the claim reads.
- **`run.exact: true`** (B23e, Jest only, needs `argv.jest`, else `HARNESS_FIXTURE_BAD_RUN`): Jest gets exactly `argv.jest`, as an editor's command line is, with none of the recorder's flags (`--config`, `--ci`, `--json`, `--outputFile`), and the reserved-flag check is skipped. The recorder's config is written as `jest.config.json` in the work directory, where Jest finds it as it finds a project's own. The golden has no `files` (as for a run that writes no JSON); the editor's own output file is captured with `json:<path>`. `argv.jest` must be non-empty. Only the cleanup flags `mockCleanup` owns (`--clearMocks`, `--resetMocks`, `--restoreMocks`) stay refused in `argv` and `before`; `--config`, `--json`, `--outputFile` and the rest are the editor's own. `before` entries run the same way. A fixture with its own Jest config (a `jest.config.*`, or a `package.json` with a `jest` key) is refused (`HARNESS_FIXTURE_BAD_RUN`): at parse time for `files.jest`, and in the work directory for the fixture's own files (`isJestConfigFile`). A fixture's `env` may hold `null`, which removes a variable the process inherits or the recorder sets (`NO_COLOR` for an editor that passes `--colors`, `CI` is set with `"false"`). `record.test.ts` records a small exact fixture against real Jest. A `json:<path>` capture is the file parsed, under `timeKeys`, with the work directory as `<root>` and each run of stack frames as `<frames>`; `json:stdout` and `json:stderr` parse the stream itself (B23e: neotest-jest's `.each` discovery reads Jest's `--json` from stdout), and a run that wrote none is refused unless the fixture says it is what the run shows.
- **`run.cwd`** (B23d A3 review): the directory the runner runs in, relative to the work directory (a path inside the fixture, which its files make), with the config still the recorder's at the root: a run from below `rootDir`, so the working directory and the root differ. `cli/report-from-subdir` runs in `pkg/` and holds Jest's headers relative to the working directory (`../root.test.ts`, `./a.test.ts`); `provino`'s `reporters.test.ts` runs the bin there.
- **`run.raw: true`** (B23a): the streams and `file:` captures are recorded as the runner wrote them (the work directory as `<root>`, then `keepLines` and `mask`), with none of the recorder's normalization (durations, code frames and stacks reduced). For a comparison of a reporter's whole output; `mask` is for times only. `cli/reporters-twenty` (20 files, the third-party reporters; `UPSTREAM.md` has vscode-jest's reporter, whose text is in `fixture.json`'s `files`, and the fixture's own `package.json` makes the work directory CommonJS) is the one that uses it. `cli/failure-frames` records the frame names of failing tests (DV88). A file-level message drops the runner's own frames (`withoutRunnerFrames`: `node_modules/` frames and a native one after them), which came and went between two recordings of `cli/collect-tests-empty-file`.
- **`run.maskKeys` and `run.cwd`** (B23b): `maskKeys` (beside a `json:` capture) records every string under the named JSON keys as `<masked>`, wherever it is: the coverage fixtures mask Istanbul's per-file `hash` (a digest that holds the work directory's path) by key, so `_coverageSchema` and any other 40-hex string are recorded as written. `cwd` starts the runner in a directory of the work directory (created if the fixture has no file there), below the config's `rootDir`: `coverage/babel-cwd-below-root` (babel-jest instruments only under the process cwd). The one reordering `normalizedJson` does is sorting an object whose every key is a path under the root (an Istanbul coverage map); `provino/test/mask.ts` is its copy.
- **`runnerEnv` drops std-env's agent and GitHub variables** (`CLAUDECODE`, `AI_AGENT`, `GITHUB_ACTIONS`, ...): Vitest's `configDefaults` read them (`reporters`, `watch`), so a golden would differ between a terminal, an agent's shell and CI.
- **`packages`** is written into the work directory's `node_modules/<name>/` before the run (`record.ts` `installPackages`), for fixtures that need an installed package: a root `__mocks__/<pkg>` case or an automocked CommonJS package. The name is `name` or `@scope/name`; a file is a relative POSIX path with no `..` segment and no trailing `/`, kept under its normalized spelling (`./x.js` and `x.js` are one file and a duplicate is refused); every package needs a `package.json` entry, because one without it inherits `"type": "module"` from this package and Node and Vitest then read its `index.js` as ES modules where Jest reads CommonJS. All of it is checked when the manifest is read (`HARNESS_FIXTURE_BAD_PACKAGES`), and again when written, with the same test of what leaves the package (`..foo.js` is a file name). The sources are plain CommonJS (`exports.x = ...`, so Vitest's Node loader sees the names), because Jest doesn't transform `node_modules` (unless the fixture's `transformIgnorePatterns` and `jestTransformJs` say it does), `node_modules/` is gitignored and no `.js` is committed (D13). `node_modules` is not listed as a fixture file.
- **`jestEsm: true`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_ESM`): for this fixture only, Jest's transformer also applies `@babel/plugin-transform-modules-commonjs` (`transform: [path, { jestEsm: true }]` in the written config), so `*.jest.test.ts` and shared support files can use `import`/`export`, as in a real project with a Babel or ts-jest setup. Without it the transformer is exactly `babel-jest`, so older goldens don't change. Babel's interop applies: a `{ default }` factory without `__esModule` gives a default import of the whole object.
- **`jestTransformJs: true`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_TRANSFORM_JS`): the recorder's transformer also takes `.js`, `.cjs` and `.mjs` files (`\.[cm]?[jt]s$`), as Jest's default `babel-jest` entry takes `\.[jt]sx?$`, so a package under `node_modules` that the fixture's `transformIgnorePatterns` lets through goes through it (with `jestEsm`, an ES module package's `import`s become `require`s). Such a package may be ES module source, which is what `cli/transform-node-modules-*` (B23e) record; `provino`'s replay has no recorder transform, so its Oxc path stands in for the default entry there. Without it Jest's output is unchanged.
- **`jestTypeScript: "babel"`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_TYPESCRIPT`): Jest runs the fixture's TypeScript as Jest's documentation sets it up (D123), `babel-jest` with `@babel/preset-typescript` (plus the CommonJS plugin under `jestEsm`, which stands for the documented `@babel/preset-env` at `node: 'current'`), with no type stripping first: Babel's `sourcesContent` is the whole TypeScript text. The coverage goldens use it (`coverage/v8-*`); without it the recorder's transformer is as above.
- **`captureDiff: true`** (B25b, needs `vitest` in `runners`, else `HARNESS_FIXTURE_BAD_CAPTURE_DIFF`): Vitest's JSON keeps a failure's message and stack but not the `diff` its runner prints under it (`processError`), so for this fixture the recorder also runs `reporters/vitest-diff.ts` (loaded by absolute path, Node builtins only, beside `--reporter=json`; it writes each failed test's errors' diffs, one JSON line a test, to the file `PROVINO_DIFF_OUT` names) and the Vitest golden's errors carry `diff`, normalized as the messages are (`""` is Vitest's empty diff, a `.not` failure's; an error with none has no key). Jest goldens never change. The 10 `expect/messages` fixtures set it.
- **`jestConfig`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_CONFIG`): `{ "roots"?: string[], "unmockedModulePathPatterns"?: string[] }` for the module-mock cases that need them. `roots` are directories inside the fixture (written as `<rootDir>/<dir>`; the test files must live under one), the patterns are regular-expression sources. Vitest has neither, and ignores them. `mod-corpus` hands them to the registry as its roots and `ModulePolicy.unmockedPathPatterns` for the Jest profile (`mod-roots-multiple`, `mod-unmocked-patterns`).
- **The id** is `area/behaviour`, the path of the fixture's `realpath` relative to the `realpath` of `fixtures/`; a fixture outside it gets its directory name. A symlink, `/tmp` against `/private/tmp` or a different case therefore gives the same id, which matters because the id is the golden's `suite` and names the work directory.
- **Profiles.** `vitest-list` is Vitest 5.0.5 with `sequence.hooks: 'list'` (default `stack`); it runs the same test files as `vitest` and writes `__goldens__/vitest-list.json`. The golden's `runner` stays `vitest`, and `profile: "vitest-list"` follows it; a default profile has no `profile` key. Jest equals `vitest-list` on hook order; `vitest` (stack) reverses same-level after-hooks.
- **`expectCrash`** maps profiles (a subset of `runners`) whose file must crash at collection (`crashed`: failed with zero tests) to a substring the crash's `fileError.message` must contain, e.g. `{ "jest": "Missing second argument" }` for `test(name)` with no function. The object is non-empty and every text a non-empty string. Its `fileError` is recorded. Use it only where the runner really fails the whole file; a file that fails but still ran a test is not a crash. Take the text from the recorded `fileError`, the cause that matters, not the `● Test suite failed to run` header.
- TypeScript test files: `*.test.ts` run under **every** listed runner; `*.jest.test.ts` only under Jest; `*.vitest.test.ts` only under Vitest (for `jest.mock` vs `vi.mock`). Support files (helpers) are copied but never run. Every listed profile needs at least one test file for its runner.
