# @provino/harness

Dev-only (private). Turns Jest and Vitest output into the neutral result model, diffs two runs, and records the **golden fixtures** every later bundle reuses for ground truth: policy values (T1.7), mocking probes (T4.1), runtime traces (T5.2) and matcher-message goldens (T7.1). Spec: Track 12 (F1/F2, R1/R2, Harness API, site contract). Result types are in `@provino/types` (`result.ts`, `bench.ts`); this package holds the runtime.

## Fixture format

A fixture is a directory `fixtures/<area>/<behaviour>/` (named for the behaviour, not numbered):

- `fixture.json`: `{ "description": string, "runners": ("jest" | "vitest" | "vitest-list")[], "env"?: Record<string, string>, "expectCrash"?: { [profile]: string }, "mockCleanup"?: {...}, "packages"?: { [name]: { [file]: source } }, "jestEsm"?: true, "jestConfig"?: { roots?, unmockedModulePathPatterns? } }`. Anything else is a coded error (`HARNESS_FIXTURE_*`).
- **`packages`** is written into the work directory's `node_modules/<name>/` before the run (`record.ts` `installPackages`), for fixtures that need an installed package: a root `__mocks__/<pkg>` case or an automocked CommonJS package. The name is `name` or `@scope/name`; a file is a relative POSIX path with no `..` segment and no trailing `/`, kept under its normalized spelling (`./x.js` and `x.js` are one file and a duplicate is refused); every package needs a `package.json` entry, because one without it inherits `"type": "module"` from this package and Node and Vitest then read its `index.js` as ES modules where Jest reads CommonJS. All of it is checked when the manifest is read (`HARNESS_FIXTURE_BAD_PACKAGES`), and again when written, with the same test of what leaves the package (`..foo.js` is a file name). The sources are plain CommonJS (`exports.x = ...`, so Vitest's Node loader sees the names), because Jest doesn't transform `node_modules`, `node_modules/` is gitignored and no `.js` is committed (D13). `node_modules` is not listed as a fixture file.
- **`jestEsm: true`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_ESM`): for this fixture only, Jest's transformer also applies `@babel/plugin-transform-modules-commonjs` (`transform: [path, { jestEsm: true }]` in the written config), so `*.jest.test.ts` and shared support files can use `import`/`export`, as in a real project with a Babel or ts-jest setup. Without it the transformer is exactly `babel-jest`, so older goldens don't change. Babel's interop applies: a `{ default }` factory without `__esModule` gives a default import of the whole object.
- **`jestConfig`** (needs `jest` in `runners`, else `HARNESS_FIXTURE_BAD_JEST_CONFIG`): `{ "roots"?: string[], "unmockedModulePathPatterns"?: string[] }` for the module-mock cases that need them. `roots` are directories inside the fixture (written as `<rootDir>/<dir>`; the test files must live under one), the patterns are regular-expression sources. Vitest has neither, and ignores them. `mod-corpus` hands them to the registry as its roots and `ModulePolicy.unmockedPathPatterns` for the Jest profile (`mod-roots-multiple`, `mod-unmocked-patterns`).
- **The id** is `area/behaviour`, the path of the fixture's `realpath` relative to the `realpath` of `fixtures/`; a fixture outside it gets its directory name. A symlink, `/tmp` against `/private/tmp` or a different case therefore gives the same id, which matters because the id is the golden's `suite` and names the work directory.
- **Profiles.** `vitest-list` is Vitest 5.0.5 with `sequence.hooks: 'list'` (default `stack`); it runs the same test files as `vitest` and writes `__goldens__/vitest-list.json`. The golden's `runner` stays `vitest`, and `profile: "vitest-list"` follows it; a default profile has no `profile` key. Jest equals `vitest-list` on hook order; `vitest` (stack) reverses same-level after-hooks.
- **`expectCrash`** maps profiles (a subset of `runners`) whose file must crash at collection (`crashed`: failed with zero tests) to a substring the crash's `fileError.message` must contain, e.g. `{ "jest": "Missing second argument" }` for `test(name)` with no function. The object is non-empty and every text a non-empty string. Its `fileError` is recorded. Use it only where the runner really fails the whole file; a file that fails but still ran a test is not a crash. Take the text from the recorded `fileError`, the cause that matters, not the `● Test suite failed to run` header.
- TypeScript test files: `*.test.ts` run under **every** listed runner; `*.jest.test.ts` only under Jest; `*.vitest.test.ts` only under Vitest (for `jest.mock` vs `vi.mock`). Support files (helpers) are copied but never run. Every listed profile needs at least one test file for its runner.
- Tests use the runner globals (`describe`, `it`, `expect`, `jest`, `vi`) and the recorder's `trace`. Type annotations are fine; the syntax must be erasable (no `enum`).
- **`trace(step: string)`** is a global the recorder installs (a setup file, `internal/runner-config.ts`). Each call appends one line to a file the recorder names in `PROVINO_TRACE_FILE`; after the run the lines become the golden's top-level `trace: string[]` (last key; absent when nothing was traced). A step is one line of text. A fixture that traces needs **exactly one test file per runner** (`HARNESS_TRACE_MULTIPLE_FILES`), because parallel files would interleave. `files[].trace` is the result model's structured hook trace and the recorder never fills it.
- Fixtures carry **no runner config**: the recorder writes it (see `internal/runner-config.ts`).
- `__goldens__/<profile>.json`: written by the recorder, never by hand.
- **The runtime corpus** (`fixtures/runtime/`, T5.2) is read by Provino's core later through Node's native `import()`. Its files use only globals and `trace`: no `import`, no `require`, no `expect` (fail with `throw new Error(...)`). Timeouts are at least 50 ms and overruns at least 3x; concurrency uses `setTimeout`s whose gaps are 20 ms or more, never microtask races. `pnpm record:runtime [--check]` records or checks it.
- **The corpus check** (`src/runtime-corpus.test.ts`) runs each fixture's one test file through `@provino/core` under each profile's policy and compares it with that profile's one golden file: trace; title path, `dupIndex`, status and location of each test; file status; **where the errors are** (a test's `errors` and the file's errors, by presence only, because core's messages are neutral); and, for a golden that crashed, the `CoreError` code of the collection error (`COLLECTION_ERROR_CODES` in the test, keyed `fixture (profile)`; a test fails unless its keys are exactly the pairs whose `fixture.json` has `expectCrash`). A golden test with no location is skipped by the location check, so each one is named in `UNLOCATED_TESTS` (today only Jest `timeouts` › "test over its timeout", whose location Jest's JSON drops) and every golden must have exactly its named list. A collected test the core never ended is `no-result` and fails. The file error is not compared when a golden test failed: the converters drop a file message that repeats a failed test (`assembleFile`). A comment in `profiles.ts` (or, for Jest, `packages/dialect-jest/src/dialect.ts`) says "runtime corpus X agrees" only if flipping that value makes the check fail; the unit tests for the pieces are `runtime-corpus/*.test.ts`.
- **The expect corpora** (`fixtures/expect/`, T7.1). `messages/` (10 fixtures, jest and vitest): each test makes exactly one failing assertion. A few make passing assertions first, to pin `passingAssertions`. Shared cases are `*.test.ts`; Jest-only cases (`jest.fn`, `expect.arrayOf`, `expect(a, b)`, a removed alias) are `*.jest.test.ts`, with `vi.fn` twins in `*.vitest.test.ts`. `policies/` (6 fixtures) records the async and assertion-count policies (F7, P1–P7); T7.8 (B17) reads them, and nothing checks them yet. There's no snapshot corpus yet: T7.9 adds it with `.snap` capture. `pnpm record:expect [--check]` records or checks both.
- **The expect check** (`src/expect-corpus.test.ts`, T7.5) runs each `messages/` fixture's Jest files through core with `expect` built the way the worker will build it, and `jest.fn`/`jest.spyOn` from `@provino/mock` under `jestMockPolicy`. Per test it compares status, each error's `name`, normalized `message`, `matcher` and `userFrame`, and `passingAssertions` with the Jest golden. Jest's `failureMessages` entry is the error's `stack` (jest-circus `getErrorStack`), so the run's text goes through the same `normalizeError`. Each fixture runs from its own directory, because `toThrow` prints the thrown error's stack relative to `process.cwd()`. The golden's `matcher` is Jest's `matcherResult.name`; the run's is `SerializedError.matcherResult.name`, which core copies from the error (with `pass`, nothing else).

- **The mock check** (`src/mock-corpus.test.ts`, T4.3, T4.4) runs each counted `fixtures/mocking/` fixture under each of its profiles and compares every `observe` line with the golden's `trace`, by case id and exact text, with a fresh registry and files in their own order (`invocationCallOrder` depends on it). Under Jest, `jest` is the object `jestGlobals` ships (host `mocks()` is the file's registry), so its wiring is checked; Vitest's is local until T1.8. Core's per-test results are checked too: every test the golden lists ran with the golden's status (Jest `hazard-frozen-spy`, a crashed golden, is exempt because its `fixture.json` has `expectCrash`, and must pass every test), and the cases come in the golden's order. The bar is every case except `DECLARED` (`fixture (profile) case` to a DV id and the exact line the engine may give): an undeclared difference fails, so does a declared case that now matches, and so does one that gives another line. `api-surface` is recorded for T11.10 and not counted. The totals are exact (`EXPECTED_COUNTED`), and an empty fixture fails; the brief's bar was Jest 72 and Vitest 74. `between.order` and Jest's `unstubEnvs`/`unstubGlobals` have no corpus backing (no case tells one order from another). A fixture whose message holds a function's source must keep quotes out of it: V8 prints the source, and Vitest's transform re-quotes strings inside it (`fn-new`).

- **The hoist check** (`src/hoist-corpus.test.ts`, T3.4) runs each input through real `babel-plugin-jest-hoist` or Vitest's `hoistMocks` and through ours, and compares, in order: the `HOIST_*` code (each real message maps to one, and an unmapped one fails), the hoisted order, `staticMocks` (`onStaticMock` for Vitest; read from the real output for Jest), and a run: each output goes through its real next step (Babel's CommonJS plugin, or the module-runner form) and runs against recording stubs, and the logs must match (calls and arguments, loads, reads, `this`, exports read twice, factories at their load). An allowance is named per case (`SKIPPED`, `REAL_HOISTER_QUIRKS`), and a test fails when a quirk's entry is no longer needed. It can't pass with a wrong engine: `identity` has an exact count, sabotaged engines must fail for a named reason, and each `HoistPolicy` key has a flip that fails, or a reason in `UNPROVABLE`. A new key fails until it has one. A "hoist corpus agrees" comment is true only if that flip exists. All counts are pinned.

- **The mod check** (`src/mod-corpus.test.ts`, T4.7, B13b) runs each `mocking/mod-*` fixture under each of its profiles through a **fake loader** (`mod-corpus/fake-loader.ts`, test-only): a temp copy of the fixture with its `packages` installed (`record.ts` `installPackages`), the real resolver, the real pipeline with the profile's `HoistPolicy` (`jestHoistPolicy`, `vitestHoistPolicy`) and `toModuleRunner`, evaluated with the real loader's wrapper (plus `require` in an ESM wrapper, for Jest's `injectCjsGlobals`, and `jest, vi` as parameters). Every import edge resolves, asks `registry.decide` (`decideUnresolved` on a miss) and takes `materialize` or the real module from a per-file cache; `resetModules` and `isolateModules` act on the cache layers and the registry. A hoist diagnostic with `severity: 'error'` fails the file. `mod-corpus/facades.ts` builds the per-module `jest`/`vi` over the registry (the mock functions are `jestGlobals`' under Jest and `createViFacade`'s under Vitest), so a call's `from` is the calling file; `mod-corpus/run-mod.ts` runs the file through `@provino/core` and removes the globals the fixture added. The comparison is `mock-corpus`'s (by case id and exact text, in order, test statuses), plus the file's own outcome on every fixture (`assertFileOutcome` in `mock-corpus/compare.ts`, also used by `mock-corpus.test.ts`: file status, which tests carry errors, whether the file carries one), and for a crashed golden its cause text (`causeText`: the first paragraph after Jest's `● Test suite failed to run`, or Vitest's first paragraph, `<root>` applied, a leading `XError: ` dropped on both sides, the `Allowed objects:` line left out), which must equal what we raised, with `DECLARED` and exact totals (`EXPECTED_COUNTED`). Two broken engines must disagree with the goldens on an exact number of cases per profile (`EXPECTED_DISAGREEING`; the counts move when a defect is fixed, because a case that failed for a reason the registry has no part in then agrees under both): `inert` (`FakeLoaderOptions.sabotage`: no import edge asks the registry, root mocks included, and the facades drop registrations) and `wrong-values` (the registry decides and runs its factories, then every mocked edge gets an empty module). **What the fake presents like the real runners, because the goldens force it, all read from `ModulePolicy.interopDefault`** (Jest `babel`, Vitest `node`, the Vitest value set in `vitestModulePolicy` from these goldens; no harness flag): under `babel` an ES module's exports object is plain with a non-enumerable `__esModule`, `loadActual` serves its names sorted, and a CommonJS value seen through `import` is Babel's wildcard (a value with `__esModule` is its own namespace, otherwise `default` first, then the keys); under `node` the exports are a null-prototype `Module` namespace in source order, and a CommonJS value is Node's namespace (every key sorted, `default` among them, `Module` tag, whatever the value carries). `loadActual` serves getters over the live exports, as the runners do, so automock's getter and `Module` rules run. Two loader behaviours the goldens show and a policy value doesn't carry: a Jest transform error reads `<file>: <message>` (`ModProfile.prefixTransformErrors`), and a Vitest file whose load fails on an unresolved relative mock reads `... imported from <test file>` (an import from inside a test doesn't). A file with no import or export syntax but a dynamic `import()` is run in module form. **B13c replaces this with the real loader and the shipped `jest`/`vi`** and must give it the same behaviours (`mock-corpus` and this check are its acceptance, T4.8): in particular `cjsView` must order a CommonJS value's namespace by `interopDefault` (`babel`: `default` first, then the value's keys; `node`: all keys sorted with `default` among them), and not `keys then default` as it does today, and its `default` must be `module.exports` for `node` even when the value has `__esModule`. A mocked value served under `factoryShape: 'module-value'` goes through the same CommonJS interop (`#mocked` in `fake-loader.ts`), so B13c's mock edge must do the same, not only the real-module edge.

## Recorder contract

`recordFixture(dir, profile, { check?, keepWorkDir? })` copies the fixture to a fresh directory under `.record/` (inside the package, so `node_modules` resolution finds the runners), writes the runner config and the trace setup, and runs the pinned Jest 30.5.2 / Vitest 5.0.5 with `CI=1`, `TZ=UTC`, `NO_COLOR=1`, `LANG=LC_ALL=C.UTF-8` (`LANGUAGE` and other `LC_*` removed) and the fixture's `env`. It converts the JSON, normalizes with that directory as `<root>`, and writes the golden: a `NormalizedRun` without `startedAt`, `env`, every duration and every `raw` (the runner's text holds machine paths), plus `profile` and `trace` where they apply. Keys are in a fixed order; 2-space JSON and a trailing newline. The work directory is deleted afterwards (`--keep` leaves it, check mode included); a failed cleanup never replaces the original error. A signal ends the CLI through `process.exit`, which skips that cleanup, so `internal/work-dirs.ts` keeps the live work directories in a set and removes them in an `exit` listener (not with `--keep`).

- **A failing test inside a fixture is expected; a broken run is not.** `HARNESS_RUN_INCOMPLETE` unless the result files equal the fixture's test files for that runner exactly, no file is `crashed`, no file has zero tests, and `runErrors` is empty. The message says which, with a crash's `fileError`. With `expectCrash` for the profile the rule inverts: every result file must be `crashed`, else `HARNESS_EXPECTED_CRASH_MISSING`, and each crash's `fileError.message` must contain the named text (a crash with no `fileError` fails too), else `HARNESS_EXPECTED_CRASH_MISMATCH`; a missing file and `runErrors` still fail. A missing or unparsable JSON file is `HARNESS_RUNNER_FAILED`.
- **Trace.** Read after the completeness check; non-empty with more than one test file for the profile is `HARNESS_TRACE_MULTIPLE_FILES`. It is part of the golden text, so `--check` compares it.
- **Leak guard.** `HARNESS_GOLDEN_LEAKS_PATH` if the serialized golden contains the work dir (or its realpath), the repo root, the package dir or the home dir. Fix the normalization rule, never the golden.
- **Timeout** (2 minutes, `TIMEOUT_MS` in `record.ts`) is the harness's own deadline: the runner is spawned with `spawnInGroup`, so on timeout the whole process group gets SIGTERM, then SIGKILL after 2 s, and the run settles 0.5 s after the child exits even if a grandchild holds the pipes. The CLI calls `exitOnSignals()`, so Ctrl-C, SIGTERM and SIGHUP end it with exit code 128 + the signal number, and the exit hook in `spawnInGroup` kills the group on the way out (it is registered first among the `exit` listeners, so the work directory is removed after the group is gone). A grandchild that starts its own session is out of reach.
- **`--check` also fails on stale goldens:** any `__goldens__/*.json` this run did not produce (runner removed from `fixture.json`, no manifest, stray file). With directories given, only those are scanned.

**To add a fixture:** make the directory, write `fixture.json` and the tests, run `pnpm provino-harness record packages/harness/fixtures/<area>/<behaviour>` from the repo root (a directory of fixtures such as `fixtures/runtime` works too; no argument records all), read the golden, and commit it. To change a golden, re-record it and say why in the commit. CI runs `provino-harness record --check`, which exits 1 on drift.

## The self-test sample (T12.6) and the parity commands

- **`sample/`** is one fixture in the fixture format (`fixture.json` with `jestEsm`), outside `fixtures/`, so `record` never reads it (its completeness rule refuses one crash among passing files). It is the spike's 63-test sample rebuilt in TypeScript from Track 12 Spikes A: 18 file keys, 88 tests, every listed feature, the F3 divergences, and `normalization-inputs.test.ts`, which throws and prints the text the rules exist for. `crash.test.ts` must crash, and nothing else may (`internal/sample.ts` `sampleRunProblems`).
- **A per-dialect pair is one file key.** `modules.jest.test.ts` and `modules.vitest.test.ts` are copied as `modules.test.ts` into their runner's copy (`sampleCopy`), so both runs report one file. `exclusions.json` and `__recorded__/` are never copied.
- **`self-test`** runs Jest (`--ci -u`) and Vitest (`run -u --allowOnly`) each in a fresh copy under `.record/` with `runner-config.ts`'s configs and `CI=1`: `-u` against an empty snapshot directory is R2's snapshot set, and Vitest refuses `.only` under CI otherwise. Then it checks, one line each: every file ran, the golden of the fresh run equals the golden of `__recorded__/<runner>.normalized.json`, the sidecar wrote `console.test.ts`'s lines (Jest per file in call order; Vitest per test, each stream in order), and the calibrated diff (matcher mode, console on, the 4 rules, `--max-diffs 0`): all three parities 1, `suitePass`, each rule matched a diff, ≥63 tests, ≥16 files, exactly the one crash. CI's `suites` job runs `self-test --candidate provino`. `--candidate provino` runs the `provino` bin on the Jest copy (`provino.config.ts`, `--no-cache`), passes when it exits 0 or 1 with a valid `normalized-json`, and writes the exact-mode `ParityReport` to `--out`. It prints no Provino number (public CI logs).
- **The 4 calibration rules** (`sample/exclusions.json`, D30: no `expires`, read only with `--calibration`) are the spike's three (`div/beforeAll-failure-status`, `div/mockReset-restores-impl`, `div/snapshot-file-format`) and `div/runner-made-error-frame`, which Tyler added at B15. Jest gives an error it makes itself (a thrown string, a `test.failing` that passed) the stack captured where the test was defined, so it has a user frame; Vitest has none. That rule is `kinds: ['user-frame']` with `absentIn: 'candidate'` (it matches only a diff where Vitest has no frame), no key glob, and no policy key yet. B15's first calibrated diff had a third unexplained frame, `toThrow`'s, which was a parse of Jest's message layout and is fixed in `internal/stack.ts` (see Gotchas → Stack and frame rules).
- **`__recorded__/`** is written only by `self-test --write-recorded`: each runner's JSON (pretty-printed) and sidecar with the work directory, the repository and the home directory rewritten to `/__root__`, `/__repo__` and `/__home__` (`rewritePaths`, only where a directory ends: a separator, a quote or the end of the text), checked by `assertNoPathLeak`, and their conversion with `/__root__` as the root and a neutral `env` (`recordedEnv`: the runner's version and the Node major; every machine field `unrecorded` or 0, because the repository is public). `convert-recorded.test.ts` converts the committed raw files and must get the committed run; `normalize.fixtures.test.ts` takes T12.2's cases from them. Biome skips the directory.
- **`diff`** reads two `NormalizedRun` files (`parseNormalizedRun`), so a golden can't be diffed: it has no `env`, `startedAt` or `raw`. `--min` is status parity (R2's gate metric), which can't see a message or console diff: `--max-diffs` is the bar for those. `--max-excluded` counts the tests exclusion rules remove from T (`counts.excluded - counts.flaky`) over the reference's tests; the sample's are 3 of 88, over 2%, which `--calibration` allows (D30). A rule can match by kind, key glob, runner pair and `absentIn` (`reference` or `candidate`: only a diff where that run has nothing).
- **`diffRuns` for a `provino:*` candidate** treats a matcher name (matcher mode) or a passing-assertion count that the reference has and the candidate lacks as a diff (B02's deferral); Vitest's JSON has neither, so for it a missing field can't disagree. Flaky keys (`DiffOptions.flaky`) leave T and report nothing.

## Shared with the bench

`@provino/bench` imports these from the package entry, so there is one of each:

- `spawnInGroup(command, args, { cwd, env, stdio, timeoutMs?, deadline?, killGraceMs? })` returns `{ child, exited }`. The child leads its own process group; `exited` settles after it exited and the group is gone (members left behind get `killGraceMs`, then SIGKILL). It installs no signal handler. `exitOnSignals()` is for entry points (`cli.ts` calls it).
- `runProcess(command, args, options)` is `spawnInGroup` plus captured output (the tail, a pipe grace, `wallMs`).
- `readRunEnvironment(runners)` and `resolveRunnerPackage(name, from)` replace the recorder's and the bench's own copies; `parseJestJson` and `parseVitestJson` read the runners' JSON.

## Commands (from the repo root)

## Gotchas

- **Jest runs fixtures as CommonJS.** Unless the fixture sets `jestEsm`, no ESM-to-CommonJS transform is installed (`babel-jest` alone only hoists `jest.mock`), so an `import` in a Jest fixture crashes the file (`Must use import to load ES Module`). In `*.jest.test.ts` use `require('./helper.ts')` (with an `as` type); `jest.mock` is hoisted above it. In `*.vitest.test.ts` use `import` and `vi.mock`. A shared `*.test.ts` can use globals only. With `jestEsm`, both runners can share ESM support files; load lazily with `require` under Jest and `await import` under Vitest.
- **A Jest transform error loses its stack and one line.** `jest-transform.ts` drops the stack of an error from Babel (it names this machine's `node_modules` and the transformer's own path, so the golden would leak them) and the `Allowed objects: ...` line of the out-of-scope error (the list follows the Node version). The message and its code frame text stay.
- **`jest.mock` factories may use pure constants.** `babel-plugin-jest-hoist` hoists a `const x = 'literal'` along with the factory, so `mod-factory-out-of-scope` uses `String('...')`, which it cannot hoist. A top-level `jest.fn`-free `mockCounter` function declaration is hoisted by JS itself and is allowed (`mock` prefix).
- **Where the two runners resolve differently (the `mod-*` slice).** A `vi.mock` of a relative path that is not on disk fails with `Cannot find module '/x.ts'` (a static import fails the whole file, `mod-virtual-static`); a bare name that is not installed works. `doMock` after a load gives the mock on the next load in both runners with no `resetModules`. Jest's non-hoisted unmock is `dontMock` (there is no `doUnmock`).
- **Node below 22.18** needs `NODE_OPTIONS=--experimental-strip-types`: the Jest child loads the `.ts` transformer through `require()`, and it inherits the environment. Not run on 22.15 here (Node 24.22 and 26.12 were).
- **`ExperimentalWarning: stripTypeScriptTypes`** appears on Node 24.22 in Jest's stderr. Harmless; the recorder shows the runner's output tail only when no JSON was written.
- **Biome skips `__goldens__/`** through `!**/__goldens__` in the root `biome.json`. Without it `pnpm format` reflows the arrays and `--check` reports drift.
- Jest's `--json` assertions carry `numPassingAsserts` and `failureDetails[i].matcherResult.name`, but its types omit them, so the converter reads them from `unknown`. Jest's file-level `message` prints paths relative to the root (`a.test.ts:7:23`); `userFrame` becomes `<root>/a.test.ts:7:23` either way.
- Jest `pending` is `it.skip`, `xit` and tests left out by `.only` or `-t`; the JSON can't say which, so `skipReason` is `unknown`. `focused` is a **file** status (passed, some tests didn't run).
- Neither JSON carries console output, so `console` is absent in goldens (the recorder doesn't use the sidecars) and in a conversion without `ConvertOptions.console`. `crashed` files take their `fileError` from the file-level message.
- **The sidecars.** Jest drops `testResult.console` once the reporters have seen it, so only a reporter can read it; `--silent` empties it, so `runSubject` passes `--silent=false`. Jest's entries carry a level (its `LogType` has no `trace`); the stream follows Node's `Console` (`warn`, `error`, `assert` and `trace` on stderr). Vitest's `onUserConsoleLog` has no level, merges adjacent writes to one stream, and reports a test's stdout before its stderr, so only each stream's order is defined; `taskId` resolves through `vitest.state.getReportedEntityById` to a test (per test, with `dupIndex` counted over `module.children.allTests()`), a suite or a module (per file). Each entry is split on `\n` and each line normalized with `normalizeText`, so a CR before a split newline stays (`crlf` can't fire on a console line).
- **`runSubject` flag order.** Jest's `--reporters` is an array flag that takes a test path after it, so the harness's flags go after the caller's argv. Jest also gets `--verbose=false`: `@jest/core` turns verbose on for a single test file, and a verbose worker writes console to the terminal instead of buffering it (30.5.2 still buffered when probed). `runSubject` removes the runner's JSON and sidecar from `outDir` before it starts, so a run that writes none fails instead of reading an earlier run's.
- **Test keys are unique by construction.** `testKey` joins the title path with ` › ` after escaping `\` and `›` inside each title (`keys.ts`), so different title arrays never share a key, and `dupIndex` counts tests with the same file and the same path array, as `@provino/types` documents. `describe('a', () => it('b'))` and `it('a › b')` are different tests (`a › b#0` and `a \› b#0`). `diffRuns` still throws `HARNESS_DUPLICATE_TEST_KEY` if a hand-built or foreign run repeats a key. A `null` in Vitest's `failureMessages` (`throw { status: 404 }`) becomes one error with the message `<no message>`.
- **A failed file with passing tests** (a hook after the last test) keeps its status and takes `fileError` from the file message, for both runners and both Jest shapes. When a test failed, the message repeats that failure, so there is no `fileError`.
- **Stack and frame rules.** A frame is `at <fn> (<loc>)` or `at <loc>`, with `<loc>` ending in `:line:col` or `<anonymous>`, `native`, `index N`; only the trailing run of frames is the stack (plus any run followed by a `[cause]:` or `Caused by:` line, Jest's cause chain), so frame-shaped text inside a diff stays in the message. The run's frames are indented alike: Jest's `toThrow` prints the received error's code frame and stack (6 spaces) right above its own stack (4 spaces), and that block, when it follows Jest's `Received message:` header (`Error message:` for a bare `.not.toThrow()`) with only blank and code-frame lines between, is dropped from both the stack and the message, so the user frame is the matcher call, as Vitest gives it; differently indented frame lines anywhere else stay in the message (B15; `expect/messages/throws` and `promises` were re-recorded for it). A frame is internal if it names no file (`<anonymous>…`, `native`, `index N`, an unreadable `eval at`) or its file path matches `node:`, `node_modules/`, `jest-circus` or `vitest/dist`; the function name is not looked at. An eval frame uses its origin. `internal/stack.ts` parses a failure once into segments (split at cause lines), each with its message lines and its frames. The path rules (ansi, crlf, file-url with 1-3 slashes, root, windows) run on the whole text, the code-frame, duration and placeholder rules on the message only, so `test/tmp/` and `10s.test.ts` survive in `userFrame`.
- **Narrow rules, on purpose.** `<root>` needs a path boundary on both sides (`/home/me/work/fixture`, `/work/fixture@1` and `/work/fixture copy/` are not the root). Durations are only `(12 ms)` and a `Time: 1.2 s` line, so configured timeouts and user strings stay. `<root>\n` is only converted to `/` when a configured root is a Windows path.
- **Parity counts.** `counts.excluded` is `referenceTests - comparedTests`: tests removed from T by a status or `missing-in-candidate` exclusion, or as flaky (`counts.flaky` of them). A test leaves F only when all its message-family diffs are excluded. The JSON guards check each file's status per runner, and Vitest's rejects Jest-only fields.
- Files in a converted run are sorted by path (runners list them in completion order); tests stay in declaration order.
- Vitest may print `ERROR: failed to copy trust settings of system certificate` on macOS. It is stderr noise.
- `diffRuns` drops an exclusion per diff kind, not per test: an excluded `message` diff never hides a `status` or `user-frame` diff on the same test. Console compares per test only when both runs attribute any; the concurrent-test multiset rule (R1) needs a marker the model doesn't carry yet. Jest attributes nothing, so a Jest reference compares every file's console as a sorted multiset, and hook order can't show (B15 gap 9).
- **Trace setup.** `internal/runner-config.ts` writes `.harness-out/trace-setup.ts` (Jest `setupFiles`, Vitest `test.setupFiles`). It has no import (Jest runs it as CommonJS) and uses `process.getBuiltinModule('node:fs')` with a synchronous append, so steps land in call order even for concurrent tests. The recorder, not the fixture's `env`, sets `PROVINO_TRACE_FILE`.
- **`.only` under the recorder's `CI=1`.** Vitest's `allowOnly` is `!isCI` (std-env also reads CI-provider variables), so `.only` is rejected: the `.only` tests carry the error and no test runs, but the file is not `crashed`. `only-scope` records that; Vitest's `.only` semantics with `allowOnly` on are not recordable here.
- **What Vitest's JSON drops.** Suite-level errors (a throwing `beforeAll`/`afterAll`, an empty suite) are not in the report: the file is `failed`, the tests keep their status, and `fileError` is absent. Jest's file message does carry them (`● Test suite failed to run`).
- A Jest describe with hooks but no tests makes the file `failed` and still runs its other tests, so it is not an `expectCrash` case; `test(name)` with no function, `test.todo(name, fn)`, an async describe callback and a describe callback that returns a value are.
