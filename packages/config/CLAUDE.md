# @provino/config

Loads a project's config file and resolves it into everything the coordinator and its workers need (coordinator side; imports `@provino/types` and `@provino/policy` only). B11 built the first part of T1.4: `loadConfigFile`, `resolveProject`, `loadProject`. The built-in dialects and environments come from the caller (`provino`), so this package names no dialect and no environment package, and never imports one.

## Map

| Path | Role |
|---|---|
| `src/load.ts` | `loadConfigFile(path, env)`: the `provino.config.*` loader (build-plan §6). It imports the file afresh through a private `importConfigModule` (not exported) and takes its default export, unwrapped like `interopRequireDefault` (`interopDefault`, exported, which the orchestrator also uses to read a global setup module's `default`), then calls it when it is a (maybe async) function of `ConfigEnv`; the result must be an object. The Jest dialect doesn't use it: Jest's configs, presets, resolvers, reporters and plugins load as jest-util's `requireOrImportModule` loads them (`packages/dialect-jest`'s `load.ts`, cached as in Jest). `loadProject(path, options)`: load, then resolve (`env` defaults to `{ command: 'run', mode: 'test' }`) |
| `src/resolve.ts` | `resolveProject(input, options)` → `ResolvedProject` for a `provino.config.*`; `resolveNeutralProject(neutral, options)` → the same for a project a dialect's config reader produced (`ConfigReader.toNeutral`, B14b). Both parse their input, then share `finishProject`: policy layers, environment, isolation, setup files, the `SerializedProjectConfig` and its ref check |
| `src/projects.ts` | `resolveProjects(input, options)` → `ResolvedConfig` (`projects`, `root` when the config has `projects`, `pool`, `maxWorkers`, `execArgv`), `loadProjects(path, options)` (B27d). No `projects` (or an empty list) is the one project; with `projects` each entry is an inline object, a directory, a config file path or a glob (tinyglobby, D199: directories only, never `node_modules`; an entry starting with `!` leaves out what the globs match; a glob never matches the config's own directory). A directory takes its own `provino.config.*` when it has one, and is named for its directory unless the config names it. The top-level keys are **not inherited**; a project has no `projects`, `pool`, `maxWorkers` or `execArgv` (they are unknown keys to it). Duplicate non-empty names, a glob that matches nothing and a missing path are `CONFIG_INVALID`. Two projects may share a `rootDir` (disjoint `include` globs, one `src/` in node and jsdom): config can't know their files, so `ResolvedConfig.uniqueFiles` (always `true`) tells the orchestrator to refuse a run in which one file is discovered by two projects (`ORCH_OVERLAPPING_PROJECTS`, `packages/orchestrator/CLAUDE.md`); `resolveProject` itself refuses a non-empty `projects` |
| `src/discover.ts` | `findConfigUpward(from)` (D196: `from`, then each parent, stopping after the first directory with `.git` or `pnpm-workspace.yaml`; it looks for `provino.config.*` only: `provino`'s `detectProject` applies D200's nearest-config rule over Jest and Vitest configs too and uses `findConfigInDirectory`), `findConfigInDirectory`, `PROVINO_CONFIG_EXTENSIONS` |
| `src/define.ts` | `defineConfig`: an identity function typed by `ProvinoConfig` (a `const` type parameter, so literals keep their types and a function's `env` is typed) |
| `src/errors.ts` | `ConfigError` with a `code` (`ConfigErrorCode`), for bad dialect options `issues`, and `subject` (B27f): the dialect `CONFIG_UNKNOWN_DIALECT` was asked for, or the top-level key `CONFIG_UNKNOWN_KEY` refused, as data (`provino` reads it to tell a missing add-on from a typo); `formatConfigIssue` (the `  path: message` line, `(options)` for an empty path), used by the dialect-options message and by `provino`'s error text |
| `src/internal/input.ts` | `parseInput` (one `optional(input, key, expected, guard)` per key), plus the shared `isString`, `isStringArray`, `messageOf`: checks each key `resolveProject` reads (`CONFIG_INVALID`), refuses `plugins` and `alsoServe` when non-empty (`CONFIG_UNSUPPORTED`, naming the key), and refuses an unknown own key (`CONFIG_UNKNOWN_KEY`, with the nearest known key by edit distance when one is close, B27d; a key of the whole run in a project says it "belongs to the top-level config only" instead). A known key is a project key, a top-level key (top level only), the name of a dialect in the config's `dialects` (else the caller's: the options of a dialect the project doesn't list are an unknown key) or of a plugin the config lists. `timeouts` and `resolve` check their own keys too |
| `src/internal/dialect.ts` | `selectDialect` (by name, else by `detect`), `dialectPolicy` (a factory gets `config[name]`, checked by the dialect's Standard Schema first), `dialectsFor` and `loadOnce` (the lazy `loadDialects`, below) |
| `src/transform-cache.ts` | `withTransformCache(project, dir)` (T3.6): wipes the transform cache directory when the lockfile changed, and returns the project with `config.loader.cacheDir = dir` (the original is untouched); `pruneTransformCache(dir)`. The orchestrator calls both; `@provino/transform` does the work. |
| `src/internal/refs.ts` | `assertWorkerConfig`: the finished `SerializedProjectConfig` is checked before `resolveProject` returns it (see "Refs") |
| `src/internal/transform.ts` | `resolveTransforms` (a neutral project's transform entries as `loader.transform`, T3.8) and `resolveTransformClaims` (B23e: the files the transforms take as `loader.transformClaims`); see "Transform entries and claims" below |
| `src/internal/setup-files.ts` | `resolveSetupFiles`: `setupFiles` entries to absolute paths, each checked to be a file |
| `src/internal/test-support.ts` | Temp dirs, `rejectsWith` and the `pipe` dialect, for the tests |

## Rules that aren't obvious

- **The config's keys are layered into the policy,** not only read beside it: `include` and `exclude` go over `orchestrator.include`/`exclude`, and `globals` over `core.injectGlobals`. The worker reads `policy.core.injectGlobals` *and* `config.globals !== null` (both must hold), so layering keeps the two in agreement. `ResolvedProject.include`/`exclude` are read back from the resolved policy.
- **Dialect choice:** a `dialect` name picks from the dialects the caller gave (a config's own `dialects` list *replaces* theirs, as `BaseConfig.dialects` says "default: the built-ins"); no name picks the highest `detect` score above zero; a tie is `CONFIG_DIALECT_TIE`, not a guess; no match is neutral (`dialect: null`, no globals). `detect` runs only when some dialect has one, and then reads the root's file names and `package.json` once.
- **Dialect options** reach a policy *factory* only (`config[dialect.name]`, through `dialect.options` when present, even when the value is `undefined`, so a schema can supply defaults). A plain policy never sees `config[name]`. `Dialect.policy` is typed bivariantly, so the compiler can't check the factory's argument: this validation is the check.
- **Environment:** the config's name, else `policy.orchestrator.envDefault`, looked up (own keys only) in the caller's table. `EnvironmentRef.options` is `{}`: config's `environment` is a name, so there are no options to give. (B10 noted `EnvironmentRef.options` and `EnvironmentOptionsMap` don't assign without a cast; nothing here builds one from the map, so the cast never came up. T1.4's `environment()` helper will meet it.)
- **Isolation:** the config's, else `isolationDefault.byEnvironment[env]` (own keys only), else `isolationDefault.default`.
- **Neutral projects (`resolveNeutralProject`):** the caller gives the dialect (the one whose reader produced the project) and the environments; the package still names none. The layers are the dialect's policy (a factory gets `undefined`), then `neutral.policy`. The project's `setupFiles` stay the worker's `setupFiles` (before the framework) and its `setupFilesAfterEnv` the worker's; each must be an absolute path to a file (`CONFIG_INVALID` naming `setupFiles[i]` or `setupFilesAfterEnv[i]`). `environment.options` reaches `EnvironmentRef.options`. `discovery` is carried to `ResolvedProject.discovery` (`null` for `resolveProject`). The orchestrator's `discoverProject` reads it (B14c): rules when present, `include`/`exclude` otherwise, and the results cache key includes it.
- **Global setup (T9.15):** a neutral project's `globalSetup` and `globalTeardown` (absolute paths, checked as the setup files are: a relative one is `CONFIG_INVALID`) become `ResolvedProject.globalSetup` (`ResolvedGlobalSetup`: `setup`, `teardown` and, from the reader, `args`, the two configs a Jest hook is called with, as the reader built them and not JSON, since they never leave the coordinator: `NeutralProject.globalSetupArgs`); absent when the project has neither hooks nor args (a project with no hook of its own keeps `{ setup: [], teardown: [], args }` when the run has one, Jest's root `globalSetup` with `projects`, which is called with the first project's config). It stays on the coordinator side: nothing of it goes into `SerializedProjectConfig`, since the coordinator runs the hooks (`@provino/orchestrator`'s `runGlobalSetup`). A `provino.config.*` project has no such key yet.
- **B27d keys:** `timeouts` go over the policy's `core.timeouts` (after the dialect's); `resolve.conditions` are appended to the environment's (no repeats); `resolve.aliases` become `loader.aliases` (one `*` anywhere in the key is the capture, and the one `*` in the target, which the key then needs, is it: `'@/*': './src/*'` is `^@/(.*)$` to `<root>/src/$1`; a key without `*` matches only itself; more than one `*`, or one in the target alone, is `CONFIG_INVALID`); `resolve.tsconfig` is `loader.tsconfig` (`'auto'` by default; a path is made absolute against the root, and the loader turns its `paths` into aliases); `environmentOptions` (JSON) reach `EnvironmentRef.options` and the conditions behaviour; `pool` and `maxWorkers` are `ResolvedConfig` defaults for `run()`, which the command line overrides; `execArgv` (D206; `isNodeFlags`: non-empty strings, a flag first) is `ResolvedConfig.execArgv`, top level only, with no command-line counterpart.
- **No dialect named means native.** A config with no `dialect` and no dialect whose `detect` scores above 0 resolves with `dialect: null`: the neutral policy, and `ResolveOptions.native`'s refs when the caller gives them (`jestDialect` has no `detect`, so a Jest project must say `dialect: 'jest'`). `provino`'s `run()` hands the Jest dialect to `resolveProjects` only through `loadDialects`, so a native project imports none.
- **Lazy dialects (B27e):** `ResolveProjectOptions.loadDialects` is called only for a config (top level, an inline project, a directory's own file) that needs a dialect `dialects` lacks: a `dialect` not among them, or an own key no project, run or listed plugin reads (a dialect's options key; `needsMoreDialects` in `input.ts`, which reads the same `knownKeys` list as `CONFIG_UNKNOWN_KEY`). A config with its own `dialects` never calls it. What it gives joins `dialects` for that config's names (a name already there keeps the eager entry), **never for detection**: `selectDialect`'s `detectAmong` is the eager list, so a dialect with `detect` that only the loader gives is used only when named. It is called at most once (`loadOnce`, shared by `resolveProjects` and each `resolveProjectInput`; a synchronous throw becomes the rejection), and a throw, a rejection or a result that isn't an array is `CONFIG_LOAD_FAILED` with the error as `cause`, the same failure for each project that needed it. `projects.test.ts` ("loadDialects") holds each case.
- **Setup files:** the neutral `setupFiles` become the worker's `setupFilesAfterEnv` (as Track 11 maps Vitest's); the worker's `setupFiles` stays `[]`. An entry is a relative path (`./`, `../`) or an absolute path, resolved against `rootDir`, or a `file:` URL (through `fileURLToPath`). Anything else is a package specifier, resolved from `rootDir` as an import would (`@provino/resolver`, imported only then, with the conditions `node`, `provino-source` and the project's `resolve.conditions`), else as `createRequire(root).resolve` does for a package only `require` reaches (B27d; `CONFIG_INVALID` naming the entry when nothing resolves it, and for a `<rootDir>` token). Each result is `stat`ed and must be a file, else `CONFIG_INVALID` naming the entry (`setupFiles[i]`).
- **Root:** `rootDir` must be an existing directory (`stat`), checked in `resolveProject` and reported before any other failure (it runs beside `detect`'s read of the root, and its error wins if both fail), whether or not a dialect has `detect`. A missing root would find no tests, and `passWithNoTests` would exit 0.
- **Refs (D21):** `assertWorkerConfig` runs last. Every `{ module, export }` ref in the serialized policy, `globals` and `environment` must be a plain ref whose `module` is an absolute path or a URL (`isImportableLocation` from `@provino/policy`, the rule the worker's config check uses too; the walk over the policy is policy's `forEachModuleRef`, here with a looser guard so a malformed ref is reported, and a function stops it), and a function anywhere in the policy is refused; each is `CONFIG_INVALID` naming the key path (`policy.core.formatEachTitle.module`, `globals.module`, `environment.module`). Then the config is `structuredClone`d and a `DataCloneError` is `CONFIG_INVALID`. So a dialect's bare or relative ref fails as exit 2 here, not as exit 1 in every worker.
- **Loader extensions:** `.js .mjs .cjs .jsx .ts .mts .cts .tsx .json` (Jest's `moduleFileExtensions` order without `.node`; a neutral default of ours), a fresh frozen array per project.
- **Mock hoisting and per-module bindings (B13c):** the dialect's `loader.hoist` goes into `SerializedLoaderConfig.hoist` by value (data with `RegExp` and `Set` leaves, which clone; `null` for a dialect with none; with no dialect it is `ResolveOptions.native.hoist`, B27j, `provino`'s `nativeHoistPolicy('provino')`, so `mock` imported from `provino` hoists, and `null` without one; `assertNativeRefs` refuses a `hoist` that is not a policy object), its `moduleScope.names` into `loader.moduleScope` (`[]` for none, and `[]` when `core.injectGlobals` is off, so a module's wrapper declares no `jest` and a use is Jest's `ReferenceError`), and its `moduleScope.factory` ref into `SerializedProjectConfig.moduleScope` (`null` for none), whether or not globals are injected (it also serves `@jest/globals`). `assertWorkerConfig` checks that ref like the globals one (`moduleScope.module` absolute, D21).
- **Config modules compiled from `export default`** (CommonJS with `__esModule` and an own `default`) are unwrapped as Jest's `interopRequireDefault` does, so tsc/Babel output isn't an empty config.
- **Detect sees symlinks to files** (`stat`), not dangling links or links to directories. Dialect options are read from an own key of the config only.
- **Resolver keys (T3.3):** a neutral project's `aliases` and `resolution` (`moduleDirectories`, `modulePaths`, `resolver`) go to `SerializedLoaderConfig.aliases`, `.moduleDirectories`, `.modulePaths` and `.resolver` (a ref with export `default`), left out when empty. The worker's loader builds the name mapper from `aliases`, so this package needs no edge to `@provino/resolver`.
- **Loader conditions** come from calling the policy's `orchestrator.environmentConditions` behaviour in the coordinator, with the environment's *name* only. An `Environment` object's own `conditions` live in the worker and are not seen here.
- **Every failure is a `ConfigError`.** Policy errors (`resolvePolicy`, `serializePolicy`), a throwing dialect `detect` or factory or schema, and an unloadable behaviour are wrapped with the original as `cause`.
- **Every load reads the file again.** Node caches an import by URL, so `loadConfigFile` imports `file:///…/config.mjs?provino-load=<uuid>`: a URL of its own per call, which reloads `.mjs`, `.mts`, and `.js`/`.ts` under a package of `type: module` (checked on Node 24.22). Node's CommonJS loader ignores the query and keys by file name (`.cjs`, `.cts`, `.js`/`.ts` under `type: commonjs`), so the file's `require.cache` entry is deleted first (`createRequire(import.meta.url).cache`). **Fresh loads of one file run one after another** (`importFresh`, a chain keyed by the file's real path, the CommonJS cache's own key, and empty when nothing loads): Node's `import()` of a CommonJS file puts its module in that cache when it reads the file and asserts the entry is still that module when it runs it, so a second load deleting it in between fails with `ERR_INTERNAL_ASSERTION` (Node 24.22's `loadCJSModuleWithModuleLoad`). Two `run()` calls that overlap on one config reach it (Jest projects read at once did, on a shared CommonJS `resolver`, before the dialect stopped using this loader). Limits: each load stays in the ES module map for the life of the process (a small leak, accepted for config files), and only the config file itself is reloaded: a module it imports or requires keeps its cached copy, so edit-and-reload of a helper needs the process to restart. A config *function* runs on every call either way (it is called with `env` each time), so one that reads `process.env` always sees the current value; module-level code reads it at load time, and now does so per load. `import.meta.url` in the config carries the query; `import.meta.filename` and `dirname` don't.
- Tests use small fake dialects (`defineDialect`) and real config files written to `$TMPDIR` at test time (no `.js` is committed, D13). The package may not import `@provino/dialect-jest` (not in its manifest deps), so the real Jest dialect is exercised in `provino`'s tests.

## Transform entries and claims (`src/internal/transform.ts`)

`resolveTransforms`: a neutral project's `transforms`, `transformIgnorePatterns`, `transformConfig` and `transformHoistedMarkers` as `loader.transform` (`SerializedTransformConfig`, T3.8), or `undefined` for none. Each rule's `module` stays an absolute path or `file:` URL; a bare name resolves from the project's root (`createRequire`, `CONFIG_INVALID` naming `transform[i]` when it can't); a pattern that isn't a regular expression is `CONFIG_INVALID` (`transform[i].pattern`, `transformIgnorePatterns[i]`). `transformIgnorePatterns` are checked each and joined with `|` (`assertIgnorePatterns`: Jest's `ScriptTransformer` builds the joined one whatever `transform` holds, so `transform: {}` is checked too; `\k<b>` and `(?<a>x)` compile alone and fail joined), before either function returns. Jest fails every test file on a bad one; this is one earlier config error (exit 1 under `provino jest`), and a pattern bad alone that the join makes good (`(a` and `b)`) is refused where Jest takes it: a DIVERGENCES candidate. `assertWorkerConfig` checks each `transformer` ref like the others. `resolveTransformClaims` (B23e): the files the transforms take as `loader.transformClaims` (`TransformClaims`: the rules' patterns plus `standInTransformPatterns`, the ones Provino's pipeline stands in for, and `transformIgnorePatterns`), even when `transform` is absent, so the loader can tell which `node_modules` files a transform takes; `undefined` with neither; a stand-in or ignore pattern that isn't a regular expression is `CONFIG_INVALID`

**No claims for Jest's default patterns (B23e):** `resolveTransformClaims` returns `undefined` when an ignore pattern is one of the spellings of "ignore every `node_modules` path" (`/node_modules/`, `/node_modules`, `node_modules/`, `node_modules`), since no `node_modules` file is any transform's then; the ignore patterns are checked first anyway, once, by `resolveTransforms`.

## Coverage (B23b)

`NeutralProject.coverage` (a `SerializedCoverageConfig`, set by a dialect reader when coverage is on) is carried through `resolveNeutralProject` to `SerializedProjectConfig.coverage`, which is what makes a worker load `@provino/coverage/runtime`. Nothing here imports `@provino/coverage`.

## The `coverage` key (B28, D212)

`ConfigCoverage` (`@provino/types`, top level only: inside a project it is `CONFIG_UNKNOWN_KEY` saying it belongs to the top-level config) is parsed in `internal/input.ts` into `ResolvedConfig.coverage` (`ResolvedCoverage`, defaults applied: `enabled` false, provider `v8`, reporters `['text', 'lcovonly']`, directory the policy's `reportsDirectory`, `exclude` `['**/node_modules/**']`). An unknown reporter name is `CONFIG_INVALID`. `src/coverage.ts` has `withCoverage(projects, coverage, runRoot)`: called by `provino` only when the run collects coverage (the flag or `enabled`, never under watch), it gives each project's `SerializedProjectConfig.coverage` its worker config (`globalRoot` the run root, `projectRoot` the project's `rootDir`, `include` with `includeRoot: true`, `excludeGlobs`, the project's own include globs made absolute as `testFiles`, the config file and setup files as `excludePaths`). Only strings and arrays cross to the worker (NN4). `resolve-native.test.ts` and `coverage.test.ts` hold it.

## The native snapshot slice (B28, D211)

For a project with no dialect, `resolve.ts` layers `@provino/policy`'s `nativeSnapshotPolicy(native.snapshot)` from `NativeRuntimeRefs` over the neutral policy (Jest's `.snap` header, joins and format keys; the printer and the inline writer as refs, which `assertWorkerConfig` checks like the others).
