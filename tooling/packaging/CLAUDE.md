# tooling/packaging

How Provino's packages are built, packed and checked (B21e: T1.6, T1.10, T7.12, T10.1, T10.2, T10.4's agent half). Private; never published. It has a manifest node (`provino-packaging`, layer `tooling`, no workspace deps), and no package imports it: the build scripts and the root scripts run files in it.

## Map

| File | Role |
|---|---|
| `src/preset.ts` | `PRESET` (tsdown: `format: 'esm'`, `platform: 'node'`, `target: 'node22.15'`, `dts.generator: 'oxc'`, `fixedExtension: false` so `.js` and `.d.ts`, `hash: false`) and `packageConfig(dir)`: one entry per `exports` subpath that has a `provino-source` `.ts` file, named by its `import` target (`./dist/node/index.js` is entry `node/index`); `types` must be `./dist/<name>.d.ts`. A package whose subpaths have no `import` condition (`@provino/types`, T1.2) is built as declarations only (`emitDtsOnly`); mixing the two fails. `deps.onlyBundle: []` and `deps.onlyImport` (own name and declared dependencies) make a build fail on an undeclared import instead of bundling it |

| `src/umbrella.ts`, `tsdown.umbrella.config.ts` | The `provino` build: see "The umbrella" |
| `src/hygiene.ts` and its parts | `pnpm hygiene`: sections `install-scripts`, `changeset-config`, `umbrella-deps`, `release`, `packs`, `knip`, `api` (the keys of `RUNNERS`, which is their order). ## The umbrella (T1.10)

`provino` ships one bundle. `umbrellaConfig` returns two tsdown builds (JavaScript, then declarations: the chunk groups of the first would name the declarations' intermediate chunks too, and one overwrote the other). Every `@provino/*` package is inlined from source (the `provino-source` condition); the third-party packages `provino` lists in `dependencies` stay external, and `deps.onlyImport` fails the build on anything else. `provino`'s devDependencies are the `@provino/*` packages it inlines (`workspace:*`); `umbrella-deps` fails when its `dependencies` stop being what those packages (and theirs) need.

- **Worker modules by file (D21).** A coordinator resolves `import.meta.resolve('@provino/dialect-jest/runtime')` and the worker imports the answer. The plugin `workerRefs` rewrites each such call to a URL of that entry's file in this build (`WORKER_ENTRIES`: `worker/bootstrap`, `worker/main`, `worker/jest-runtime`, `worker/jest-global-setup` (the leaf the coordinator loads to report a failing Jest global hook: only `pretty-format`, never the runtime), `worker/policy-behaviours`, `worker/env-node`, `worker/env-jsdom`), so coordinator and worker share one copy of the engine. A `@provino/…` specifier the table lacks fails the build; the plugin is the one enforcement point: after the rewrite it also fails the build on any `import.meta.resolve(` whose argument is not a string literal (a comment line is not a call), so no test scans the sources (`umbrella.test.ts` plants each case).
- **Three chunks.** `codeSplitting.groups` takes, in priority order: `loading.js` (`LOADING`: the sources of `@provino/transform`, `@provino/resolver` and `@provino/loader`, about 190 kB, whatever number of entries use them), then `coordinator.js` (`COORDINATOR`: the run, discovery and the pool, reporters, config, `provino`'s own sources, the dialect's policy values; about 160 kB, with `includeDependenciesRecursively: false`, or it drags `transform`, `rpc` and `policy` in and the worker loads it), then every other module more than one entry uses in `shared.js` (about 115 kB: the engine, `expect`, mock, snapshot, timers, `rpc` and the rest). Third-party packages stay external, so each is imported by the chunk that holds the module that names it: `loading.js` is the only chunk that imports `oxc-parser`, `oxc-transform`, `oxc-resolver`, `oxc-walker`, `magic-string`, `@jridgewell/remapping` and `es-module-lexer` (about 17 ms of cold import, which `expect` never uses; T7.12's bar reads the expect runtime without it). The direction is `loading.js` → `shared.js` and `coordinator.js` → both, never back: `shared.js` imports no chunk. `worker/jest-runtime.js` (the Jest dialect's runtime, the `expect` a test file reaches) imports `shared.js` and no `loading.js`; `worker/main.js` imports `loading.js` (the runner builds the loader). A worker loads none of the coordinator (it also skips `tinyglobby` and `picomatch`), so its cold start is seven files from the package: `worker/bootstrap.js`, `shared.js`, `worker/main.js`, `loading.js`, `worker/jest-runtime.js`, `worker/policy-behaviours.js`, `worker/env-node.js` (`packages/provino/test/exports.test.ts` counts with a `registerHooks` recorder, at most 10, and a second test there fails if importing `provino` and `worker/jest-runtime.js` loads `loading.js`, `coordinator.js` or any Oxc, `magic-string`, `@jridgewell` or `es-module-lexer` file; Node 24 has no `node.module` trace category). Before the split the three were one `shared.js` of about 220 kB and the worker loaded six files, with the expect import carrying 18 more (the natives, `magic-string`, `@jridgewell/*`, `oxc-walker`). The cost is that a worker loads coordinator code that sits in the same chunk: `entriesAware: true` splits it by sharing set, but names chunks with `/` and gives the worker more files.
- **The bin's light files.** `src/cli.ts` imports `internal/quick.ts` (with the `usage.ts`, `reporter-names.ts` and `version.ts` it reads) and `internal/native-binding.ts` statically and the rest dynamically, so those five are kept out of both chunk groups (`BIN_LIGHT`, and `includeDependenciesRecursively: false` on `shared`): in `dist/cli.js` and its own small chunks, nothing that imports an Oxc package. Put another import in the bin and `--version` loads the natives again; `test/native-binding.test.ts` checks the loaded files. **The compile cache is one too** (B21d, T3.7): `internal/compile-cache.ts` is in `BIN_LIGHT_FILES`, and the transform's `v8cache/` and `cache/store.ts` (the `CACHEDIR.TAG` writer it shares) are kept out of the `loading` and `shared` groups, so the bin turns Node's compile cache on (`enableBinCompileCache`) before it imports the rest and `dist/cli.js` imports only `store.js` and `quick.js` of its own. The cost is one small shared chunk (`store.js`) that a worker's cold start loads too.
- **The bin.** `bin` stays `./src/cli.ts` in the workspace (the bench and harness read it); `publishConfig.bin` is `./dist/cli.js`, which `pnpm pack` writes into the tarball.

## Planted cases

Every check has a case that must fail, and a real-repo case that must pass.

| Gate | Test | Plant |
|---|---|---|
| untagged export | `gates.test.ts` | a `.d.ts` with an export lacking a release tag: API Extractor `ae-missing-release-tag` |
| `@public` change with no changeset | `gates.test.ts`, `checks.test.ts` | reports with a changed `@public` signature (and a `@beta` one that isn't a change); a temp git repo for the changesets added since the base |
| publint, attw | `gates.test.ts` | a missing types file, CommonJS under `"type": "module"`, an `exports` an `import` can't resolve |
| install script | `checks.test.ts` | `preinstall`, `install`, `postinstall` in any package, private or not, and the root |
| release workflow | `checks.test.ts` | each property removed from the draft (`id-token`, a token, a plain publish, no provenance, a self-hosted runner, a PR trigger, no publish step) |
| knip | `umbrella.test.ts` | a scratch project with an unused file, and one with an undeclared import |
| T7.12's ban list | `tooling/boundaries/src/planted.test.ts` | a runtime import of each banned package, flat and pnpm layouts |

## Choices and gotchas

- **Build inputs are exact.** `turbo.json` `build.inputs` names the import closure of the two tsdown configs (`preset.ts`, `package-json.ts`, `umbrella.ts`, the configs, and this package.json) and no glob, so editing a check (`hygiene.ts`) rebuilds nothing. `turbo.test.ts` derives the closure from the configs' imports and requires exactly that: a new file a config starts to import fails it until it is added.
- **Tiers.** D67's semver packages (`SEMVER_PACKAGES`) have committed API reports and the changeset gate. The other published packages are `@beta` as a whole: their `@public` tags (the whole tree uses them) mark an export as intended, and promise nothing, so they have no report. Retagging them would touch every package.
- **API Extractor** runs with `newlineKind: 'lf'`, `localBuild: true` into a temp folder (the committed report is compared by hand, so a difference needs a changeset and not only a rewrite), and `ae-forgotten-export` off (a bundled declaration file keeps the types it doesn't export). Reports are per entry point because it takes one; its own TypeScript is 6.0.3.
- **The changeset gate** compares the report at the merge base of `--base` and HEAD (`git show <merge-base>:<path>`; the base branch's tip would blame another PR's changes on a stacked branch) with the one on disk (or the one `--update-api` writes) and looks for `.changeset/*.md` added since (committed, staged or untracked). A base it can't resolve fails the run.
- **knip reads the built declarations.** `provino`'s `exports` make `dist/*.d.ts` entry files, so after a build knip sees them import `@jest/expect-utils`, `@standard-schema/spec` and `oxc-parser` and counts those dependencies as used; on a fresh checkout it doesn't, and `pnpm knip` failed. The root `knip.ts` (a TypeScript config, so it can read the manifest) ignores every `dependencies` entry of `packages/provino` by one pattern built from its package.json, so there is no list to keep in step: `umbrella-deps` proves each is needed by an inlined package and tsdown's `onlyImport` fails a build that imports one `provino` lacks. It passes, with no configuration hints, with `dist` absent or present.
- **knip** treats exports and exported types as warnings (a baseline of about 80 and 30, mostly vendored code and test helpers). `knip.ts` lists, with a reason, each dependency a static read can't see.
- **The release lint reads text, not YAML** (no YAML parser is a dependency). It strips comments and checks the lines. A draft carries `--dry-run` on every publish. The D75 ban matches npm, npx, yarn and bun where a command starts on any line (a `run:` value, a line of a `run: |` block, after `&&`, `||`, `;`, `|`, `(` or `$(`), after dropping `uses:` lines and the inputs under `with:` (so `cache: npm` is not a command). Checking it against the parsed workflow would take a YAML parser as a devDependency, which is Tyler's call.
- **The release is pnpm only (D75).** Checked 2026-11-12 against pnpm's docs (pnpm.io: `cli/publish`, `cli/stage`, `cli/dist-tag`) and pnpm 12.18.0: `pnpm publish --provenance` attaches provenance on its own under trusted publishing, pnpm exchanges the job's OIDC token (`id-token: write`) for a short-lived npm credential and falls back to configured credentials only when OIDC is unavailable, `pnpm stage publish` is npm's staged publishing (`--dry-run`, `-r`, `--force`; `pnpm stage approve` promotes with a one-time password), and `pnpm -r publish` and `pnpm -r stage publish` skip a version already on the registry (shown with a temp workspace holding `left-pad@1.3.0` and an unpublished package: the dry run lists only the unpublished one, and `--force` adds the published). So `templates/release.yml` is one `pnpm -r stage publish --access public --provenance` over the workspace, not a loop over `pnpm pack` tarballs, and the lint forbids every other publish and any npm, npx, yarn or bun command.
- **Biome owns formatting of `packages.json`;** the manifest edit that added `provino-packaging` and the ban lists went through `biome format`.
