# tooling/packaging

How Provino's packages are built, packed and checked (B21e: T1.6, T1.10, T7.12, T10.1, T10.2, T10.4's agent half). Private; never published. It has a manifest node (`provino-packaging`, layer `tooling`, no workspace deps), and no package imports it: the build scripts and the root scripts run files in it.

## The umbrella (T1.10)

`provino` ships one bundle. `umbrellaConfig` returns two tsdown builds (JavaScript, then declarations: the chunk groups of the first would name the declarations' intermediate chunks too, and one overwrote the other). Every `@provino/*` package is inlined from source (the `provino-source` condition); the third-party packages `provino` lists in `dependencies` stay external, and `deps.onlyImport` fails the build on anything else. `provino`'s devDependencies are the `@provino/*` packages it inlines (`workspace:*`); `umbrella-deps` fails when its `dependencies` stop being what those packages (and theirs) need.

- **Worker modules by file (D21).** A coordinator resolves `import.meta.resolve('@provino/orchestrator/worker/main')` and the worker imports the answer. The plugin `workerRefs` rewrites each such call to a URL of that entry's file in this build (`WORKER_ENTRIES`: `worker/bootstrap`, `worker/main`, `worker/policy-behaviours`, `worker/env-node`, `worker/env-jsdom`, `worker/api` (the native runtime's served `provino` module and globals, `@provino/api`, D186)), so coordinator and worker share one copy of the engine. A `@provino/…` specifier the table lacks fails the build; the plugin is the one enforcement point: after the rewrite it also fails the build on any `import.meta.resolve(` whose argument is not a string literal (a comment line is not a call), so no test scans the sources (`umbrella.test.ts` plants each case).
- **Three chunks.** `codeSplitting.groups` takes, in priority order: `loading.js` (`LOADING`: the sources of `@provino/transform`, `@provino/resolver` and `@provino/loader`, about 190 kB, whatever number of entries use them), then `coordinator.js` (`COORDINATOR`: the run, discovery and the pool, reporters, config, `provino`'s own sources, the dialect's policy values; about 160 kB, with `includeDependenciesRecursively: false`, or it drags `transform`, `rpc` and `policy` in and the worker loads it), then every other module more than one entry uses in `shared.js` (about 115 kB: the engine, `expect`, mock, snapshot, timers, `rpc` and the rest). Third-party packages stay external, so each is imported by the chunk that holds the module that names it: `loading.js` is the only chunk that imports `oxc-parser`, `oxc-transform`, `oxc-resolver`, `oxc-walker`, `magic-string`, `@jridgewell/remapping` and `es-module-lexer` (about 17 ms of cold import, which `expect` never uses; T7.12's bar reads the expect runtime without it). The direction is `loading.js` → `shared.js` and `coordinator.js` → both, never back: `shared.js` imports no chunk. The Jest dialect's runtime (the add-on's `runtime/index.js` since B27f, the `expect` a test file reaches) imports `internal/jest-runtime.js`, which imports `shared.js` and no `loading.js`; `worker/main.js` imports `loading.js` (the runner builds the loader). A worker loads none of the coordinator (it also skips `tinyglobby` and `picomatch`), so its cold start was ten files from the package on 2026-11-17 and is nine since B27e (`pack.js` folded into `loading.js`): `worker/bootstrap.js`, `shared.js`, `worker/main.js`, `lazy-api.js` (`shared.js` imports it), `loading.js`, `mode.js` (the compile cache's small chunk), `worker/policy-behaviours.js`, `worker/env-node.js`, and since B27f `internal/jest-runtime.js` and the add-on's `runtime/index.js` (ten over the two packages, which is what `exports.test.ts` counts); a native worker has `worker/expect-table.js` and `worker/api.js` in the runtime's place, ten (`packages/provino/test/exports.test.ts` counts with a `registerHooks` recorder, at most 10, and a second test there fails if importing `provino` and `@provino/dialect-jest/runtime` loads `loading.js`, `coordinator.js` or any Oxc, `magic-string`, `@jridgewell` or `es-module-lexer` file; Node 24 has no `node.module` trace category). Before the split the three were one `shared.js` of about 220 kB and the worker loaded six files, with the expect import carrying 18 more (the natives, `magic-string`, `@jridgewell/*`, `oxc-walker`). The cost is that a worker loads coordinator code that sits in the same chunk: `entriesAware: true` splits it by sharing set, but names chunks with `/` and gives the worker more files.
- **The dialect commands' chunks (B27e, B27f).** `jest-node.js` (`JEST_NODE`, priority 4) holds `provino jest`'s own files (`jest-command`, `jest-reporters`, `jest-selection`, `jest-root-hint`, `provino-flags`, `select-projects`) and `vitest-node.js` (`VITEST_NODE`) `provino vitest`'s `vitest-command.ts`. They import the dialects' `/node`, which are the add-ons' (below) and external, so only `cli.ts`'s dynamic imports reach them: `coordinator.js` and `shared.js` import no add-on, and a native run evaluates none (`packages/provino/test/native-load.test.ts`). `jest.js` and `vitest.js` (`provino/jest`, `provino/vitest`) re-export the add-ons. The chunks import `coordinator.js` and `shared.js`, never the reverse. The V8 code cache's `cache.ts` and `pack.ts` are `LOADING`'s (only the loader uses them; `BIN_LIGHT` keeps `v8cache/{index,mode,native}.ts` and `cache/store.ts`, and the `loading` group tests `LOADING` and not `BIN_LIGHT`, as `shared` does, so that list is the one source), which took `pack.js` out of every worker's cold start.
- **The `watch` chunk (B23f).** `watch.js` (`WATCH`, priority 5, `includeDependenciesRecursively: false`) holds `provino`'s `jest-watch.ts` and `watch-interrupt.ts`, the orchestrator's `watch/` (session, watcher, coalesce, stale) and the dialect's `node/watch/` (Jest's watch loop). `jest-command.ts` reaches it by `await import('./jest-watch.ts')` inside the `--watch`/`--watchAll` branch, so no other run, and no worker, loads it. Two files of the loop stay out because the bin uses them on every run: `plugin-error.ts` (`JestWatchPluginError`, split out of `plugin-host.ts`) and `terminal.ts` (`JEST_CLEAR_LINE`); in the watch group they made `cli2.js` import `watch.js` statically. `exports.test.ts` ("watch mode is its own chunk") fails if any chunk or worker file imports `watch.js` or `jest-watch.js` statically, if the dynamic import is not the one the bin has, and if a run without `--watch` (bin or worker) loads either.
- **The `live` chunk (B26).** `live.js` (`LIVE`, priority 5, `includeDependenciesRecursively: false`) holds `@provino/reporters/live` (the renderer, the `provino` reporter, the capability detection), with `live2.js` the facade of its dynamic import; `COORDINATOR` leaves `reporters/src/live/` out. `reportersFor` reaches it by `await import('@provino/reporters/live')` only when `provino` is chosen, so a worker, the `expect` import and a run with another reporter load none of it; what it shares with the other reporters (`style.ts`, the error serializer, `format.ts`'s pieces) stays in `coordinator.js`, which it imports. `exports.test.ts` ("the provino reporter is its own chunk") fails if a file outside it imports it statically, if anything but `coordinator.js` reaches it by dynamic import, if a worker loads it, or if `--reporter agent` loads it; `--reporter provino` must load it, and no run but `--reporter html` loads the `html` chunk.
- **The `html` chunk (B26 Phase 5).** `html.js` (`HTML`, priority 5, `includeDependenciesRecursively: false`) holds `@provino/reporters/html` (the reporter, the data, the document and the page's script and styles), with `html2.js` the facade of its dynamic import; `COORDINATOR` leaves `reporters/src/html/` out, and what it shares with the other reporters stays in `coordinator.js`. `reportersFor` reaches it by `await import('@provino/reporters/html')` only when `html` is chosen. The page's script is `renderReport` written with `Function.prototype.toString()`, so the bundler must leave it self-contained (the chunk is not minified): `exports.test.ts` ("the html reporter is its own chunk, and its page runs from the build") fails if a file outside it imports it statically, if anything but `coordinator.js` reaches it by dynamic import, if a worker or a run with another reporter loads it, or if the script of the page the built bin writes (one file, the CSP naming its hash) throws in a context that has nothing but its parameter and a DOM that answers every call with itself.
- **The `lazy-api` leaf.** `import 'provino'` (`dist/index.js`) must load no engine chunk, but the `lazy` forwarders (`@provino/lazy`'s `api.ts`) and the three leaves they import (`LazyError`, `setSiteVia` and `currentLazyRuntime`: `errors.ts`, `runtime/site.ts`, `slot.ts`) are used by other entries too, so `minShareCount: 2` would put them in `shared.js` and `index.js` would import its 125 kB. The leaves were always shared with the worker's entries; the forwarders became shared in B27b, when `worker/api` began to serve them in the native `provino` namespace. The `lazy-api` group (`LAZY_API`, priority 4, `includeDependenciesRecursively: false`) keeps those four in `lazy-api.js` (a few kB, importing only `node:url`); `shared.js` imports it, so a worker loads it too. `exports.test.ts` asserts `index.js` imports only `./lazy-api.js` and that importing `provino` loads no `shared.js`, `loading.js` or coordinator.
- **The bin's light files.** `src/cli.ts` imports `internal/quick.ts` (with the `usage.ts`, `reporter-names.ts` and `version.ts` it reads) and `internal/native-binding.ts` statically and the rest dynamically, so those five are kept out of both chunk groups (`BIN_LIGHT`, and `includeDependenciesRecursively: false` on `shared`): in `dist/cli.js` and its own small chunks, nothing that imports an Oxc package. Put another import in the bin and `--version` loads the natives again; `test/native-binding.test.ts` checks the loaded files. **The compile cache is one too** (B21d, T3.7): `internal/compile-cache.ts` is in `BIN_LIGHT_FILES`, and the transform's `v8cache/` and `cache/store.ts` (the `CACHEDIR.TAG` writer it shares) are kept out of the `loading` and `shared` groups, so the bin turns Node's compile cache on (`enableBinCompileCache`) before it imports the rest and `dist/cli.js` imports only `store.js` and `quick.js` of its own. The cost is one small shared chunk (`store.js`) that a worker's cold start loads too. **So is `internal/node-loader.ts`** (B23e): it imports `node:module` only and is inlined into `dist/cli.js`, which records Node's loader before it reads a config.
- **The bin.** `bin` stays `./src/cli.ts` in the workspace (the bench and harness read it); `publishConfig.bin` is `./dist/cli.js`, which `pnpm pack` writes into the tarball.

## The add-ons (B27f, D187)

`@provino/dialect-jest` and `@provino/dialect-vitest` are install units of their own (`ADD_ONS` in `src/internal-entries.ts`): each names `provino` as a peer at `workspace:*` (an exact version once packed), lists its third-party packages (the jest-* five, `pretty-format`, the four `@babel/*`, `babel-preset-current-node-syntax`, `pure-rand`; Chai, the Oxc pair, `picomatch`, `tinyglobby`) as its own `dependencies`, and has every `@provino/*` package as a dev dependency only, for its tests and the workspace's source mode.

- **One engine.** `packageConfigs` (`preset.ts`, what `tsdown.config.ts` builds) gives an add-on the plugin `internalImports`: every `@provino/*` import (static, dynamic or a type's) resolves, `order: 'pre'`, to its `provino/internal/<entry>` subpath from `INTERNAL_ENTRIES` and stays external, and each `import.meta.resolve('@provino/…')` of the engine (a worker ref) is rewritten to that subpath; the add-on's own subpaths stay. A specifier the table lacks fails the build. The umbrella exports each target (`./internal/jest-runtime`, `vitest-runtime`, `config`, `resolver`, `env-node`, `vite-alias`, `types`) from `packages/provino/src/internal/engine/`, re-export files kept out of `COORDINATOR` that name, value by value, what the add-ons' builds import (and every type, `export type *`; `@provino/policy` whole, since `slice-discipline` refuses its values by name in `provino`): an `export *` of the packages kept worker-only engine code in the graph, which landed in `shared.js` and cost the coordinator of every run about 250 kB (B27f's design round; `exports.test.ts` fails on a name an add-on imports that is missing, and on one exported that none imports); they are internal, with no semver and no API report (`apiEntries` skips them). The worker-side packages of one add-on share one entry, so its worker reads one file of the umbrella for all of them; `jest-runtime` leaves the resolver out, so the Jest `expect` loads no `loading.js` (T7.12). `internal/config` re-exports the two names the Vitest reader uses: all of `@provino/config` split the transform's `store.ts` into a chunk every worker loaded. `umbrella.test.ts` holds the table's targets equal to the exports, and `packages/provino/test/exports.test.ts` that every name an add-on's build imports is exported.
- **One file per worker.** An add-on's `./runtime` is a second build of its own (`WORKER_SUBPATHS`), so it shares no chunk with the coordinator's entries (`jest-require.ts` is then in both outputs). A Jest worker loads 10 files from the two packages: the 8 of `provino` a native worker has without its runtime, `internal/jest-runtime.js` and `dialect-jest:runtime/index.js`; a Vitest worker the same with its two.
- **Refs.** A dialect's refs are its own `import.meta.resolve` of its subpaths, so they name the installed add-on's files (D21); `workerRefs` fails the umbrella's build on an add-on specifier, and `provino jest` takes the environment adapter's ref from the dialect's globals ref.
- **The JS build** bundles every `@provino/*` package but the add-ons (`isEngine`, `neverBundle`), and `onlyImport` allows the add-ons' names; the declarations still inline the dialects' types, so `provino/jest` types without the add-on. **Declarations are two passes:** the public entries, then `internal/*` (its chunks in `internal/chunks/`), so the internal entries move no public declaration. The public pass keeps the add-ons' five former worker modules as entries (`DECLARATION_ONLY_ENTRIES`), whose files `dropDeclarations` leaves unwritten: its chunk graph, and the mangled names `etc/provino.api.md` lists (D67), are then B27e's, and the report equals it.
- **Loaded from the project.** `provino`'s `internal/add-on.ts` resolves its imports of an add-on from the project root first (`resolveAddOnsFrom`, a sync resolve hook, then Node's own resolution from `provino`), holds the add-on to `provino`'s version before it links, and its install line pins that version (`pnpm add -D @provino/dialect-jest@<version>`; npm's `latest` need not be it). The smoke's Jest app sets `hoist=false`.
- **The workspace cycle.** `provino` lists the add-ons as dev dependencies and they name it as a peer, so `pnpm-workspace.yaml` sets `ignoreWorkspaceCycles` (Turborepo orders `provino` after them; `pnpm -r` would refuse to sort). The boundaries manifest check ignores the `provino` peer (`tooling/boundaries/src/workspace.ts`).
- **`umbrella-deps`** skips the add-ons in `inlinedPackages` and adds `addOnProblems`: the peer at `workspace:*`, no `@provino/*` runtime dependency, no add-on among `provino`'s, no other package naming the peer (`checks.test.ts` plants each).

## The release workflow (B21h, D162–D165)

`.github/workflows/release.yml`, after Pixel Perfect's reference (`always-up-to-date`'s), runs on a pushed `v*` tag and nothing else. Its jobs: `check` (the tag is a version; every non-private `packages/*/package.json` has that version, which the `fixed` group keeps equal; the commit is an ancestor of `origin/main`; `packages/provino/CHANGELOG.md` has the line `## <version>`, which is the heading changesets writes; and the dist-tag is the first part of the prerelease, `rc` for `0.1.0-rc.0`, or `latest`), then in parallel `gates` (typecheck, `pnpm format-and-lint`, boundaries, both type-test jobs, `pnpm hygiene`; `fetch-depth: 0`, since hygiene measures API changes from the merge base with `origin/main`) and `test` (`pnpm test:shard run <1|2>`, the two shards CI runs, with CI's core-dump step; together they are `pnpm test`, and `test-shards.ts` fails if a package is in neither, or in both without being split: `provino` runs in both, each shard taking half its files through `PROVINO_TEST_SHARD` and `src/node-test.ts`, which puts `--test-shard` ahead of the globs, since Node ignores it after them), then `publish` (`contents: write` and `id-token: write` on this job alone; a frozen install, `pnpm build --force`, since no package has a `prepack`; `node tooling/packaging/src/cli.ts hygiene --only packs` on that build (the cli, since the `hygiene` script would build a second time), since the tarballs come from this job's `dist` and not the one `gates` checked; `pnpm -r publish`, which skips versions already on npm so a rerun after a partial publish is safe; and a GitHub release cut from the CHANGELOG entry with `awk`, `--prerelease` when the dist-tag isn't `latest`, skipped when it exists). pnpm's version is package.json's `packageManager`, as in `ci.yml`; Node's comes from `.tool-versions`. The `check` step's shell was run against a scratch repository for a matching tag, a wrong version, a stable and a numeric-prerelease tag and a commit off `main`, and the awk against a CHANGELOG with and without the entry (2026-11-17).

Versions: `.changeset/config.json` has one `fixed` group of the 22 public packages and `.changeset/pre.json` holds pre mode (`rc`). `pnpm changeset status --verbose` computes, without writing anything, `0.1.0-rc.0` for all 22 (every existing changeset is `minor` or `patch`, the group takes the highest, and the packages start at `0.0.0`). Never run `changeset version` outside the Version packages PR.

## The install matrix (B21h, T10.2, T10.3)

`.github/workflows/install-matrix.yml` runs only on `workflow_dispatch` (`gh workflow run install-matrix.yml`), started by hand (D168: no pull request, no push, no schedule; it is not a merge gate). It is the one file where npm, npx, yarn and bun may appear (D75): they are what it tests. No lint reads it (`release-lint.ts` reads `release.yml` alone).

- **`pack`** (ubuntu-24.04): a frozen install, `pnpm pack:all --out inputs/tarballs`, then `inputs/support/`: the three smoke files, written from `SMOKE_FILES` by importing `src/smoke.ts` (so they can't drift from it), and `support.sh`, a POSIX shell file the job writes from a heredoc in the workflow, so the shell every other job shares exists once. `inputs` is one artifact; a cell installs the `provino` and `@provino/dialect-jest` tarballs (B27f, D187: `provino_tarball` sets `DIALECT_TGZ` too; a registry cell publishes both; edited 2026-11-22, not yet run).
- **`cell`**: {ubuntu-24.04, ubuntu-24.04-arm, macos-15, windows-2025} × {npm 11, npm 12, pnpm 12, yarn 4 with the node-modules linker, bun} × Node {22.15.0, 24, 26} (`matrix.node`), `fail-fast: false`, 20 minutes (72 cells; the slowest took about a minute). Each cell puts its package manager on PATH from npm (`install_pm`, which checks the major version), installs `provino` into an empty `app/`, and asserts `provino --version` prints the packed version and `provino jest --ci` ends with `Tests: 3 passed, 3 total`. A Linux cell installs from a Verdaccio 7 (`docker run`, config written by `registry_start`: `provino` and `@provino/*` have no uplink, everything else proxies npmjs) with the tarball published into it as it is; macOS and Windows have no Docker, so they install the tarball by relative path (`file:` for yarn).
- **`alpine`**: the same, with npm, in `node:24-alpine`, started with `docker run --network host` from the host job (a `container:` job would run the actions on Alpine), against the host's Verdaccio.
- **Yarn Plug'n'Play is not a cell** (Tyler, 2026-11-19): Provino's workers die under it (every file ends as "The worker finished <file> without reporting its result"), so it is listed as a gap in `wiki/compatibility.md` until that is fixed.
- **T10.3's three cases**, each ending in `expect_suite_or_binding_message`: the suite runs, or `provino jest` exits 1 with one `Provino: the native Oxc binding` line, a `Missing:` line of `@oxc-*/binding-*` packages and no stack frame (`--version` must answer first). (1) `lockfile-linux` writes a `package-lock.json` on linux-x64 and removes every Oxc binding but `linux-x64-gnu` from it (the entries and the names in the three packages' `optionalDependencies`: with only the entries removed `npm ci` refuses the lockfile itself, `Missing: … from lock file`), then `lockfile-npm-ci` runs `npm ci` from it on macOS and Windows; (2) `omit-optional`: `npm install --omit=optional` on all three OSes; (3) `other-os`: pnpm with `supportedArchitectures` set to an OS that isn't the runner's (`pnpm-workspace.yaml`).
- **Choices.** Yarn's one-day `npmMinimalAgeGate` quarantines a tarball published a minute ago, so a registry install preapproves `provino` alone (`npmPreapprovedPackages`). The package managers come from `npm install -g` (`@yarnpkg/cli-dist@4` with `--force`, since runners ship Yarn 1), not corepack, which Node 26 doesn't ship. Output goes through files, not pipes: bash's `pipefail` fails a step whose `grep -q` ends its writer early. npm 12 requires Node `^22.22.2 || ^24.15.0 || >=26` and refuses to install itself on 22.15 (EBADENGINE), so `install_pm` retries with `--force` and a warning: that cell tests a pairing npm itself doesn't support.

## Planted cases

Every check has a case that must fail, and a real-repo case that must pass.

| Gate | Test | Plant |
|---|---|---|
| untagged export | `gates.test.ts` | a `.d.ts` with an export lacking a release tag: API Extractor `ae-missing-release-tag` |

## Choices and gotchas

- **Build inputs are exact.** `turbo.json` `build.inputs` names the import closure of the two tsdown configs (`preset.ts`, `package-json.ts`, `umbrella.ts`, the configs, and this package.json) and no glob, so editing a check (`hygiene.ts`) rebuilds nothing. `turbo.test.ts` derives the closure from the configs' imports and requires exactly that: a new file a config starts to import fails it until it is added.
- **Notices and license headers.** The build keeps some vendored files' headers and drops others (measured on 2026-11-13, over the vendored modules whose source has one: `provino`'s bundle keeps 11 of 13, `@provino/dialect-vitest`'s dist 2 of 19, `@provino/snapshot`'s 1 of 2), and some copied files never had one (Vitest's `jsdom-keys.ts` and `.each` code, `natural-compare`'s only has `@license`). So the headers are not what satisfies the licenses: `THIRD_PARTY_NOTICES.md`, with the full text for each upstream, is, and `packs` requires it in every tarball whose `dist` holds copied code (today `provino`, `@provino/dialect-jest`, `@provino/dialect-vitest`, `@provino/snapshot`, `@provino/env-shared`, from B23b `@provino/coverage`, and from B26 `@provino/reporters`). To add a vendor directory: write its `UPSTREAM.md`, name it in the root `THIRD_PARTY_NOTICES.md`, copy that file over every shipping package's copy, and list the file in `files` of any package that newly ships copied code. The Jenkins `junit-10.xsd` is test-only and ships nowhere.
- **Tiers.** D67's semver packages (`SEMVER_PACKAGES`) have committed API reports and the changeset gate. The other published packages are `@beta` as a whole: their `@public` tags (the whole tree uses them) mark an export as intended, and promise nothing, so they have no report. Retagging them would touch every package.
- **API Extractor** runs with `newlineKind: 'lf'`, `localBuild: true` into a temp folder (the committed report is compared by hand, so a difference needs a changeset and not only a rewrite), and `ae-forgotten-export` off (a bundled declaration file keeps the types it doesn't export). Reports are per entry point because it takes one; its own TypeScript is 6.0.3.
- **The changeset gate** compares the report at the merge base of `--base` and HEAD (`git show <merge-base>:<path>`; the base branch's tip would blame another PR's changes on a stacked branch) with the one on disk (or the one `--update-api` writes) and looks for `.changeset/*.md` added since (committed, staged or untracked). A base it can't resolve fails the run.
- **knip reads the built declarations.** `provino`'s `exports` make `dist/*.d.ts` entry files, so after a build knip sees them import `@jest/expect-utils`, `@standard-schema/spec` and `oxc-parser` and counts those dependencies as used; on a fresh checkout it doesn't, and `pnpm knip` failed. The root `knip.ts` (a TypeScript config, so it can read the manifest) ignores every `dependencies` entry of `packages/provino` by one pattern built from its package.json, so there is no list to keep in step: `umbrella-deps` proves each is needed by an inlined package and tsdown's `onlyImport` fails a build that imports one `provino` lacks. It passes, with no configuration hints, with `dist` absent or present.
- **knip** treats exports and exported types as warnings (a baseline of about 80 and 30, mostly vendored code and test helpers). `knip.ts` lists, with a reason, each dependency a static read can't see.
- **The release lint reads text, not YAML** (no YAML parser is a dependency). It strips comments and checks the lines, so the publish command stays on one line (flags on a continuation line fail loudly, not silently). The `on:` block must be exactly `push:` with a `tags:` that holds only `v*`, as a flow list or a block list. A step's own lines (for the checkout and setup-node rules) run from its `uses:` line to the next line indented less than the `uses` key. The D75 ban matches npm, npx, yarn and bun where a command starts on any line (a `run:` value, a line of a `run: |` block, after `&&`, `||`, `;`, `|`, `(` or `$(`), after dropping `uses:` lines and the inputs under `with:` (so `cache: npm` is not a command). Checking it against the parsed workflow would take a YAML parser as a devDependency, which is Tyler's call.
- **The release is pnpm only (D75).** Checked 2026-11-12 against pnpm's docs (pnpm.io: `cli/publish`, `cli/stage`, `cli/dist-tag`) and pnpm 12.18.0: `pnpm publish --provenance` attaches provenance on its own under trusted publishing, pnpm exchanges the job's OIDC token (`id-token: write`) for a short-lived npm credential and falls back to configured credentials only when OIDC is unavailable, `pnpm stage publish` is npm's staged publishing (`--dry-run`, `-r`, `--force`; `pnpm stage approve` promotes with a one-time password), and `pnpm -r publish` and `pnpm -r stage publish` skip a version already on the registry (shown with a temp workspace holding `left-pad@1.3.0` and an unpublished package: the dry run lists only the unpublished one, and `--force` adds the published). B21e drafted the staged form; D163 (2026-11-17) replaced it with the direct one, so `release.yml` is one `pnpm -r publish --access public --no-git-checks --provenance --tag "$DIST_TAG"` over the workspace, not a loop over `pnpm pack` tarballs, and the lint forbids `pnpm stage publish`, every other publish and any npm, npx, yarn or bun command. `pnpm publish --dry-run` (checked 2026-11-17 on pnpm 12.18.0, with `--no-git-checks --tag rc --access public`) lists all 22 public packages in dependency order and the private ones never.
- **Biome owns formatting of `packages.json`;** the manifest edit that added `provino-packaging` and the ban lists went through `biome format`.
